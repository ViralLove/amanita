# Amanita Passport — personhood-driven federated identity model

**Версия:** 1.0  
**Дата:** 2026-03-14  
**Методика:** run-analysis + проектное решение на основе ранее зафиксированной архитектуры SBT / DID / Passport.

---

## 1. Почему именно такой заголовок

Формула **personhood-driven identity model** по смыслу подходит, но в чистом виде она не покрывает ключевую часть вашей идеи: идентичность у нас не единая и не монолитная, а **федеративная**, распределённая по сообществам и затем оркестрируемая в Amanita Passport.

Поэтому для этой главы точнее использовать:

- **Personhood-driven**: в центре не real-name бюрократия и не аккаунт платформы, а человек как носитель устойчивой субъектности и репутации.
- **Federated identity model**: у одного человека может быть несколько community-level идентичностей и репутаций, которые не схлопываются в один примитивный профиль.

Итоговая формула:

**Amanita Passport — personhood-driven federated identity model**

Она лучше отражает:

- primacy человека над платформой;
- независимость сообществ;
- DID per community;
- автоматическую оркестрацию в Passport;
- холистическое, но не насильственное объединение репутации.

---

## 2. Исходные решения для этой модели

Ниже зафиксированы принятые вводные:

1. **Биометрия не является частью протокольной идентичности** и используется только как `local key unlock` на устройстве пользователя.
2. **DID создаётся per community**, а не как один глобальный DID на всю экосистему.
3. **Amanita Passport** — это не один DID, а **оркестрационный слой** над набором community DIDs и community souls.
4. **Public identity использует и display name, и handle.**
5. **Глобальный handle технически не проверяется**, поэтому используется community-prefixed handle.
6. **Пользователь сам выбирает, какое сообщество считать витриной личности** в Passport.
7. **Legal / compliance слой сейчас не является приоритетом** и не должен определять ядро архитектуры.
8. **Репутация федеративна:** внутри сообщества она первична, а на уровне Passport показывается составно и прозрачно, без схлопывания в один "магический" score.
9. **Оркестрация между сообществами автоматическая**, а не ручная.

---

## 3. Главный принцип модели

Идентичность в Amanita не должна строиться вокруг:

- официального имени;
- государственного реестра;
- единого централизованного identity provider;
- социальной платформы;
- биометрической базы.

Идентичность должна строиться вокруг комбинации:

- **personhood** — устойчивый субъект, за которым стоит живой человек;
- **community membership** — вход и признание внутри конкретного круга;
- **community reputation** — локальная репутация и роль;
- **federated orchestration** — Passport, который собирает все community-контексты в один холистический обзор.

Иными словами, **человек один, но его социально-профессиональные проявления множественны**. Протокол не должен ломать эту множественность.

---

## 4. Слои идентичности

### 4.1 Device trust layer

Это самый нижний слой доверия.

- Ключи пользователя защищаются на устройстве.
- Биометрия допускается только как локальный механизм разблокировки ключа.
- Биометрические данные, шаблоны, faceprint/fingerprint hash не покидают устройство.
- Для реализации подходят `Secure Enclave`, `Android Keystore`, `WebAuthn / passkeys`, локальный encrypted vault.

**Вывод:** биометрия здесь не идентифицирует человека для сети; она только разрешает локальное использование ключа.

### 4.2 Community identity layer

Это основной слой протокола.

Для каждого сообщества пользователь получает собственный набор сущностей:

- community DID;
- community soul;
- community reputation;
- community role / badges / trust path;
- community handle.

Здесь и возникает **первичная идентичность внутри сообщества**.

### 4.3 Passport orchestration layer

`Amanita Passport` — надслой над community identities.

Его задача:

- автоматически оркестрировать все community DIDs, принадлежащие одному человеку;
- показывать их как связанные контексты;
- давать пользователю выбрать **showcase community** — главную витрину личности;
- обеспечивать единый вход в экосистему маркетплейсов, каталогов и reputation views.

Passport не отменяет локальные идентичности, а **собирает их в холистическую картину**.

### 4.4 Ecosystem / marketplace layer

На уровне страны, региона или крупного мета-рынка Passport становится слоем отображения и маршрутизации:

- один человек может быть виден в нескольких сообществах;
- в каждом сообществе у него свой уровень зрелости, уверенности, профессионализма и роли;
- агрегатор видит не один flattening-profile, а **композицию локальных репутаций**.

---

## 5. Personhood без централизованной биометрии

Так как биометрия используется только для локального разблокирования ключа, **personhood в протоколе не должен доказываться биометрией**.

В этой архитектуре personhood лучше выражается через комбинацию:

- invite lineage / social graph происхождения;
- наличие soul в сообществе;
- накопленную локальную репутацию;
- community attestations;
- историю действий, завершённых сделок, contribution trail;
- при необходимости — внешние verifiable credentials, но не обязательные для ядра.

Это даёт максимум дистанции от централизованного контроля:

- нет общей базы биометрии;
- нет единого центра, который решает, кто "настоящий человек";
- нет привязки к государственным документам по умолчанию;
- доверие строится через сеть сообществ и репутационные траектории.

---

## 6. DID per community и роль Amanita Passport

Принцип **DID per community** здесь логичен и архитектурно сильнее, чем один глобальный DID на всё:

- каждое сообщество живёт на своих контрактах и своих адресах;
- каждое сообщество может иметь собственные правила admission, reputation и social mining;
- один и тот же человек в одном круге может быть мастером, а в другом — новичком;
- один глобальный DID слишком рано бы навязал единую модель личности.

Поэтому рекомендуемая структура такая:

- у человека есть **community DID A** в сообществе A;
- **community DID B** в сообществе B;
- **community DID C** в сообществе C;
- `Amanita Passport` автоматически оркестрирует их как принадлежащие одной personhood-основе.

Важно: Passport здесь не обязан быть "главным DID". Он может быть:

- federated resolver;
- orchestration profile;
- visual and reputational aggregator;
- routing layer для маркетплейсов и экосистемных сервисов.

Это лучше согласуется с вашей идеей независимых концентрических кругов.

## 7. Модель имени, псевдонима и handle

### 7.1 Что не должно быть ядром

Идентичность **не должна** строиться вокруг:

- `givenName`;
- `familyName`;
- real-name verification;
- уникальности по имени и фамилии.

Люди с одинаковыми именами существуют постоянно; имя не должно быть primary key.

### 7.2 Что должно быть ядром публичного слоя

Рекомендуемая пара:

- `displayName` — свободное имя самовыражения;
- `handle` — стабильный идентификатор для ссылок, поиска и UX.

Это означает:

- `displayName` может быть псевдонимом, мононимом, художественным именем, коллективным именем;
- `handle` даёт читаемую уникальность;
- криптографическая уникальность обеспечивается не именем, а DID / soul / ключами.

### 7.3 Один длинный field или имя/фамилия

Для вашей философии свободы я рекомендую:

- **в ядре профиля хранить одно основное поле**: `displayName`;
- **не делать обязательными** `name` / `surname`;
- если когда-либо понадобится совместимость с legacy-формами, добавить это как **опциональный вторичный слой**, а не как основной профиль.

То есть базовая модель должна быть:

```json
{
  "displayName": "Moss Architect",
  "handle": "@spiral:moss-architect"
}
```

А не:

```json
{
  "firstName": "Maria",
  "lastName": "Ivanova"
}
```

Причина простая: `displayName` не тащит за собой старую систему, а `firstName/lastName` почти неизбежно тащат.

### 7.4 Нужен ли всё же привычный формат имени

Да, но только как опциональная совместимость, и не сейчас.

Если позже понадобится:

- для бухгалтерии;
- для доставки;
- для локального compliance;
- для внешних интеграций;

то лучше добавлять это не в ядро Passport, а в отдельный private / selective-disclosure слой.

## 8. Уникальность: внутри сообщества и кросс-комьюнити

### 8.1 Что должно быть уникальным

- community DID;
- soul reference внутри конкретного сообщества;
- community handle;
- Passport linkage between community identities.

### 8.2 Что не должно быть обязано быть уникальным

- `displayName`;
- псевдоним как форма самовыражения;
- имя или фамилия, если они когда-либо появятся как optional fields.

### 8.3 Handle-модель

Так как глобальную уникальность проверить нельзя или не стоит, рекомендуемая форма:

- `@community:handle`

Примеры:

- `@spiral:moss-architect`
- `@forest:anna-root`
- `@craft:signal-baker`

Плюсы:

- uniqueness scope ясен;
- не нужен глобальный name registry;
- пользователь может иметь разные handles в разных сообществах;
- в Passport можно выбрать, какой community handle показывать как основную витрину.

### 8.4 Что должно показываться в Passport

Passport должен отображать:

- `showcaseCommunityId`;
- `showcaseHandle`;
- `showcaseDisplayName`;
- список остальных community personas;
- явную связь между ними.

То есть глобальный публичный вид не равен глобальному уникальному username. Это **витрина**, а не централизованная учётка.

---

## 9. Федеративная репутация

### 9.1 Базовый принцип

Репутация должна быть:

- **локально первичной** внутри сообщества;
- **федеративно обозримой** на уровне Passport;
- **не схлопнутой** в один общий score.

### 9.2 Почему нельзя делать один глобальный score

Потому что человек:

- может быть сильным в одном домене и слабым в другом;
- может чувствовать себя уверенно в одном сообществе и осторожно в другом;
- может менять роль, траекторию и уровень ответственности между кругами.

Один универсальный рейтинг уничтожает эту реальность.

### 9.3 Рекомендуемая модель показа

Passport должен собирать:

- community reputation components;
- badges и role markers;
- completed deals / contributions;
- trust lineage;
- confidence context per community.

А затем показывать:

- **federated overview**;
- **community-by-community breakdown**;
- **showcase view**, выбранный пользователем;
- при необходимости derived metrics, но не как единственную правду.

---

## 10. Автоматическая оркестрация

Так как пользователь выбрал модель **automatic orchestration**, нужно различать два уровня:

### 10.1 Автоматическая связь community identities

Система автоматически понимает, что разные community DIDs относятся к одной personhood-основе, если выполнены правила связки, определённые протоколом.

Это может строиться на:

- общем управляющем ключе;
- подтверждённой Passport linkage credential;
- подписи challenge несколькими community identities;
- event-driven orchestration в оркестраторе Passport.

### 10.2 Автоматическое построение общего профиля

Passport автоматически:

- индексирует community souls и community DIDs;
- подтягивает локальные reputation views;
- собирает Passport profile;
- выставляет showcase community по выбору пользователя.

Пользователь не должен руками связывать каждый контекст в интерфейсе маркетплейса.

## 11. Интеграция Amanita Passport с X

### 11.1 Базовый принцип

X не должен становиться identity root. Он должен использоваться как:

- интерфейс привычного публичного присутствия;
- слой социального майнинга;
- транспорт для discovery;
- внешний social-signal surface.

То есть **Passport использует X, но не зависит от X онтологически**.

### 11.2 Что реально можно использовать

На текущем уровне доступны как минимум такие механизмы:

- **Log in with X / Sign in with X** — для опциональной привязки X-аккаунта к Passport-профилю;
- **Web Intents** — для follow / post / reply / share without building own social shell;
- **ссылочный трафик через публичные Passport URLs**;
- **preview cards** при публикации ссылок на Passport / community profile pages;
- **X API** как канал чтения публичных социальных сигналов и построения community growth tools, если это оправдано и экономически доступно.

### 11.3 Как использовать X для reputation preview

Самый практичный путь:

1. У каждого Passport / community profile есть публичный web URL.
2. Эта страница отдает корректные Open Graph / X card meta tags.
3. При шаринге ссылки в X появляется rich preview:
   - displayName / showcase handle;
   - сообщество;
   - ключевые reputation markers;
   - краткий summary;
   - визуальный Passport card.

Это не требует, чтобы X понимал вашу нативную модель DID. Для X это просто shareable page, а для пользователя — привычный интерфейс предпросмотра.

### 11.4 Как использовать X для social mining

X может работать как внешний слой социального майнинга сообщества:

- публикация invite campaigns;
- threads о достижениях, опыте, кейсах;
- organic discovery новых кругов;
- follow-graph как soft signal интереса;
- social proof вокруг community activity;
- распространение Passport / community reputation pages через привычный UI.

При этом важно:

- не делать X обязательным;
- не делать число лайков ядром репутации;
- использовать X как surface и amplifier, а не как sovereign source of truth.

### 11.5 Что можно связать с X-аккаунтом

Опционально Passport может хранить:

- `xHandle`;
- `xUserId`;
- `xProfileUrl`;
- `xLinkedAt`;
- `xVerificationStatus` как purely external marker.

Но это должен быть именно **external identity link**, а не замена soul / DID.

### 11.6 Ограничения интеграции с X

- X не является вашим trust layer.
- X может менять API-условия, стоимость, rate limits и политику доступа.
- Preview-карточки и социальный трафик зависят от интерфейса X, а не от протокола Amanita.
- Поэтому вся ценность Passport должна жить в собственных DID, credentials, souls и репутационных данных; X — только фасад и distribution layer.

## 12. Рекомендуемая модель данных для публичного профиля

Минимальный публичный слой для Passport:

```json
{
  "passportId": "apass:country-region:user-001",
  "showcaseCommunityId": "spiral",
  "showcaseHandle": "@spiral:moss-architect",
  "showcaseDisplayName": "Moss Architect",
  "communityProfiles": [
    {
      "communityId": "spiral",
      "did": "did:amanita:spiral:abc123",
      "handle": "@spiral:moss-architect",
      "displayName": "Moss Architect",
      "role": "maker",
      "reputation": 180
    },
    {
      "communityId": "forest",
      "did": "did:amanita:forest:def456",
      "handle": "@forest:anna-root",
      "displayName": "Anna Root",
      "role": "guide",
      "reputation": 92
    }
  ],
  "externalIdentities": {
    "x": {
      "handle": "@mossarchitect",
      "profileUrl": "https://x.com/mossarchitect"
    }
  }
}
```

Здесь:

- нет обязательных `firstName/lastName`;
- есть `displayName` и `handle`;
- есть федеративный список community profiles;
- есть витрина;
- есть внешняя интеграция с X как optional layer.

---

## 13. Архитектурные рекомендации

### 13.1 Что рекомендуется принять как принцип

- `displayName` — primary human-facing field;
- `@community:handle` — primary navigational identifier;
- DID per community;
- automatic Passport orchestration;
- federated reputation with full per-community breakdown;
- X as interface layer, not trust root;
- biometric only as local key unlock.

### 13.2 Что не рекомендуется делать

- обязательный real-name onboarding;
- глобальный username registry;
- один глобальный reputation score;
- биометрию как сетевой идентификатор;
- обязательную зависимость Passport от X;
- firstName/lastName как основу профиля.

---

## 14. Итог

Для Amanita Passport наиболее адекватна следующая формула:

**не one-identity system, а personhood-driven federated identity model.**

Это означает:

- человек сохраняет свободу самовыражения;
- сообщества сохраняют автономию;
- репутация остаётся контекстной;
- Passport даёт холистическое окно обзора;
- X используется как знакомый социальный интерфейс и канал social mining;
- биометрия не превращается в централизованный контрольный механизм.

В такой модели Passport становится не "новым паспортом государства", а **оркестратором живых контекстов личности** в независимой экосистеме сообществ.
