# Feasibility Analysis — X integration for LoveDo posts, tokenization and social mining

**Версия:** 1.0  
**Дата:** 2026-03-14  
**Методика:** run-analysis + факты из кода репозитория + проверка публично доступных интерфейсов X.

---

## 1. Цель анализа

Проверить реализуемость трёх сценариев использования X внутри Amanita Passport / LoveDo-экономики:

1. использовать X как **транспорт для discovery** LoveDo-постов (отзывов);
2. при создании X-поста через интеграцию с `Amanita Passport` делать его также **LoveDoPost token** в экосистеме Amanita через proxy API + вызов смарт-контракта;
3. принимать лайки на такие X-посты и проводить их через алгоритм так, чтобы часть из них становилась **superlikes** и элементом social mining.

---

## 2. Краткий вывод

### 2.1 Итог по трём сценариям


| Сценарий                                 | Feasibility          | Краткий вывод                                                                                                                                                                                                 |
| ---------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `X as discovery transport for LoveDo`    | **Высокая**          | Реализуемо практически сразу через Passport URLs, preview cards, optional Sign in with X и, при необходимости, X API для discovery/analytics.                                                                 |
| `X post -> LoveDoPost token`             | **Средняя**          | Реализуемо через Amanita proxy/orchestrator, но не атомарно. Нужны Saga/idempotency, хранение `xPostId`, X account link и канонический metadata flow.                                                         |
| `X likes -> superlikes -> social mining` | **Низкая / средняя** | В текущей архитектуре **не стоит** напрямую приравнивать X likes к on-chain superlikes. Реалистичен только многоступенчатый алгоритм: X likes как off-chain signal -> кандидат -> oracle / attest / finalize. |


### 2.2 Главный архитектурный вывод

**X хорошо подходит как внешний discovery / distribution / attention layer, но плохо подходит как source of truth для social mining.**

Для Amanita это означает:

- X можно и стоит использовать для распространения LoveDo и Passport-профилей;
- X-пост можно связывать с on-chain LoveDo token;
- X-like не должен автоматически становиться on-chain superlike без дополнительной валидации, иначе ломается анти-сибил и community trust model.

## 3. Факты из текущего кода Amanita

### 3.1 LoveDoPostNFT уже существует как ончейн-сущность для отзывов

`contracts/LoveDoPostNFT.sol`:

- `mintLoveDoPost(address sellerTo, string calldata uri)` — минт LoveDo NFT;
- NFT хранит `author`, `sellerTo`, `linkedSeller`, `superlikes`, `timestamp`;
- `tokenURI` задаётся внешним URI;
- есть события `LoveDoMinted` и `Superliked`;
- есть лимиты:
  - максимум 8 постов в месяц на пользователя;
  - максимум 8 упоминаний на seller;
  - максимум 8 superlikes в месяц на адрес.

### 3.2 Superlike уже жёстко встроен в социальную модель доверия

`contracts/LoveDoPostNFT.sol`:

- `addSuperlike(uint256 tokenId, uint256 expectedNonce)`:
  - запрещает self-like;
  - требует существование поста;
  - требует nonce;
  - требует, чтобы лайкер и автор были в одном invite-circle;
  - требует `amanitaRegistry.hasSellerRole(loveDos[tokenId].sellerTo)`.

То есть текущий **superlike не является "любым внешним лайком"**. Это строгое доверительное действие внутри invite-graph модели.

### 3.3 LoveEmissionEngine завязан на superlike как эмиссионный триггер

`contracts/LoveEmissionEngine.sol`:

- `emitForSuperlike(uint256 tokenId, address liker)` вызывает `loveDo.addSuperlike(tokenId)`;
- начисляет `loveAccrued` и `lgovAccrued`;
- `claimLOVECOIN()` и `claimLGOV()` строятся поверх этого механизма.

### *3.4 В LoveDo / emission слое уже есть архитектурный долг*

*В репозитории уже зафиксировано несоответствие:*

- `contracts/LoveEmissionEngine.sol` *ожидает:*
  - `addSuperlike(uint256 tokenId) returns (bool)`
  - `getPost(...) returns tuple`
- *а* `contracts/LoveDoPostNFT.sol` *реально имеет:*
  - `addSuperlike(uint256 tokenId, uint256 expectedNonce)`
  - `getPost(...) returns (LoveDo memory)`

*Это зафиксировано в:*

- `contracts/docs/analysis/tasks/task-contracts-docs-vs-code-mismatches.md`

***Вывод:** до серьёзной X-интеграции нужно сначала выровнять канонический LoveDo stack внутри самого проекта.*

## 4. Что реально даёт X как внешняя система

По доступным публичным интерфейсам X можно опираться на следующее:

- **Log in with X / Sign in with X** — для опциональной привязки X-аккаунта к профилю пользователя;
- **Web Intents** — для share / reply / follow без построения собственного social shell;
- **X Cards / preview cards** — для rich preview при публикации ссылок;
- **X API** — для работы с постами, пользователями и публичными социальными сигналами, но с pay-per-usage, rate limits и меняющейся продуктовой политикой.

При этом X:

- не является trust root;
- не является стабильным публичным протоколом;
- может менять pricing, quotas и условия доступа;
- не должен быть единственным источником истины для on-chain эмиссии.

## 5. Сценарий 1 — X как транспорт для discovery LoveDo-постов

### 5.1 Что именно здесь хочется получить

Пользователь или сообщество публикует LoveDo-отзывы в X, и X используется как:

- discovery layer;
- канал распределения внимания;
- социальная витрина для Passport / LoveDo;
- механизм привычного интерфейса для людей.

### 5.2 Реализуемость

**Высокая.**

Это самый реалистичный и наименее рискованный сценарий.

### 5.3 Рекомендуемая реализация

1. У каждого LoveDo-поста в Amanita есть публичный URL.
2. Этот URL рендерит:
  - текст/summary отзыва;
  - автора;
  - seller;
  - community;
  - число on-chain superlikes;
  - Passport / community context.
3. Страница отдаёт:
  - Open Graph metadata;
  - X card metadata;
  - image preview.
4. Публикация в X ведёт людей на Amanita URL, а не наоборот.

### 5.4 Почему это правильно

- source of truth остаётся в Amanita;
- X используется как transport/distribution layer;
- discovery дешёв и понятен пользователям;
- можно строить social mining без передачи core reputation логики в X.

### 5.5 Ограничения

- X выдаёт внимание, но не гарантирует справедливое распределение;
- previews зависят от кэша X;
- охваты и API-видимость зависят от правил X.

### 5.6 Вывод по сценарию 1

Этот сценарий рекомендуется внедрять первым. Он даёт максимум пользы при минимальном архитектурном риске.

## 6. Сценарий 2 — создание X-поста как LoveDoPost token

### 6.1 Целевая идея

При создании X-поста пользователь хочет, чтобы:

- пост появился в X;
- одновременно появился on-chain `LoveDoPost token`;
- обе сущности были связаны между собой через `xPostId` / URL / metadata.

### 6.2 Реализуемость

**Средняя.**

Реализуемо, но не как "один магический атомарный клик" без дополнительной orchestration logic.

### 6.3 Почему не атомарно

Здесь участвуют две разные системы:

- X API;
- блокчейн-транзакция на `LoveDoPostNFT`.

Между ними невозможно гарантировать настоящую атомарность. Возможны состояния:

- X post создался, а mint не прошёл;
- mint прошёл, а X post не создался;
- обе операции прошли, но связь не записалась;
- пользователь отозвал доступ к X;
- сеть/X API дали rate-limit или временный сбой.

То есть нужна **Saga / orchestrator model**, а не "один tx".

### 6.4 Правильная архитектура

Рекомендуемый поток:

1. Пользователь логинится в Amanita и опционально связывает Passport с X-аккаунтом.
2. В UI Amanita создаёт LoveDo через **Amanita composer**, а не через чистый x.com composer.
3. Composer формирует канонический payload:
  - `sellerTo`
  - `communityId`
  - текст LoveDo
  - media
  - metadata JSON / IPFS CID
  - intent `publishToX=true`
4. Amanita proxy/orchestrator:
  - публикует пост в X от имени пользователя;
  - получает `xPostId` / canonical URL;
  - пишет metadata в IPFS/Arweave;
  - вызывает `mintLoveDoPost(...)`;
  - добавляет в metadata ссылку на X post.
5. Если X publish succeeds, а mint fails:
  - статус = `x_published_chain_failed`;
  - нужен retry / recover flow.
6. Если mint succeeds, а X publish fails:
  - статус = `chain_minted_x_failed`;
  - нужен retry / publish later flow.

### 6.5 Что нужно добавить в metadata LoveDo

Минимум:

```json
{
  "sourcePlatform": "x",
  "sourcePostId": "1234567890",
  "sourcePostUrl": "https://x.com/.../status/1234567890",
  "crossPosted": true,
  "canonicalOrigin": "amanita",
  "communityId": "spiral",
  "passportId": "apass:...",
  "sellerTo": "0x...",
  "authorDid": "did:amanita:spiral:..."
}
```

### 6.6 Ключевой продуктовый выбор

Есть два подхода:

#### A. X-first

Пользователь создаёт пост прямо в X, а Amanita потом пытается его токенизировать.

Минусы:

- тяжело гарантировать корректный format;
- нет гарантии, что есть нужные metadata;
- сложно подтверждать author intent;
- больше space для spoofing и race conditions.

#### B. Amanita-first

Пользователь создаёт LoveDo в Amanita, а X становится каналом кросс-постинга.

Плюсы:

- Amanita остаётся canonical source;
- проще валидировать seller/community/passport context;
- проще обеспечивать idempotency;
- проще связывать Passport, DID и community metadata.

**Рекомендация:** брать именно `Amanita-first`.

### 6.7 Зависимости и блокеры

Перед внедрением нужно:

- привести `LoveDoPostNFT` и `LoveEmissionEngine` к одному каноническому API;
- определить, где source of truth по `seller role`;
- ввести metadata schema для cross-posted LoveDo;
- спроектировать retry/idempotency policy в proxy API.

### 6.8 Вывод по сценарию 2

Сценарий реализуем, но только через **Passport-aware proxy/orchestrator** и только при модели **Amanita-first, X-second**.

## 7. Сценарий 3 — X likes как источник superlikes и social mining

### 7.1 Желаемый результат

Люди ставят лайки в X на кросспостнутый LoveDo, после чего часть лайков проходит алгоритм и становится:

- `superlikes`;
- сигналом social mining;
- потенциальным основанием для начисления LOVECOIN / LGOV.

### 7.2 Реализуемость

**Низкая / средняя**, если речь о прямой конверсии `X like -> on-chain superlike`.

### 7.3 Почему прямая конверсия плоха

Текущий `LoveDoPostNFT` задаёт очень строгую модель superlike:

- лайкер должен быть в invite-graph;
- лайкер должен быть в том же круге, что и автор;
- действует monthly limit;
- действует anti-replay через nonce;
- seller должен быть валидирован;
- superlike — это не просто внимание, а **социально валидированное действие доверия**.

Обычный X like:

- не доказывает identity внутри Amanita;
- не доказывает community membership;
- не доказывает invite lineage;
- может быть ботовым;
- не соответствует текущим ограничениям контракта.

Поэтому прямое соответствие:

`X like = LoveDo superlike`

архитектурно неверно.

### 7.4 Что можно сделать вместо этого

Нужна многоступенчатая модель:

#### Шаг 1. Сбор off-chain signals

Amanita indexer/proxy собирает сигналы:

- X likes;
- reposts;
- replies;
- profile linkage;
- interaction history;
- community overlap.

#### Шаг 2. Алгоритм кандидатов

Система определяет, какие сигналы могут стать **candidate superlikes**.

Примеры критериев:

- X account связан с Passport;
- Passport связан с community DID;
- пользователь реально состоит в community;
- нет self-like;
- пользователь входит в тот же trust circle;
- достигнут trust score threshold;
- это не бот / не всплеск аномальной активности.

#### Шаг 3. Нормализация в Amanita identity space

Сигнал переводится из:

- `xUserId`

в:

- `passportId`
- `communityDid`
- `wallet`

Без этой нормализации делать superlike нельзя.

#### Шаг 4. Finalization

После валидации сигнал может:

- либо стать **off-chain superlike attestation**;
- либо быть подтверждён seller'ом / oracle / community moderator;
- либо вызвать on-chain `addSuperlike(...)` уже от доверенного системного актора.

### 7.5 Рекомендуемая модель уровней

Нужно разделить три уровня:

1. **Like** — внешний social signal из X.
2. **Qualified Like** — X like, прошедший Amanita algorithm.
3. **Superlike** — только тот qualified signal, который финализирован в Amanita trust model.

То есть:

`X like != superlike`

но:

`X like -> qualified candidate -> superlike`

может быть валидной архитектурой.

### 7.6 Важный продуктовый риск

Если дать raw X engagement влиять на токен-эмиссию слишком прямо, получится:

- покупка внимания;
- бот-фарминг;
- централизация репутации через алгоритмы X;
- вынос social mining из Amanita в платформенную экономику X.

Это противоречит personhood-driven и community-trust модели.

### 7.7 Сбор лайков: технические ограничения

Даже если API позволяет читать likes/engagement, practically нужно учитывать:

- доступ зависит от плана и квот X API;
- event ingestion может быть нестабилен;
- нельзя проектировать токен-эмиссию на механике, где внешний провайдер может поменять доступ в любой момент;
- поллинг safer, чем ставка на "идеальный webhook", но дороже и медленнее.

### 7.8 Вывод по сценарию 3

Сценарий реалистичен только в такой формулировке:

**X likes используются как off-chain signals для ранжирования и отбора кандидатов, а on-chain superlikes рождаются только после Amanita-native валидации.**

- публичные LoveDo URLs;
- X cards / preview;
- share to X;
- optional Sign in with X.

- Amanita-first composer;
- X cross-post via proxy API;
- `xPostId <-> tokenId` mapping;

- сбор лайков / reposts / replies;
- scoring;
- anti-bot heuristics;
- candidate superlikes.

### Фаза 4. Controlled superlike finalization

- qualified likes;
- Amanita-native validation;
- oracle / attester / seller confirmation;
- только после этого on-chain superlike/emission.

## 11. Архитектурные рекомендации

### 11.1 Что рекомендуется

- использовать X прежде всего как **discovery and distribution layer**;
- сделать `Amanita-first` модель создания LoveDo;
- хранить каноническую связь `tokenId <-> xPostId`;
- вводить слой `qualified likes`, а не прямой мост `like -> superlike`;
- сохранять source of truth в Amanita contracts / Passport / community DID.

### 11.2 Что не рекомендуется

- делать X главным identity root;
- делать X-post canonical source of LoveDo;
- минтить on-chain superlike автоматически по каждому X like;
- строить токен-эмиссию на сыром engagement X;
- внедрять X-like-based mining до выравнивания `LoveDoPostNFT` и `LoveEmissionEngine`.

## 12. Итог

Три сценария имеют разную степень зрелости:

- **Discovery через X** — хорошая и практически готовая идея.
- **Кросспостинг X post + LoveDo token** — хорошая идея, но требует Passport-aware proxy/orchestrator и модели Saga.
- **Лайки X как superlikes** — в текущем виде нельзя считать каноничной on-chain механикой; это возможно только как многоступенчатая система off-chain qualification с Amanita-native finalization.

Итоговая правильная формула:

**X должен усиливать LoveDo-экономику, но не определять её сущность.**

Source of truth должен оставаться в:

- Amanita Passport;
- community DID;
- LoveDoPostNFT;
- LoveEmissionEngine;
- invite / trust graph.

## 13. Процесс токенизации X-поста в LoveDo — простым языком

**Важно:** X не является эксклюзивным UI. Это **один из стартовых точек**: пользователь может создать LoveDo из веб-приложения Amanita, из мобильного приложения, из бота или через «старт с X». Ниже описан именно сценарий «старт с X»: пользователь решает опубликовать отзыв (LoveDo), и мы заодно публикуем его в X и делаем ончейн-токен.

### Как это выглядит для пользователя

1. Пользователь заходит в Amanita (Passport, приложение или бот) и выбирает «Написать LoveDo» или «Опубликовать отзыв».
2. Указывает, **кому** отзыв (продавец / мастер из своего круга), пишет текст, при желании прикладывает медиа.
3. Ставит галочку «Опубликовать также в X» (или по умолчанию включено — в зависимости от продукта).
4. Жмёт «Опубликовать».
5. Система: создаёт запись в Amanita, минтит LoveDoPost NFT, при успехе публикует пост в X и связывает пост в X с этим NFT. Пользователь видит ссылку на свой пост в X и на страницу LoveDo в Amanita.

То есть **точка входа — Amanita**, а X — канал распространения. Альтернатива: пользователь сначала пишет пост в X, потом в Amanita нажимает «Токенизировать мой последний пост в X» — тогда система читает пост по API, проверяет автора и привязку к Passport, и только после этого минтит LoveDo. В обоих случаях **источник правды и валидации — Amanita**, X — только источник текста/медиа или площадка для публикации.

### Что происходит под капотом (коротко)

- Данные отзыва (кому, текст, метаданные) сохраняются у нас и при необходимости уезжают в IPFS/Arweave.
- Вызывается смарт-контракт `LoveDoPostNFT.mintLoveDoPost(sellerTo, uri)` — появляется ончейн-токен (LoveDo).
- Если включён кросспост в X: наш бэкенд от имени пользователя (через сохранённый OAuth) вызывает X API «создать пост», получает ID поста в X.
- Мы сохраняем связку: `tokenId ↔ xPostId` (и при необходимости URL). В метаданных LoveDo (uri) храним `sourcePlatform: "x"`, `sourcePostId`, `sourcePostUrl`.
- Если публикация в X не удалась — токен уже есть, статус «не опубликовано в X», можно повторить публикацию позже. Если не удался минт — пост в X можно удалить или оставить просто как обычный твит без токена.

Итог: **токенизация = сначала минт LoveDo у нас, потом при желании публикация в X и сохранение связи**. X не заменяет наш UI — он один из каналов.

## 14. Реальный X API: полный поток (на базе публичной документации)

Ниже — какие **реальные** вызовы X API нужны для сценария «создать пост в X + заминтить LoveDo + потом учитывать лайки». Актуальные endpoint'ы и ограничения см. в [X Developer Portal](https://developer.x.com) и в тарифах (раздел 19).

### 14.1 Создание поста в X

- **Endpoint:** `POST /2/tweets`
- **Назначение:** создать пост (текст, опционально медиа) от имени пользователя.
- **Аутентификация:** OAuth 2.0 (user context) — от имени того, кто пишет LoveDo. Без user context постить нельзя.
- **Тело запроса (упрощённо):** `text` (до 280 символов в v2), опционально `media.media_ids`, `reply_settings` и др.
- **Ответ:** объект с `data.id` — это **xPostId** (snowflake ID поста в X). Его мы сохраняем в нашей БД и в метаданных LoveDo как `sourcePostId`.

Ограничения по тарифам: лимиты на количество постов в месяц и в 15 минут (см. раздел 19). На Free — порядка 500 постов/месяц на приложение; для мультипользовательского продукта нужен как минимум Basic или pay-per-use.

### 14.2 Получение поста и метрик (лайки, репосты)

- **Endpoint:** `GET /2/tweets` с параметром `ids=<xPostId>` и `tweet.fields=public_metrics,created_at,author_id`.
- **Назначение:** проверить, что пост существует, взять `like_count`, `retweet_count`, `reply_count` и т.д.
- **Аутентификация:** Bearer (app) или OAuth в зависимости от тарифа. Чтение чужих постов на Free почти недоступно; на Basic и выше — в рамках квот reads.

Так мы можем показывать в Amanita «сколько лайков у этого LoveDo в X» и использовать эти цифры в алгоритме кандидатов для superlike (см. раздел 17).

### 14.3 Список пользователей, лайкнувших пост

- **Endpoint:** `GET /2/tweets/:id/liking_users` (или эквивалент в актуальной версии API — в документации X указан как endpoint для получения списка пользователей, поставивших лайк посту).
- **Назначение:** получить список X-аккаунтов (user id), которые лайкнули пост. Нужен для маппинга «лайк в X → кандидат superlike»: проверяем, есть ли у этого X user привязка к Passport и к тому же community/invite-circle.
- **Ограничения:** доступность и квоты зависят от тарифа. На Free этот endpoint недоступен; на Basic — в рамках общих read-лимитов. Частые вызовы по многим постам быстро съедают квоту.

Итого по API: **создать пост** — `POST /2/tweets`; **узнать метрики и кто лайкнул** — `GET /2/tweets` + `GET /2/tweets/:id/liking_users`. Полный поток токенизации: наш бэкенд после минта LoveDo вызывает `POST /2/tweets`, сохраняет `xPostId` и при необходимости обновляет uri/metadata.

## 15. Идентификация LoveDo-постов в ленте X

Чтобы в ленте X (и в поиске) можно было понимать, что пост — это именно LoveDo из Amanita, нужен **устойчивый признак**, по которому и люди, и наша система могут его опознать.

### 15.1 Варианты без партнёрства с X

- **Уникальный хештег.** Например `#LoveDo` или `#AmanitaLoveDo`. В текст поста при кросспостинге добавляем хештег. Плюсы: просто, не зависит от X. Минусы: подделка тривиальна (любой может написать #LoveDo без токена); нужен поиск по хештегу и последующая проверка по нашей базе `xPostId → tokenId`.
- **Канонический URL в посте.** В текст или в карточку поста включаем ссылку на страницу LoveDo в Amanita, например `https://amanita.xxx/lovedo/123` (где 123 — tokenId или slug). При открытии ссылки показывается rich preview (Open Graph / X Cards). Плюсы: однозначная привязка к нашему токену; пользователь переходит в экосистему. Минусы: URL можно скопировать и вставить в чужой пост — тогда опознавание «этот пост = этот LoveDo» только по факту совпадения URL в нашей базе (мы знаем, какой xPostId мы создали для tokenId 123).
- **Комбинация.** Хештег + обязательная ссылка на Amanita в каждом кросспосте. В нашей системе считаем LoveDo-постом в X только тот пост, для которого мы сами вызвали `POST /2/tweets` и сохранили `xPostId ↔ tokenId`. Остальные посты с #LoveDo — просто «упоминания», без автоматической токенизации.

### 15.2 Идентификация в нашей системе

- В **нашей** базе LoveDo-пост в X идентифицируется однозначно по паре `(xPostId, tokenId)` в таблице связок. По `xPostId` мы достаём `tokenId`, контракт, seller, author. Для отображения в «ленте» внутри Amanita мы можем показывать посты из X по списку `xPostId`, которые есть в этой таблице, и подтягивать метрики через `GET /2/tweets?...public_metrics`.
- В **ленте самого X** универсального «официального» типа поста «LoveDo» нет — X не знает про наш контракт. Поэтому идентификация там — только по хештегу и/или по URL. Фильтр «показать только LoveDo» возможен только в нашем приложении (мы фильтруем по своим xPostId).

### 15.3 Если будет партнёрство с X

Теоретически при партнёрстве можно обсуждать: кастомный тип карточки, служебные метаданные поста (например `partner_metadata.type = "amanita_lovedo"`, `tokenId`), выделенный хештег или пометка в UI. Это не гарантировано и не обязательно для MVP; для старта достаточно хештега + URL + хранение связки у нас.

## 16. Вывод on-chain социально майнящихся лайков (superlikes)

Лайки в X сами по себе **не** являются on-chain superlike. Они становятся входом в процесс, который заканчивается on-chain только после проверок Amanita.

### 16.1 Цепочка в общих чертах

1. **Сбор сигналов.** По постам, которые у нас заведены как LoveDo (есть запись `xPostId → tokenId`), периодически вызываем X API: метрики поста и список лайкнувших (`liking_users`). Получаем набор пар (xPostId, xUserId лайкера).
2. **Кандидаты.** Для каждого лайкера проверяем: привязан ли этот X-аккаунт к Passport; есть ли у этого Passport/кошелька душа в том же community; входит ли лайкер в тот же invite-circle, что и автор поста; не автор ли это поста (self-like); не превышены ли лимиты superlike в месяц. Если всё ок — это **qualified like** (кандидат в superlike).
3. **Маппинг в Amanita.** xUserId → wallet/address в нашей системе (через связку X ↔ Passport). Без привязки X к Passport лайк не может стать superlike.
4. **Финализация on-chain.** Кто-то должен вызвать контракт. Варианты: (A) доверенный backend с EMITTER_ROLE вызывает `LoveEmissionEngine.emitForSuperlike(tokenId, likerAddress)` после того как внутренний процесс зафиксировал qualified like; (B) продавец или модератор в UI подтверждает «засчитать суперлайк» — тогда с бэкенда вызывается тот же метод; (C) оракул/аттестатор подписывает решение, и контракт принимает подпись. В любом случае на контракте вызывается уже существующая логика: `addSuperlike` + эмиссия. То есть **on-chain социально майнящиеся лайки = те же superlikes, что и сейчас**, только источник сигнала «кто лайкнул» — не только наш UI, но и X, прошедший квалификацию.

### 16.2 Важно

- Ончейн меняется только в момент вызова `addSuperlike` / `emitForSuperlike`. До этого всё off-chain: лайки в X, таблица кандидатов, проверки.
- Лимиты контракта (8 superlikes в месяц на адрес, один суперлайк на пост от одного адреса, один круг доверия) остаются. Мы просто «подставляем» в эту модель адрес, полученный из X после проверки привязки и круга.

### 16.3 Сценарий с пушами и явным согласием лайкера (предложение)

Идея: **не** засчитывать лайк в X как суперлайк автоматически, а периодически проверять, кто лайкнул LoveDo-пост, и **предлагать** пользователям с привязанным Amanita Passport оформить суперлайк для майнинга — через пуш с понятным контекстом и лимитами.

#### Кто инициирует проверку

Проверки «кто лайкнул» логично делать **от имени системы** (оркестратор/бэкенд), а не буквально «от лица автора поста» с его OAuth: у автора может не быть выданного нам токена X, да и не нужно нагружать его аккаунт массой read-запросов. Смысл «от лица автора» здесь — **в контексте поста**: мы проверяем лайки именно по тем постам, которые принадлежат авторам (у нас есть `xPostId → tokenId → author`). То есть:

- **Кто дергает API:** наш бэкенд с app-level доступом к X API (Bearer или сервисный OAuth).
- **По каким постам:** по всем LoveDo-постам в X, для которых есть связка `xPostId ↔ tokenId` в нашей базе (или по подмножеству: например только за последние N дней или по запросу автора «обновить лайки по моим постам»).

#### Пошаговый поток

1. **Периодический опрос.** По расписанию (раз в день, раз в 6 часов — с учётом квот X API) для каждого такого xPostId вызываем `GET /2/tweets/:id/liking_users` (и при необходимости пагинацию). Получаем список xUserId лайкнувших.
2. **Фильтр по Passport.** Для каждого xUserId проверяем: есть ли в нашей системе привязка «этот X-аккаунт ↔ Amanita Passport». Если нет — этот лайкер в данном цикле не участвует (можно не слать пуш или слать разовое «привяжи X к Passport, чтобы участвовать в суперлайках»).
3. **Проверка кандидата в superlike.** Для привязанных к Passport проверяем: тот же community/invite-circle, что и автор поста; не автор поста; лимиты контракта (ещё не ставил суперлайк этому посту; не исчерпан лимит суперлайков в месяц у этого адреса). Если всё ок — считаем лайкера **кандидатом на суперлайк**.
4. **Пуш и информирование.** Кандидату отправляем пуш (in-app, email или оба) с сутью:
  - «Ты лайкнул LoveDo-пост [краткое описание/ссылка]. Хочешь оформить суперлайк для майнинга? Это поддержит продавца и засчитается в social mining».
  - Показать **текущее состояние лимитов:** сколько суперлайков у пользователя осталось в этом месяце (например «5 из 8»), что один суперлайк на пост — один раз, что суперлайк возможен только в рамках своего круга доверия.
  - Кнопки: «Да, дать суперлайк» / «Позже» / «Нет».
5. **Подтверждение и ончейн.** Если пользователь нажимает «Да»:
  - либо он в приложении подписывает транзакцию (мы вызываем от его кошелька нужный метод, если контракт это допускает);
  - либо мы фиксируем согласие в нашей БД и backend с EMITTER_ROLE вызывает `LoveEmissionEngine.emitForSuperlike(tokenId, likerAddress)` при соблюдении всех правил контракта (nonce, лимиты, круг — ещё раз проверяем перед вызовом).
  - Важно: один и тот же (xPostId, xUserId) не должен приводить к повторным пушам «дать суперлайк» после того, как суперлайк уже поставлен или пользователь явно отказался (храним состояние: `already_superliked` / `declined_prompt`).

#### Что даёт такой сценарий

- **Согласие и прозрачность:** суперлайк ставится только после явного действия пользователя; он видит последствия и лимиты.
- **Нет автоматической подстановки:** мы не приравниваем «лайк в X» к «суперлайк», а только предлагаем конвертировать.
- **Удобный контекст:** в пуше можно показать автора поста, продавца, текущие лимиты и ссылку на разбор «что такое суперлайк» в хелпе.
- **Снижение спама:** пушим только тем, кто реально может дать суперлайк (Passport + тот же круг), и не повторяем запрос, если уже суперлайк поставлен или отказ.

#### Технические нюансы

- **Частота проверок.** Зависит от квот X API: каждый вызов `liking_users` — read. Можно проверять не все посты каждый раз, а по приоритету (свежие, с новыми лайками по метрикам) или по запросу автора.
- **Канал пуша.** In-app предпочтителен (пользователь уже в экосистеме). Email — запасной вариант для тех, у кого нет активной сессии. X DM возможен только при наличии прав и партнёрских ограничений X — не обязательно для MVP.
- **Идемпотентность.** Один и тот же лайкер не должен получать дважды предложение «дать суперлайк» по одному и тому же посту после того, как он уже дал суперлайк или нажал «Нет». При повторном опросе liking_users мы сверяемся с нашей таблицей «суперлайки по tokenId» и «отказы/промпты».
- **Автор поста.** Автор может в настройках включить/выключить «предлагать лайкерам из Passport оформить суперлайк по моим LoveDo» — чтобы не слать пуши от имени контекста его поста без его согласия (если решим, что настройка нужна).

#### Резюме по разделу 16.3

Предложенный сценарий хорошо ложится на модель «qualified like → явное действие пользователя → on-chain superlike»: X-лайк даёт только **повод для пуша**, а суперлайк появляется в контракте только после согласия лайкера и проверки лимитов/круга. Дополнять документ можно явной схемой состояний (лайк в X → кандидат → пуш отправлен → согласие/отказ → суперлайк on-chain) и списком полей для таблицы «промпты суперлайка» (xPostId, tokenId, xUserId, passportId, status, sent_at, responded_at).

## 17. Партнёрство с X

### 17.1 Нужно ли для описанного сценария

**Для MVP — нет.** Реализуемо на публичном API:

- публикация поста — `POST /2/tweets` (OAuth user context);
- чтение метрик и списка лайкнувших — на тарифах Basic и выше или pay-per-use;
- идентификация LoveDo в ленте X — хештег + URL + наша таблица `xPostId ↔ tokenId`.

Партнёрство не обязательно, чтобы «X как старт» и токенизация работали.

### 17.2 Когда партнёрство может быть полезно

- **Выделенный тип поста / карточка.** Чтобы в ленте X посты LoveDo визуально отличались (бейдж, тип карточки) — нужны договорённости с X.
- **Расширенные квоты или отдельный SLA.** При большом объёме постов и read-запросов (лайки по многим постам) тарифы могут стать высокими; партнёрский контракт может дать отдельные лимиты или условия.
- **Compliance и данные.** Удаление поста в X, приостановка аккаунта — для синхронизации с нашей стороной полезны compliance-стримы; они доступны на Enterprise. Партнёрство может упростить доступ к таким возможностям.
- **Официальная интеграция в продукт X.** Упоминание в каталоге интеграций, совместные кейсы — только через договорённости с X.

Итого: **старт без партнёрства; партнёрство — для масштаба, узнаваемости и возможных привилегий по API/compliance.**

### 18.3 Оценка для сценария «X как старт + social mining по лайкам»

- Допустим: 1 000 LoveDo-постов в X в месяц; по каждому посту раз в день запрашиваем метрики и раз в день — список лайкнувших; плюс user lookup для части лайкеров.

## 19. Реализуемость сценария на других платформах (Facebook, Instagram, TikTok)

Для сценария «постить через API + OAuth + метрики поста + идентификаторы лайкнувших и комментаторов» проверены возможности трёх платформ. Итог — в таблице и кратко по каждой.

### 19.1 Сводная таблица


| Требование                               | X (Twitter)                        | Facebook                                     | Instagram                                    | TikTok                                              |
| ---------------------------------------- | ---------------------------------- | -------------------------------------------- | -------------------------------------------- | --------------------------------------------------- |
| Постинг через API                        | ✅ `POST /2/tweets`                 | ✅ Graph API (user feed, page posts)          | ✅ Graph API (media publish, reels, carousel) | ✅ Content Posting API (video)                       |
| OAuth                                    | ✅ OAuth 2.0 / 1.0a                 | ✅ Facebook Login                             | ✅ Facebook Login for Business / Instagram    | ✅ OAuth 2.0                                         |
| Метрики поста (счётчики)                 | ✅ `tweet.fields=public_metrics`    | ✅ Insights, summary (reactions count)        | ✅ Insights (likes, comments, reach и т.д.)   | ✅ Research API / status (like_count, comment_count) |
| Список идентификаторов **лайкнувших**    | ✅ `GET /2/tweets/:id/liking_users` | ❌ Только агрегат (список по Post deprecated) | ❌ Только агрегат в официальном Graph API     | ❌ Нет (есть только «видео, лайкнутые юзером»)       |
| Список идентификаторов **комментаторов** | ✅ через поиск/ответы по твиту      | ✅ `GET /{post-id}/comments` (поле `from`)    | ✅ комментарии с данными об авторе            | ✅ Research API: список комментариев с commenter     |


**Вывод:** полный сценарий «пост + метрики + идентификаторы лайкнувших» по публичному API реализуем **только на X**. На Facebook, Instagram и TikTok списка лайкнувших в официальном API нет; идентификаторы комментаторов доступны на всех трёх.

### 19.2 Facebook

- **Постинг:** Graph API — создание поста в ленте пользователя или на странице (`POST /{user-id}/feed`, страничные посты). Нужны права доступа к публикации и OAuth.
- **Метрики:** Insights, а также `summary=true` по реакциям — получаем сводные счётчики (like, love, wow и т.д.). Реакции по объекту Post: endpoint `/reactions` в текущей документации даёт типы реакций, но для **поста** в актуальных версиях API список отдельных пользователей, поставивших лайк/реакцию, **не возвращается** — только агрегат (total_count). Раньше был `GET /{post-id}/likes` со списком пользователей — он объявлен deprecated (v8.0+, полное отключение с ноября 2020).
- **Комментарии:** `GET /{post-id}/comments` — список комментариев, в каждом объекте есть поле `from` с информацией об авторе комментария (идентификатор пользователя и т.д.). Подходит для «идентификаторы комментаторов».
- **Итог по Facebook:** постить и получать метрики по посту можно; идентификаторы комментаторов — да; **идентификаторы лайкнувших/поставивших реакцию по посту — нет** в рамках официального API. Сценарий с пушами «хотите дать суперлайк» по списку лайкнувших на Facebook через публичный API реализовать нельзя.

### 19.3 Instagram

- **Постинг:** Instagram Graph API — публикация контента (фото, видео, reels, carousel) от имени бизнес-/креатор-аккаунта. OAuth через Facebook Login for Business или Instagram. Есть лимиты (например 200 вызовов в час) и уровень доступа (Standard/Advanced).
- **Метрики:** Insights по медиа — лайки, комментарии, охват, сохранения и т.д. (агрегат). Задержка данных до 48 часов; метрики хранятся до 2 лет.
- **Лайкнувшие:** В актуальной официальной документации Meta **нет** endpoint вида «список пользователей, лайкнувших данное медиа». Доступны только агрегированные показатели (like count). Упоминания про `GET /media/{media-id}/likes` относятся к устаревшему или неофициальному API; в текущем Graph API такого нет.
- **Комментарии:** Есть работа с комментариями (получение, ответы, модерация). По комментариям можно получать автора (идентификатор пользователя), т.е. **идентификаторы комментаторов** доступны.
- **Итог по Instagram:** постить и получать метрики можно; идентификаторы комментаторов — да; **список лайкнувших по медиа в официальном API недоступен**. Сценарий «лайк в Instagram → пуш → суперлайк» по официальному API не реализуем; возможен только сценарий по комментаторам (предлагать суперлайк тем, кто прокомментировал).

### 19.4 TikTok

- **Постинг:** Content Posting API — загрузка и публикация видео (Direct Post или в черновики). OAuth 2.0, лимиты на запросы (например 6 post-запросов в минуту на пользователя). Неаудированные приложения ограничены приватным просмотром до прохождения модерации.
- **Метрики:** Статус поста и после модерации — post_id, состояние публикации. Research API (при доступе) даёт по видео счётчики: like_count, comment_count, view_count, share_count и т.д.
- **Лайкнувшие:** Официальный API **не предоставляет** список пользователей, лайкнувших конкретное видео. Есть endpoint «видео, которые лайкнул указанный пользователь» (`user/liked_videos`), т.е. направление «пользователь → видео», а не «видео → пользователи-лайкеры». Для сценария «кто лайкнул этот LoveDo-пост» данных нет.
- **Комментарии:** Research API: endpoint списка комментариев по video_id — возвращаются комментарии с данными об авторе (commenter). **Идентификаторы комментаторов** таким образом получить можно.
- **Итог по TikTok:** постить и получать метрики по видео можно; идентификаторы комментаторов — да; **список лайкнувших по видео — нет**. Аналогично Instagram: сценарий с суперлайками по лайкам через официальный API не реализуем; по комментариям — теоретически можно строить предложения «оформить суперлайк» комментаторам.

### 19.5 Общий вывод по платформам

- **Единственная платформа**, на которой из коробки реализуем полный сценарий (пост + метрики + **идентификаторы лайкнувших** + при желании комментаторы) — **X**.
- **Facebook, Instagram, TikTok:** постинг, OAuth и метрики поста (счётчики) есть; идентификаторы **комментаторов** есть; **идентификаторов лайкнувших** в официальном API нет. Поэтому:
  - сценарий с пушами «вы лайкнули LoveDo — хотите дать суперлайк?» по списку лайкнувших на этих платформах через публичный API **не реализуем**;
  - возможны альтернативы: предлагать суперлайк по **комментаторам** (кто прокомментировал — получает пуш с предложением оформить суперлайк), либо ограничиваться на этих платформах только discovery и счётчиками без персональных пушей по лайкам.

При расширении LoveDo на Facebook/Instagram/TikTok имеет смысл закладывать в архитектуру отдельный слой «источник сигнала»: для X — лайки + комментарии; для остальных — только комментарии (и при появлении доступа к спискам лайкнувших — добавить позже).
