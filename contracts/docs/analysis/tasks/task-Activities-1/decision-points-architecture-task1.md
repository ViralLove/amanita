## Концепт: matchmaking-платформа для activities (после решений)

**Участники экосистемы:**
- **Создатель активности (creator)** — активированный пользователь с ACTIVITY_CREATOR_ROLE; создаёт активность, сам переводит её в публикацию (active = true) через авторизованный UI; может снять с публикации (active = false).
- **Участник (participant)** — ищет и находит активности (matchmaking).
- **Платформа (admin)** — управление контрактом (пауза, апгрейд, при необходимости force deactivate).

**Lifecycle on-chain:** только **active** (false = черновик, true = опубликовано). Контроль качества и «только свой UI» — в UI + API (валидация по гайду, авторизация приложений).

Ниже — исходные точки принятия решений и варианты (исторический контекст); актуальная архитектура — в [roles-architecture-synthesis.md](../../../roles-architecture-synthesis.md).

## 1. Идентичность создателя Activity (кто может вызывать createActivity)

**Вопрос:** Кто имеет право создавать запись Activity в контракте?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. SpiralEngine: активированный пользователь с ролью** | Как в ProductRegistry: `hasRole(SELLER_ROLE, msg.sender)` и `usedInviteByUser(msg.sender) != 0`. Либо ввести в SpiralEngine новую роль (например ACTIVITY_CREATOR_ROLE). | ✅ Один источник правды (SpiralEngine), меньше дублирования ролей. Доп. внешний вызов (~2–5k gas). | ✅ Единые правила для всех: вход через инвайт и роль; нет «ручного» назначения создателей только в ActivityRegistry. | ✅ Кто создатель — видно из SpiralEngine (роль + активация); контракт не скрывает критерий. |
| **B. Локальная роль в ActivityRegistry (CREATOR_ROLE)** | Роль хранится только в ActivityRegistry; админ выдаёт `grantRole(CREATOR_ROLE, account)`. | ✅ Нет вызова SpiralEngine при create; чуть дешевле по газу. | ⚠️ Админ может произвольно добавлять/убирать создателей; нет связи с общей активацией в экосистеме. | ⚠️ Критерий «кто создатель» живёт только в ActivityRegistry; для пользователя менее очевидна связь с инвайтами. |
| **C. Любой адрес (без проверки)** | createActivity может вызвать любой. | ✅ Максимально дёшево по газу. | ❌ Нет контроля качества; спам, фейковые активности. | ❌ Нет явного критерия «кто может создавать». |

**Рекомендация:** **A** — привязка к SpiralEngine (активированный пользователь + роль). Для консистентности с ProductRegistry и концептом «один вход в экосистему» (инвайт). Подвариант: использовать **SELLER_ROLE** (создатель активности = тот же пул, что и продавец) или ввести **ACTIVITY_CREATOR_ROLE** в SpiralEngine, если создатели активностей и продавцы продуктов должны быть разными множествами.

## 2. Роль «модератор»: где хранить и как именовать

**Вопрос:** Кто может переводить статус SentToReview → Approved и Approved → Published? Где эта роль задаётся — в SpiralEngine или в ActivityRegistry?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. Роль только в ActivityRegistry (MODERATOR_ROLE)** | `bytes32 MODERATOR_ROLE = keccak256("MODERATOR_ROLE")`; выдаёт админ; проверка `onlyRole(MODERATOR_ROLE)` для переходов SentToReview→Approved и Approved→Published. | ✅ Нет зависимости от SpiralEngine для модерации; один вызов при updateActivityStatus. | ✅ Чёткое разделение: создатели — через SpiralEngine, модераторы — явно назначены в ActivityRegistry. | ✅ В контракте и событиях видно, что есть отдельная роль модератора; список модераторов проверяем через getRoleMember. |
| **B. Роль в SpiralEngine (ACTIVITY_MODERATOR_ROLE)** | Новая роль в SpiralEngine; ActivityRegistry хранит `ISpiralEngine` и проверяет `spiralEngine.hasRole(ACTIVITY_MODERATOR_ROLE, msg.sender)`. | ⚠️ Доп. внешний вызов при каждом updateActivityStatus модератором. | ✅ Единый центр ролей экосистемы; модератор — часть спиральной иерархии. | ✅ Кто модератор — видно из SpiralEngine; но нужно знать про два контракта. |
| **C. Только ADMIN в ActivityRegistry** | Переходы SentToReview→Approved и Approved→Published разрешены только `ADMIN_ROLE` (или DEFAULT_ADMIN_ROLE). Отдельной роли «модератор» нет. | ✅ Минимум ролей, проще код. | ⚠️ Админ = и оператор платформы, и модератор контента; смешение обязанностей. | ⚠️ Неочевидно, что «модерация» = действие админа; сложнее аудит «кто именно модерировал». |

**Рекомендация:** **A** — **MODERATOR_ROLE в ActivityRegistry**. Модерация — функция именно реестра активностей; не обязательно вешать её на SpiralEngine. Эффективность (меньше внешних вызовов), честность (явное назначение модераторов), прозрачность (роль и события в одном контракте).

## 3. Кто может переводить статус (разбивка по переходам)

**Вопрос:** Для каждого перехода статуса — кто уполномочен его делать?

| Переход | Варианты | Эффективность | Честность / справедливость | Прозрачность |
|---------|----------|----------------|----------------------------|--------------|
| **Draft → SentToReview** | Только creator активности. | ✅ Одна проверка: `activities[id].creator == msg.sender`. | ✅ Только автор отправляет на ревью; нет подделки «отправил на ревью» со стороны третьих лиц. | ✅ Явно: смена статуса на SentToReview возможна только от создателя. |
| **SentToReview → Approved** | Только роль модератора (или ADMIN). | ✅ Одна проверка роли. | ✅ Решение о допуске принимает только модератор/админ. | ✅ В событиях видно, что статус сменил модератор/админ. |
| **Approved → Published** | Только роль модератора (или ADMIN). | ✅ Аналогично. | ✅ Публикация в поиск — под контролем модератора. | ✅ Прозрачно. |
| **Published → Draft (unpublish)** | **Варианты:** (1) только creator; (2) только ADMIN; (3) creator или ADMIN. | (1) Минимум ролей. (2) Только админ может «снять» с публикации. (3) Гибко: автор может снять сам, админ — при нарушении. | (1) Справедливо: автор решает снять. (2) Справедливо: только платформа снимает при нарушениях. (3) Баланс: автор и платформа. | Во всех вариантах правило явно и проверяемо on-chain. |

**Рекомендация:**  
- Draft→SentToReview: **только creator**.  
- SentToReview→Approved, Approved→Published: **только MODERATOR_ROLE** (или ADMIN_ROLE, если решено не вводить MODERATOR_ROLE).  
- Published→Draft: **creator или ADMIN** — чтобы автор мог снять активность сам, а платформа — при модераторском решении.

## 4. Строгость state machine (допустимые переходы)

**Вопрос:** Разрешать ли только явно заданные переходы статусов или допускать «форсирование» (например, админом)?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. Строгая state machine** | Допустимы только: Draft→SentToReview, SentToReview→Approved, Approved→Published, Published→Draft. Любой другой переход — revert. | ✅ Одна проверка по таблице переходов; предсказуемый газ. | ✅ Все действуют по одним правилам; нет «прыжков» через ревью. | ✅ Правила переходов явно зашиты в контракт и документируемы. |
| **B. Строгая + экстренный обход для ADMIN** | Как A, но ADMIN_ROLE может перевести любую активность в любой статус (например, сброс в Draft при нарушении). | ✅ Редкий путь; в обычных сценариях — строгая машина. | ⚠️ Справедливо при чёткой политике использования «только в экстренных случаях». | ✅ Лучше явно описать в доке/натами: «ADMIN может форсировать только в случаях X». |
| **C. Свободная смена (любой разрешённый по роли)** | Любой переход, если у вызывающего есть право на данный статус (например, модератор может ставить любой статус). | ⚠️ Гибко, но сложнее валидация и тесты. | ⚠️ Выше риск ошибок и злоупотреблений (например, перевод обратно в Draft без явного unpublish). | ⚠️ Правила менее очевидны. |

**Рекомендация:** **A** (строгая state machine). При необходимости экстренных действий — отдельно обсудить **B** и зафиксировать политику использования ADMIN.

## 5. Поле `active`: хранить отдельно или выводить из статуса

**Вопрос:** В структуре Activity есть и `status` (enum), и `active` (bool). Нужны ли оба?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. active и status независимы** | `active` — отдельный флаг (например, «участие в каталоге/поиске»); можно снять с публикации без смены статуса. | ⚠️ Два поля для сходной семантики; больше логики и тестов. | Зависит от продуктовой трактовки. | Два понятия — нужно чётко документировать разницу. |
| **B. active = (status == Published)** | Не хранить `active`; «активность в поиске» выводить как `status == Published`. | ✅ Меньше состояния, проще инварианты и газ. | ✅ Один источник истины: в поиске только Published. | ✅ Одна явная семантика: опубликовано = доступно. |
| **C. Только active, без enum status** | Один флаг active; жизненный цикл вести off-chain или в другом поле. | ❌ Теряется явный lifecycle и валидация переходов on-chain. | ❌ Сложнее гарантировать честный процесс ревью. | ❌ Менее прозрачно. |

**Рекомендация:** **B** — не дублировать; считать «активность в поиске» по `status == Published`. Если в Epic жёстко зафиксирован отдельный `active`, оставить его для совместимости с ABI, но синхронизировать с Published (например, при переходе в Published выставлять active = true, при Unpublish — false).

## 6. Источник ролей создателя: одна роль для Products и Activities или раздельные

**Вопрос:** Создатель активности = тот же пул, что и продавец (SELLER_ROLE), или отдельная роль (ACTIVITY_CREATOR_ROLE)?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. Та же SELLER_ROLE** | В ActivityRegistry проверять `spiralEngine.hasRole(SELLER_ROLE, msg.sender)` и активацию. | ✅ Нет изменений в SpiralEngine; переиспользование роли. | ✅ Единый порог входа: кто может продавать, тот может создавать активности (логично для единой платформы). | ✅ Одна роль «создатель контента» в экосистеме. |
| **B. Новая ACTIVITY_CREATOR_ROLE в SpiralEngine** | Ввести в SpiralEngine роль ACTIVITY_CREATOR_ROLE; выдавать отдельно от SELLER_ROLE. | ⚠️ Нужны доработки SpiralEngine и сценарии выдачи роли. | ✅ Можно разделить: продавцы ≠ создатели активностей (если продукт так задуман). | ✅ Явно: «создатель активностей» — отдельная роль. |

**Рекомендация:** **A** (SELLER_ROLE), если продукт не требует разделения «только продавцы» и «только создатели активностей». Иначе — **B** с явным введением ACTIVITY_CREATOR_ROLE в SpiralEngine.

## 7. Интеграция с SpiralEngine: обязательная зависимость или опциональная

**Вопрос:** Контракт ActivityRegistry всегда требует установленный SpiralEngine или может работать без него (например, только с локальными ролями)?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. SpiralEngine обязателен** | `initialize(admin, _spiralEngine)`; createActivity только при `address(spiralEngine) != address(0)` и проверке через SpiralEngine. | ✅ Единая точка правды; консистентность с ProductRegistry. | ✅ Все создатели проходят один и тот же порог (активация + роль). | ✅ Зависимость и критерий доступа явно заданы. |
| **B. SpiralEngine опционален** | Если SpiralEngine не установлен — fallback на локальную CREATOR_ROLE. | ⚠️ Две ветки логики, тесты и сценарии. | ⚠️ Разные правила «с SpiralEngine» и «без» — риск неравных условий. | ⚠️ Сложнее объяснить, когда какой режим. |

**Рекомендация:** **A** — SpiralEngine обязателен для createActivity (как в ProductRegistry). Упрощает контракт и выравнивает условия для всех.

## 8. События: кто инициировал смену статуса (для аудита)

**Вопрос:** В событии ActivityStatusUpdated достаточно ли (oldStatus, newStatus) или нужно явно передать инициатора?

| Вариант | Описание | Эффективность | Честность / справедливость | Прозрачность |
|--------|----------|----------------|----------------------------|--------------|
| **A. Без инициатора** | `ActivityStatusUpdated(activityId, oldStatus, newStatus)`. | ✅ Меньше данных в логе. | ⚠️ Нельзя on-chain доказать, кто сменил статус. | ⚠️ Аудит только по tx.origin/msg.sender в самой транзакции. |
| **B. С инициатором** | `ActivityStatusUpdated(activityId, oldStatus, newStatus, msg.sender)`. | ✅ Один indexed address — приемлемый газ. | ✅ Явная ответственность: кто перевёл статус. | ✅ В логах видно, кто инициировал переход. |

**Рекомендация:** **B** — включать в событие адрес инициатора (или роль), чтобы усилить честность и прозрачность модерации и unpublish.

## 9. Система ролей (актуальная — после принятых решений)

**Актуальная схема** без модерации on-chain и без многостатусного lifecycle:

| Роль | Где хранится | Действия в ActivityRegistry |
|------|--------------|-----------------------------|
| **Создатель активности** | SpiralEngine: **ACTIVITY_CREATOR_ROLE** + активация (usedInviteByUser != 0) | createActivity, activateActivity, deactivateActivity (свои) |
| **Админ** | ActivityRegistry: ADMIN_ROLE, DEFAULT_ADMIN_ROLE | pause/unpause, setSpiralEngine; при необходимости forceDeactivate(activityId) |
| **Апгрейдер** | ActivityRegistry: UPGRADER_ROLE | upgradeToAndCall |

Модератор **не вводится**. Контроль качества — в UI (GPT инструкции); доступ к API — только авторизованные приложения (secret key / app auth). Полная картина: **roles-architecture-synthesis.md**.
