# Ретроспектива процесса: как мы отработали фазу 3

**Дата:** 2026-01-29  
**Объект:** не «что сделано» (это в phase3-retrospective-activity-registry.md), а **как мы работали** — подход, структура, коммуникация, сбои, уроки.

---

## 1. Исходный запрос и выбор способа работы

**Запрос:** выполнить каждый TODO item методом @runitem.md (run-task) с подробным логированием каждого шага алгоритма в диалоге.

**Что сделали:**
- Вынесли все 5 шагов фазы 3 из solution-architecture в TODO list (phase3-1 … phase3-5).
- Для каждого пункта пытались пройти 7 фаз run-task: Understanding → Knowledge Check → Acceptance Criteria → Planning → Implementation → Validation → Retrospective.
- Логирование «в диалоге» — текстовые блоки в одном длинном ответе: по каждому TODO описание фаз 1–7 и результат.

**Итог:** Структура run-task задала порядок (сначала понять, потом критерии, потом план, потом код, потом проверка). Это уменьшило риск пропустить проверку или критерии.

## 2. Что сработало хорошо

**Чёткий план из документа.** План фазы 3 (3.1–3.5) был однозначным; не пришлось додумывать шаги — только выполнять и сверять.

**TODO как чеклист.** Разложение фазы 3 в 5 TODO дало явный список «что осталось» и позволило отмечать завершённое (phase3-1 … phase3-5 completed). Оператор мог видеть прогресс по пунктам.

**Проверка после каждого изменения.** После 3.1 — компиляция; после 3.2 — компиляция; после 3.3 — запуск тестов (35 passing); после 3.4 — 36 тестов; после 3.5 — 37 тестов. Короткие циклы «сделал → проверил» снизили риск накопления скрытых ошибок.

**Использование существующих образцов.** Logic по образцу других UUPS (ProductRegistryLogic, SpiralEngineLogic); Proxy — копия структуры ProductRegistryProxy. Меньше изобретения велосипедов, меньше расхождений со стилем проекта.

**Ретроспектива по продукту (phase3-retrospective).** Отдельный документ «что задано / что сделано / расхождения» дал явную сверку с планом и основу для следующей ретроспективы — процесса.

## 3. Что сработало плохо или создало риски

**Один длинный ответ на все 5 пунктов.** Все 5 TODO были выполнены в одной сессии, в одном развёрнутом ответе. Логи по 3.1, 3.2, 3.3, 3.4, 3.5 шли подряд. В интерфейсе (или из-за ограничения длины) оператор видел в логах только «phase3.2 и дальше ничего» — создалось впечатление остановки или ложного успеха, хотя 3.3–3.5 были сделаны и проверены.

**Нет явных контрольных точек в логе.** Не было коротких маркеров вида «[3.3 DONE]», «[3.4 DONE]», которые остались бы видимы даже при обрезке. При обрезке ответа терялась уверенность, что 3.3–3.5 действительно выполнены.

**Опциональный 3.5 реализован без явного согласования.** В плане 3.5 помечен как «при необходимости». Решение «реализовать forceDeactivate и тест» было принято в ходе выполнения, без отдельного вопроса оператору. По содержанию это улучшило контракт, но по процессу — небольшой выход за рамки «строго по плану».

**Run-task по сути сжат.** Фазы 2 (Knowledge Check) и 3 (Acceptance Criteria) часто описывались одной строкой; детальные критерии приёмки не всегда выносились в отдельный список (например, в YAML). Это допустимо для маленьких шагов, но для более крупных пунктов явные acceptance criteria в начале уменьшили бы риск недоделок.

## 4. Как мы отреагировали на сбой видимости

**Запрос оператора:** «я вижу в логах phase3.2 и дальше ничего — остановка? ложный успех?»

**Действия:**  
- Уточнили, что имеется в виду (терминал vs TODO vs обрезка ответа).  
- Проверили код и тесты: наличие UUPS, Proxy, тестов на upgradeToAndCall, Full State Preservation, forceDeactivate; запустили все 37 тестов — проходят.  
- Ответили кратко: не остановка и не ложный успех; 3.3–3.5 сделаны в той же сессии; обрезка/длина ответа привели к тому, что в логах видна только часть.

**Итог:** Проблема была не в выполнении, а в **коммуникации и видимости прогресса**. Проверка по коду и тестам сняла сомнения; для будущего нужны форматы, которые остаются читаемыми при обрезке.

## 5. Уроки для следующих фаз

**Короткие итоги в начале или в конце.** При выполнении нескольких пунктов подряд в одном ответе — в самом начале или в конце давать краткий чеклист: «3.1 ✓, 3.2 ✓, 3.3 ✓, 3.4 ✓, 3.5 ✓» и одну строку проверки («37 тестов, compile OK»). Тогда при обрезке середины остаётся видно, что фаза завершена полностью.

**Явные маркеры завершения пунктов.** После каждого пункта добавлять одну строку вида `[Phase 3.X DONE]` или `--- 3.X OK ---`, чтобы при прокрутке лога можно было быстро увидеть, до какого пункта выполнение дошло.

**По одному пункту за ответ (при желании максимальной прозрачности).** Альтернатива: выполнять 3.1 → ответ с логом и «3.1 готов, переходим к 3.2» → 3.2 → ответ … Тогда не будет одного огромного блока и обрезка не скроет факт выполнения. Минус — больше сообщений в диалоге.

**Опциональные пункты — явное решение.** Для пунктов «при необходимости» / «опционально» в начале шага кратко фиксировать: «реализуем» или «пропускаем, причина». Тогда в ретроспективе процесса не будет неопределённости, было ли решение согласовано.

**Ретроспектива процесса отдельно от ретроспективы продукта.** Как и сделано: phase3-retrospective = что сделано по плану; phase3-process-retrospective = как работали, что улучшить. Так проще возвращаться к процессу при следующих фазах (4, 5, …) без смешивания с содержанием задач.
