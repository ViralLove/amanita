## DP1. Сигнатура batch: массив expiries vs один expiry на весь batch

| Вариант | Описание | Плюсы | Минусы |
|--------|----------|--------|--------|
| **A** | `mintInviteBatch(string[] calldata inviteCodes, uint256[] calldata expiries)` — длина массивов совпадает | Гибкость: у каждого инвайта свой expiry | Длиннее calldata, скрипт должен собирать массив expiries (сейчас везде 0) |
| **B** | `mintInviteBatch(string[] calldata inviteCodes, uint256 expiry)` — один expiry на все | Проще вызов из scripts (всегда 0), меньше calldata | Нет разного expiry в одной batch |

**Рекомендация:** **A** — по AC и постановке уже указаны массивы `inviteCodes` и `expiries`; обратная совместимость с одиночным `mintInvite` по семантике; в Action 777 можно передать `expiries = [0,0,...,0]`.

## DP2. MAX_BATCH_SIZE — значение верхней границы

| Вариант | Значение | Обоснование |
|--------|----------|-------------|
| **A** | 12 | Ровно под текущий Action 777 (12 инвайтов) |
| **B** | 50 | Запас под будущее; укладывается в лимит газа (постановка п.7) |
| **C** | 100 или без жёсткого лимита | Максимальная гибкость, риск по газу |

**Рекомендация:** **B (50)** — покрывает 12 и даёт запас; явный лимит защищает от слишком больших batch и переполнения газа.

## DP3. Вынести логику одного инвайта в _mintInviteSingle или дублировать в цикле

| Вариант | Описание | Плюсы | Минусы |
|--------|----------|--------|--------|
| **A** | Ввести внутреннюю `_mintInviteSingle(inviteCode, expiry) returns (uint256 tokenId)`; `mintInvite` и цикл в `mintInviteBatch` вызывают её | Один источник истины, проще поддерживать | Доп. вызов внутри контракта (небольшой overhead по газу) |
| **B** | В цикле `mintInviteBatch` продублировать логику из `mintInvite` (inline) | Нет лишнего internal call | Дублирование кода, при изменении mintInvite нужно менять и batch |

**Рекомендация:** **A** — постановка п.2 плана: «при необходимости вынести общую часть»; меньше риска рассинхрона и багов при правках.

**Итог (для согласования):** [ ] A  [ ] B
