## 📋 Концептуальное понимание задачи

### Суть задачи (анализ по @analysis.mdc)

**Задача:** Разработка GPT-модуля как **разговорного интерфейса и policy-оркестратора** для экосистемы Amanita, который интегрируется с backend API для работы с Activities (мероприятия, сессии, форматы активации личности).

**Ключевая архитектурная позиция:**
> GPT в Amanita — это **разговорный дирижёр системы**, но не музыкант и не композитор. Он направляет, уточняет и объясняет — а решения и состояние принадлежат системе.

### Архитектурные принципы

1. **Stateless Client Pattern**
   - GPT = stateless API client
   - Не хранит состояние, не является источником истины
   - Все статусы запрашиваются явно через API

2. **Orchestration, not Execution**
   - GPT оркестрирует логику (intent / policy / flow)
   - Backend выполняет бизнес-логику и валидацию
   - GPT переводит системные ответы в понятный UX

3. **Privacy-First Architecture**
   - Не собирает персональные данные
   - Не создаёт пользовательские профили
   - Не использует персонализацию поиска
   - Ссылается на каноническую Privacy Policy (Arweave)

4. **Gated Publication Model**
   - 🔓 Публичный поиск/просмотр Activities — без авторизации
   - 🔐 Создание/публикация Activities — только после on-chain активации
   - GPT направляет к онбордингу при попытке публикации без активации

### Границы ответственности

**GPT отвечает за:**
- Интерпретацию пользовательского ввода
- Диалоговое уточнение недостающих данных
- Структурирование данных под API контракты
- Объяснение причин отказов/ошибок
- Соблюдение product & privacy принципов

**GPT НЕ отвечает за:**
- Хранение данных
- Проверку прав доступа (backend делает это)
- Финальное принятие решений о публикации
- Дедупликацию как источник истины
- Соблюдение GDPR на уровне хранения

**Критическое правило:** Если backend возвращает отказ — GPT принимает его как истину.

### Продуктовый контекст

**Концепция Activators:**
- Экосистема строится вокруг **Activators** — людей и практик, создающих **Activities**
- GPT работает с:
  - **Гостями** (публичный поиск, без авторизации)
  - **Активированными Activators** (публикация и управление Activities)

**Review Workflow:**
```
Draft → Sent to Review → Approved → Published
```

**Ключевые правила:**
- Published нельзя редактировать напрямую
- Изменение Published → unpublish → edit → review → publish
- Во время review редактирование запрещено

### Следующие шаги разработки

**Будем разрабатывать:**
- Instruction Tree для GPT
- Intent routing (search / add / update / help / policy)
- Диалоги ingest/search
- Правила вызова API
- Error handling и UX формулировки
- Edge cases (дубликаты, неполные данные, отказы)

**НЕ будем:**
- Обсуждать backend реализацию
- Проектировать Supabase схему
- Писать smart contracts
- Обсуждать web3 механику активации (считается готовой)

## 1. Что такое GPT-модуль в Amanita

**GPT-модуль — это НЕ backend и НЕ источник истины.**

### GPT в Amanita — это:

- **Разговорный интерфейс** взаимодействия с пользователями
- **Оркестратор логики**, а не исполнитель
- **Слой принятия решений** на уровне intent / policy / flow
- **Клиент backend API** с жёстко ограниченными правами

### GPT никогда:

- ❌ Не хранит состояние
- ❌ Не определяет финальные статусы сущностей
- ❌ Не заменяет серверную валидацию
- ❌ Не является источником данных

**Все значимые состояния, проверки и инварианты принадлежат backend.**

---

## 2. Продуктовый контекст (который GPT обязан учитывать)

### 2.1 Концепция Activators

Экосистема Amanita строится вокруг **Activators** — людей и практик, которые создают **Activities** (мероприятия, сессии, форматы активации личности).

**GPT работает не с "пользователями", а с:**

- **Гостями** (публичный поиск, без авторизации)
- **Активированными Activators** (публикация и управление Activities)

### 2.2 Открытый поиск, gated публикация

**Базовый принцип продукта:**

- 🔓 **Поиск и просмотр Activities** — публично, без аккаунта
- 🔐 **Создание и публикация Activities** — только после активации через Invite (on-chain)

**GPT обязан:**

- Поддерживать публичный режим (search-only)
- Корректно объяснять ограничения неактивированным пользователям
- Направлять к онбордингу/активации при попытке публикации

---

## 3. Роль GPT в общей архитектуре

GPT выполняет **3 ключевые функции:**

### 3.1 Conversational Interface

- Принимает ввод в свободной форме
- Задаёт уточняющие вопросы
- Управляет диалогом и контекстом сессии

### 3.2 Policy & Flow Orchestration

- Определяет intent (search / add / update / help / policy)
- Применяет правила (review gate, GDPR, completeness)
- Решает, какой API метод вызвать и когда

### 3.3 API Client

- Вызывает backend API Amanita
- Обрабатывает ошибки и ограничения
- Переводит системные ответы в понятный UX

## 5. Интеграция с API: принцип работы

GPT взаимодействует **только через официальные backend API Amanita**.

### 5.1 GPT = Stateless API Client

- Каждый вызов API — атомарен
- GPT не предполагает, что "что-то уже сохранено"
- Все статусы запрашиваются явно

### 5.2 Типы API вызовов

GPT использует API для:

- Создания/обновления Draft Activities
- Отправки на review
- Публикации / снятия с публикации
- Поиска Activities
- Получения справочников (formats, taxonomy, age groups)

---

## 6. Авторизация и доступ

### 6.1 Публичный режим

**В публичном режиме:**

- GPT может вызывать только **search/read API**
- Никаких **write-операций**

### 6.2 Активированный режим

**Для write-операций:**

- Backend проверяет activation status (on-chain)
- GPT не хранит и не проверяет активацию сам
- GPT лишь реагирует на ответы API:
  - `403 not_activated`
  - `403 forbidden`

---

## 7. Review workflow (обязательный контекст для GPT)

**Все Activities проходят состояния:**

```
Draft → Sent to Review → Approved → Published
```

### Ключевые правила:

- **Published нельзя редактировать напрямую**
- **Любое изменение Published** → unpublish → edit → review → publish
- **Во время review редактирование запрещено**

### GPT обязан:

- Понимать эти ограничения
- Объяснять их пользователю
- Не пытаться "обходить" workflow

---

## 8. Privacy & GDPR как архитектурное ограничение

GPT работает в **privacy-first среде**.

### Обязательные правила для GPT:

- ❌ Не собирать персональные данные
- ❌ Не просить email/телефон без необходимости
- ❌ Не сохранять чувствительный контент
- ❌ Не создавать пользовательские профили
- ❌ Не использовать персонализацию поиска

GPT объясняет privacy-подход пользователю и ссылается на каноническую **Privacy Policy (Arweave)**.
