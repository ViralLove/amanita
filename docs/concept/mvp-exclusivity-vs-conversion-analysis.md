# MVP: Дилемма эксклюзивности vs конверсии — анализ и решения

**Версия:** 1.0  
**Дата создания:** 2026-01-13  
**Контекст:** MVP запуск первой ноды на mainnet Polygon  
**Методология:** @analysis.mdc, @Zeya888-Meta

---

## 🎯 Контекст и проблема

### Текущая ситуация MVP

**Готовность к запуску:**
- ✅ Каталог экспортирован и выложен
- ✅ Контракты готовы к деплою в mainnet Polygon (процесс известен, подводных камней нет)
- ✅ Базовая инфраструктура работает

**Ограничения MVP фазы:**
- ❌ Нет автоматической синхронизации заказов
- ❌ Нет блокчейн-слоя для отслеживания заказов
- ⚠️ Amanita wallet (webapp) — базовая реализация, недостаточная секьюрность
- 📋 Работа в ручном режиме для нескольких seller nodes

**Цель MVP:**
Engage покупателей на магазинах для создания адресов (кошельков) под будущие loyalty токены и накопление покупательской репутации.

---

## ⚖️ Дилемма

### Проблема: два противоречащих требования

#### 1️⃣ Эксклюзивность и чистота доступа (SpiralEngine логика)

**Архитектурные принципы:**
- **12 инвайтов на активированного пользователя** (hard limit в контракте)
- **Invite-only модель** — доступ только через инвайт-код
- **Контроль качества** через социальные связи (organic trust communities)
- **Ответственность активатора** за поведение приглашённого пользователя
- **Ценность инвайта** = привилегия, не entitlement

**Экономическая логика:**
- Ограниченность инвайтов создаёт ценность
- Качество > количества
- Селективное привлечение ценных пользователей
- Финансовая ответственность каждого участника

**Техническая реализация:**
```solidity
// SpiralEngine.sol
mapping(address => address[]) public activatedBy;  // max 12
function activateUser(...) public onlyRole(ACTIVATOR_ROLE) {
    require(activatedBy[msg.sender].length < 12, "Circle limit reached");
    require(newInviteCodes.length == 12, "Must provide exactly 12 invite codes");
}
```

---

#### 2️⃣ Повышение конверсии для селлеров

**Бизнес-потребность:**
- Селлеры хотят больше покупателей
- Нужно мотивировать инвайтить своих клиентов
- Каждый инвайт — это потенциальный покупатель
- В MVP фазе критично быстро набрать базу адресов

**Проблема ограничений:**
- 12 инвайтов = максимум 12 прямых приглашений
- Ограничение может создать барьер для конверсии
- Селлеры могут быть не готовы "тратить" инвайты на непроверенных клиентов
- Риск "замораживания" инвайтов из-за страха ошибиться

**Мотивация селлеров:**
- Видимость прогресса (сколько инвайтов использовано)
- Метрики эффективности инвайтов (конверсия, покупки)
- Связь между инвайтингом и доходами

## 🔍 Анализ возможных решений

### Решение 1: Временная программа "MVP Boost" (рекомендуемое)

**Концепция:**
Временное ослабление ограничений для MVP фазы с постепенным возвратом к полной эксклюзивности.

**Механизм:**
- **MVP Window:** Первые N месяцев после деплоя
- **Temporary Invite Pool:** Дополнительный пул инвайтов для селлеров (например, +24 инвайта сверх 12 базовых)
- **Постепенное затухание:** После MVP window дополнительные инвайты прекращают генерироваться
- **Маркировка:** Инвайты MVP периода помечаются флагом `isMVPInvite = true`

**Техническая реализация:**
```solidity
// Добавить в SpiralEngine
uint256 public mvpWindowEndTimestamp;
mapping(address => uint256) public mvpInvitePool;  // дополнительные инвайты
mapping(uint256 => bool) public isMVPInvite;

function mintMVPInvite(string memory inviteCode, uint256 expiry) 
    public onlyRole(SELLER_ROLE) returns (uint256) 
{
    require(block.timestamp <= mvpWindowEndTimestamp, "MVP window ended");
    require(mvpInvitePool[msg.sender] > 0, "No MVP invites left");
    
    uint256 tokenId = mintInvite(inviteCode, expiry);
    isMVPInvite[tokenId] = true;
    mvpInvitePool[msg.sender]--;
    
    return tokenId;
}
```

**Преимущества:**
- ✅ Сохраняет архитектурную чистоту в долгосрочной перспективе
- ✅ Даёт селлером свободу для экспериментов в MVP
- ✅ Автоматически возвращает систему к эксклюзивности
- ✅ Позволяет собрать данные для анализа эффективности

**Недостатки:**
- ⚠️ Требует изменений в контракте
- ⚠️ Нужно определить критерии завершения MVP window
- ⚠️ Селлеры могут ожидать продолжения программы

**Применимость для MVP:** ⭐⭐⭐⭐⭐ (высокая)

### Решение 2: Слоистая модель инвайтов (Tiered Invite System)

**Концепция:**
Разделение инвайтов на "уровни" с разными правами и ограничениями.

**Механизм:**
- **Tier 1 (Exclusive):** Полные права, социальная капитализация, возможность стать селлером (12 инвайтов)
- **Tier 2 (Standard):** Базовый доступ, покупки, просмотр каталога, но ограниченная токеномика (неограниченно для селлеров)
- **Tier 3 (Guest):** Только просмотр, создание адреса, без токенов (автоматический доступ через магазин)

**Техническая реализация:**
```solidity
enum InviteTier { Exclusive, Standard, Guest }

mapping(address => InviteTier) public userTier;
mapping(uint256 => InviteTier) public inviteTier;

function activateUserTier2(...) public onlyRole(SELLER_ROLE) {
    // Стандартная активация без лимита на количество
    userTier[user] = InviteTier.Standard;
}

function activateUserTier3(address user) public onlyRole(SELLER_ROLE) {
    // Гостевая активация для создания адреса
    userTier[user] = InviteTier.Guest;
    usedInviteByUser[user] = type(uint256).max;  // маркер guest
}
```

**Преимущества:**
- ✅ Сохраняет эксклюзивность Tier 1
- ✅ Даёт гибкость для разных сценариев использования
- ✅ Позволяет постепенную миграцию пользователей между уровнями

**Недостатки:**
- ⚠️ Усложняет архитектуру и UX
- ⚠️ Может создать путаницу "кто есть кто"
- ⚠️ Требует переработки токеномики под разные уровни
- ⚠️ Риск "второсортных" пользователей

**Применимость для MVP:** ⭐⭐ (низкая — слишком сложно для старта)

### Решение 3: Программа "Invite Vouchers" (офф-чейн + он-чейн валидация)

**Концепция:**
Создание временных "ваучеров" для инвайтов, которые селлеры могут генерировать офф-чейн, но валидировать он-чейн.

**Механизм:**
- Селлер генерирует ваучер через бота (офф-чейн)
- Ваучер содержит временный код + адрес селлера + timestamp
- При активации ваучер проверяется на контракте (валидность селлера, срок действия)
- После валидации создаётся полноценный инвайт через SpiralEngine

**Техническая реализация:**
```solidity
struct InviteVoucher {
    address seller;
    bytes32 voucherHash;
    uint256 expiresAt;
    bool used;
}

mapping(bytes32 => InviteVoucher) public vouchers;

function validateVoucher(bytes32 voucherHash, string memory inviteCode) 
    public returns (uint256) 
{
    InviteVoucher memory voucher = vouchers[voucherHash];
    require(voucher.seller != address(0), "Invalid voucher");
    require(!voucher.used, "Voucher already used");
    require(block.timestamp <= voucher.expiresAt, "Voucher expired");
    
    vouchers[voucherHash].used = true;
    
    // Создаём полноценный инвайт
    return mintInvite(inviteCode, 0);
}
```

**Преимущества:**
- ✅ Минимальные изменения в контракте
- ✅ Гибкость для экспериментов
- ✅ Можно быстро отключить программу

**Недостатки:**
- ⚠️ Сложность в управлении (офф-чейн генерация)
- ⚠️ Риск злоупотреблений (нужна валидация селлера)
- ⚠️ Дополнительный слой абстракции

**Применимость для MVP:** ⭐⭐⭐ (средняя)

### Решение 4: "Soft Launch" модель (рекомендуемое для немедленного старта)

**Концепция:**
Фокус на качественных связях через существующую систему, но с усиленной поддержкой селлеров.

**Механизм:**
- Использовать существующую SpiralEngine логику БЕЗ изменений
- Создать инструменты для селлеров:
  - **Аналитика эффективности инвайтов:** Дашборд с метриками (конверсия, покупки, активность)
  - **Рекомендации по инвайтингу:** Когда и кому предлагать инвайты
  - **Templates для коммуникации:** Готовые сообщения для приглашения
  - **Gamification:** Прогресс-бары, достижения, видимость вклада

**Off-chain поддержка:**
- Ручная помощь селлерам в первых инвайтах
- Обучение лучшим практикам
- Мониторинг и обратная связь

**Преимущества:**
- ✅ Не требует изменений в контракте
- ✅ Сохраняет архитектурную чистоту
- ✅ Усиливает качество связей
- ✅ Можно реализовать немедленно

**Недостатки:**
- ⚠️ Не решает проблему ограничения в 12 инвайтов
- ⚠️ Требует ручной работы (но это и так MVP)
- ⚠️ Медленнее масштабируется

**Применимость для MVP:** ⭐⭐⭐⭐⭐ (высокая — можно начать сейчас)

### Решение 5: Гибридная модель "Fast Track + Full Access"

**Концепция:**
Разделение онбординга на два пути: быстрый (для MVP) и полноценный (для долгосрочных пользователей).

**Механизм:**
- **Fast Track:** Создание адреса без полной активации инвайта
  - Доступ к каталогу
  - Создание кошелька для будущих токенов
  - Ограниченная функциональность (нет токенов, нет инвайтов)
  - Возможность "апгрейда" до полноценного аккаунта через инвайт

- **Full Access:** Полная активация через SpiralEngine
  - Все права и токеномика
  - 12 инвайтов
  - Социальная капитализация

**Техническая реализация:**
```solidity
mapping(address => bool) public isFastTrackUser;
mapping(address => bool) public hasFullAccess;

function createFastTrackAddress(address user) public onlyRole(SELLER_ROLE) {
    isFastTrackUser[user] = true;
    // Просто маркируем адрес, без SpiralEngine активации
}

function upgradeToFullAccess(string memory inviteCode, ...) public {
    require(isFastTrackUser[msg.sender], "Not a fast track user");
    // Стандартная активация через SpiralEngine
    activateUser(inviteCode, msg.sender, newInviteCodes, expiry);
    hasFullAccess[msg.sender] = true;
    isFastTrackUser[msg.sender] = false;
}
```

**Преимущества:**
- ✅ Позволяет быстро набрать базу адресов
- ✅ Сохраняет эксклюзивность для полного доступа
- ✅ Создаёт воронку конверсии Fast Track → Full Access

**Недостатки:**
- ⚠️ Два типа пользователей (усложняет UX)
- ⚠️ Риск "застревания" на Fast Track
- ⚠️ Требует изменений в контракте и боте

**Применимость для MVP:** ⭐⭐⭐⭐ (высокая, но требует разработки)

## 📈 Метрики для отслеживания

### Ключевые показатели (KPIs)

**Для эксклюзивности:**
- Среднее количество использованных инвайтов на селлера
- Конверсия инвайтов (активации / выданные инвайты)
- Качество активаций (покупки, активность приглашённых)

**Для конверсии:**
- Общее количество активированных адресов
- Рост числа селлеров
- Время от инвайта до первой покупки
- Retention приглашённых пользователей

**Баланс:**
- Соотношение "exclusive" активаций vs "fast track"
- Эффективность разных типов инвайтов
- Удовлетворённость селлеров (опросы)
