## 1. Назначение и границы

Этот документ описывает **целевую модель безопасности ролей в SpiralEngine** для двух критических категорий участников:

- **Activators** — пользователи, которые растят сеть (активируют других) и создают активности (events/services).
- **Sellers** — участники, которые продают товары/услуги и получают экономическую выгоду.

Цель политики:

- Зафиксировать **жёсткие, прозрачные правила** эволюции прав:
  - от базового активированного пользователя → к надёжному активатору → к (потенциально) кандидату в продавцы.
- Обеспечить **высокий уровень безопасности** (защита от ботов и токсичного контента), не жертвуя **справедливостью и прозрачностью** для честных участников.
- Сформировать **концептуальную модель**, независимую от удобства текущей реализации; MVP будет вырезаться из этой модели отдельными тасками.

**В scope:**  
- Роли `ACTIVATOR_ROLE`, `SELLER_ROLE` в контексте SpiralEngine (роль создателя активностей концептуально приравнена к ACTIVATOR).  
- Отношения «кругов» (concentric circles) вокруг деплоера в invite/activation-дереве.  
- Концепция репутации и рекомендаций для выдачи SELLER.

**Вне scope (здесь только концептуально упомянуто):**  
- Конкретная реализация DAO/голосований.  
- UI/боты/интерфейсы и их UX.  
- Юридические аспекты за пределами общей архитектуры (они в `Contracts Security Architecture.md`).

## 2. Роли и базовые инварианты

Краткое напоминание (см. подробно `roles-architecture-synthesis.md`, раздел 2–3):

| Роль в SpiralEngine | Базовое назначение | Кто может получать (целевое видение) |
|---------------------|--------------------|--------------------------------------|
| `DEFAULT_ADMIN_ROLE` | Стартовый админ, рутовая конфигурация | Только при деплое |
| `ADMIN_ROLE`        | Управление критическими настройками, санкциями | Ограниченная группа доверенных лиц/DAO |
| `ACTIVATOR_ROLE`    | Активация новых пользователей, рост круга, создание и управление активностями (ActivityRegistry) | Каждый активированный пользователь (по умолчанию) |
| `SELLER_ROLE`       | Создание товаров/компонентов (ProductRegistry, OrganicComponentRegistry) | Только через **сложный, многоуровневый путь** валидации |

Общий инвариант:

- **Без инвайта** (`usedInviteByUser[user] == 0`) пользователь **не считается участником экосистемы** и не может:
  - быть активатором;
  - создавать активности;
  - быть продавцом.

## 3. Политика для Activators

### 3.1. Базовая модель

**Правило 1.** При успешной активации пользователя (`activateUser`) SpiralEngine:

- устанавливает `usedInviteByUser[user] != 0`;
- автоматически назначает пользователю `ACTIVATOR_ROLE`.

Тем самым **каждый активированный участник** становится:

- потенциальным **растителем круга** (может активировать следующих);
- потенциальным **создателем активностей** (events/services), т.к. ActivityRegistry трактует `ACTIVATOR_ROLE + usedInviteByUser != 0` как условие «activated activity creator».

Это соответствует таблице 2.2/3.2 в `roles-architecture-synthesis.md` и отражает ценности:

- **Справедливость:** доступ к созданию активности не является элитарной привилегией.
- **Прозрачность:** правило понятное и единое для всех.

### 3.2. Постепенный рост возможностей активатора

Чтобы избежать злоупотреблений и поддерживать **безопасность**, вводится модель **уровней активатора** (Activator Levels), основанная на метриках поведения:

#### Метрики для активаторов

- `activationsCount[user]` — сколько пользователей активировано этим активатором.
- `activationViolations[user]` — сколько нарушений зафиксировано по активированным им пользователям (SpiralEngine уже имеет каскадные санкции; эта метрика может строиться на их основе).
- `activitiesCreated[user]` — количество созданных активностей.
- `activitiesReported[user]` — количество активностей, помеченных как нарушающие кодекс (через механизмы репортов/модерации).
- `timeInSystem[user]` — время с момента активации (age).

#### Уровни

> Конкретные пороги — параметры, определяемые сообществом (можно хранить как on-chain константы/конфигurable параметры).

1. **Activator L0 (новичок)**:
   - Критерий: только что активирован (`activationsCount=0`, `timeInSystem` малый).
   - Права:
     - может создавать активности, но:
       - _опционально_ — лимит по количеству активных активностей (например, ≤ 3);
       - не имеет права рекомендовать SELLER’ов.

2. **Activator L1 (надежный активатор)**:
   - Критерии (примерные):
     - `activationsCount ≥ A1_min` (например, ≥ 5);
     - `activationViolations` в пределах допустимого уровня;
     - `activitiesReported / activitiesCreated` ниже порога.
   - Права:
     - повышенные лимиты на количество активностей;
     - _опционально_ — может рекомендовать новых активаторов/создателей в локальных контекстах;
     - по-прежнему **не** может напрямую выдавать SELLER_ROLE.

3. **Activator L2+ (старшие активаторы / community leaders)**:
   - Дополнительные критерии:
     - высокий стаж (`timeInSystem`);
     - хорошие репутационные метрики по своим кругам (низкий уровень нарушений).
   - Возможные доп. права:
     - участие в локальных DAO/советах, принимающих решения о санкциях;
     - больший вес голоса при голосовании за SELLER’ов (но не прямой grant).

**Замечание:**  
Модель уровней не обязывает честного человека стать L2 — **он может быть просто Creator и базовым Activator всю жизнь**. Уровни нужны для того, чтобы дать дополнительную ответственность/вес только тем, кто устойчиво показал честность и полезность.

### 3.3. Санкции и отзыв прав активатора

Санкции должны быть **каскадными и прозрачными**:

- Нарушения активированных пользователей увеличивают `activationViolations[activator]`.
- При достижении порогов:
  - **уровень активатора понижается** (L2 → L1 → L0);
  - могут быть введены лимиты:
    - на новые активации;
    - на создание новых активностей.
- В тяжёлых случаях:
  - `ACTIVATOR_ROLE` может быть отозвана (ADMIN/DAO по понятным процедурам);
  - вместе с этим можно временно/навсегда запретить участие в рекомендациях кого-либо (в будущем — в том числе SELLER’ов).

Все такие изменения должны:

- логироваться событиями (`ActivatorSanctioned`, `ActivatorLevelChanged`);
- быть видимыми любому внешнему наблюдателю (прозрачность).

## 4. Политика для Sellers (продавцов)

Здесь политика **существенно более строгая**, чем для активаторов.

### 4.1. Общие требования к продавцу

Продавец — это участник, который:

- выставляет товары/компоненты, в том числе потенциально чувствительные (медицина, психоактивные вещества и т.д.);
- участвует в экономике (принимает деньги).

Требования:

- **Жёсткий вход** (никакой автоматической выдачи SELLER_ROLE при активации).
- **Наблюдаемая история поведения** (reputation / violations).
- **Широкая рекомендательная подушка** — не один админ, а множество независимых акторов.

### 4.2. Пять челленджей на путь от активатора к селлеру

Политика для SELLER исходит из идеи **глубокой, поэтапной проверки** активатора, прежде чем он получит право продавать. Этот путь задаётся как последовательность **5 челленджей**.

#### Челлендж 1 — Путь провайдера через LoveDo (минимум 8 майнинговых сессий)

- Активатор должен проявить себя как **провайдер** в LoveDo-экономике:
  - минимум 8 независимых эпизодов, в которых он выступает как `sellerTo` в LoveDo-постах и получает суперлайки (через `LoveEmissionEngine.emitForSuperlike`);
  - LoveEmissionEngine уже накапливает для него `loveAccrued` и `lgovAccrued`, а `LOVE_DO_THRESHOLD` задаёт минимальную базовую репутацию.
- Это создаёт **первичный слой доверия**: сообщество уже “голосовало” за его услуги/контент лайками, и это зафиксировано on-chain.

#### Челлендж 2 — LGOV stake-кампания (само- и внешняя поддержка)

- После того как минимальная LoveDo-история выполнена, активатор объявляет себя **кандидатом в SELLER**.
- Он и другие участники запускают **stake-кампанию LGOV**:
  - кандидат может застейкать **ограниченную долю своих LGOV** за себя (ограничение предотвращает полностью “самосделанных” селлеров);
  - другие активаторы/селлеры стейкают LGOV, сигнализируя готовность “подписаться” под его поведением.
- Стейк LGOV в этом контексте — залог, который:
  - блокируется на время дальнейших челленджей и probation-периода;
  - в случае тяжёлых нарушений кандидата может быть частично/полностью потерян.

#### Челлендж 3 — Доказательство, что он производитель, а не реселлер

- Цель — отличить **реального производителя** от реселлера.
- Вводится набор тематических LoveDo-челленджей:
  - серии постов о процессе производства/создания услуги (мастерская, кухня, студия, код-репозиторий и т.п.);
  - кросс-подтверждения от других пользователей через LoveDo-посты (mentions) о том, что они получили продукт/услугу **напрямую** от кандидата.
- Эти сигналы:
  - не заменяют живую проверку людей, но создают **прозрачный ончейн-трейл**:
    - какой именно продукт/услуга ассоциируется с кандидатом;
    - как долго и в каком качестве он его предоставляет;
    - кто из реальных людей (активаторов) это подтверждает.

#### Челлендж 4 — Концентрические круги и рекомендательный индекс 8 (связь с Anti-Sybil Policy)

- Архитектура SpiralEngine задаёт **дерево активаций**; для каждого пользователя определяется:
  - `distanceFromRoot` — число шагов по пути активаций от корневого аккаунта (деплоер/первый admin);  
    это и есть **удалённость от центра**.
- На основе этой дистанции формируется **circle index** и **вес круга**:
  - круг 0: центр (деплоер / корневой admin);
  - круг 1: непосредственные активированные;
  - круг 2: их активированные и т.д.
- Вводится **коэффициент межкругового снижения веса** `circleDecay`:
  - `0 < circleDecay < 1`, одинаковый для всех переходов между кругами;
  - `circleWeight[0] = 1` (или зафиксированное базовое значение);
  - для `k ≥ 1`:  
    \\( circleWeight[k] = circleWeight[k-1] \cdot circleDecay \\).
- Этот `circleDecay` — один из **ключевых параметров политики**, определяемый:
  - сначала деплоером и ближайшим окружением (круга 1–2) через голосование LGOV;
  - затем — DAO/сообществом.

Рекомендательный индекс для кандидата в SELLER строится на основе:

- stake `LGOV` рекомендателей;
- `circleWeight` (удалённость от центра);
- репутационных коэффициентов (`repWeight`).

Формально, для рекомендателя `r` (см. также формулы в `docs/tech/Anti Sybil Policy.md`):

\\[
W_r = stake[r] \cdot repWeight[r] \cdot circleWeight[\mathrm{distanceFromRoot}(r)]
\\]

Итоговый индекс кандидата:

\\[
I(C) = \sum_{r} W_r
\\]

Целевой порог безопасности `T` выбирается так, чтобы:

- **минимальный сценарий:** 8 “полновесных” рекомендаций от первых кругов (distance 1–2, circleWeight ≈ 1, высокий `repWeight`) дают `I(C) \approx 8`;
- по мере роста `distanceFromRoot` (уменьшения `circleWeight`) и/или ослабления репутации рекомендателей, для достижения `I(C) \ge 8` потребуется:
  - либо больше стейка `LGOV`;
  - либо большее количество независимых рекомендателей.

Таким образом:

- метрика “минимальный индекс 8” сохраняет интуицию “8 голосов близких доверенных селлеров”;
- но даёт **контролируемый рост**: дальние круги могут накапливать индекс за счёт количества и собственного LGOV, но это сложно и прозрачно.

#### Челлендж 5 — Испытательный срок и слэш ответственности

- После успешного прохождения предыдущих этапов кандидат получает SELLER_ROLE с пометкой “на испытательном сроке”.
- На протяжении probation-периода:
  - его поведение отслеживается через ProductRegistry, LoveEmissionEngine и систему санкций;
  - stake LGOV рекомендателей остаётся заблокированным.
- По итогам:
  - при устойчиво честном поведении:
    - статус SELLER становится “постоянным”;
    - stake LGOV размораживается (возможно, по частям).
  - при тяжёлых нарушениях:
    - SELLER_ROLE отзывается;
    - stake LGOV частично или полностью слэшится (по заранее зафиксированным правилам);
    - репутационный вес рекомендателей в будущих голосованиях уменьшается.

Эта 5-ступенчатая лестница объединяет:

- **геймификацию** (челленджи и LoveDo-путь),
- **социальную проверку** (кросс-подтверждения и доверие кругов),
- и **жёсткую экономическую ответственность** через stake и slashing LGOV.

### 4.3. Дополнительные условия для кандидата

Помимо индекса рекомендаций, кандидат должен:

- Иметь достаточную **личную репутацию**:
  - история честной активности (как ACTIVITY_CREATOR);
  - отсутствующие / редкие санкции;
  - возможно, минимальный срок нахождения в системе (`timeInSystem ≥ MinSellerAge`).
- Не находиться под текущими **санкциями** (suspension, severe violations).

Выдача SELLER_ROLE должна:

- фиксироваться отдельным событием `SellerRoleGranted` (уже есть в системе);
- содержать информацию о:
  - суммарном индексе `I(C)`;
  - количестве рекомендаций и, возможно, хэше списка рекомендателей (для аудита, без нарушения приватности, если она важна).

### 4.5. Санкции и отзыв SELLER_ROLE

Чтобы соблюсти **безопасность**:

- Для каждого SELLER отслеживать:
  - `sellerViolations` — нарушения продавца (качество товаров/услуг, нарушения правил);
  - `recommendationQuality` — качество рекомендованных им селлеров (если они были забанены/санкционированы, это ударяет по рекомендателю).

При достижении порогов:

- SELLER_ROLE может быть:
  - временно приостановлена (suspended);
  - окончательно отозвана (revoked) по процедурам DAO/ADMIN (в зависимости от уровня децентрализации).

Важно:

- Отзывы SELLER’ов и санкции по рекомендациям должны **уменьшать их рекомендационный вес W_r**, чтобы они не могли бесконечно продвигать “плохих акторов” без последствий.

## 5. Governance и параметризация

Все ключевые коэффициенты и пороги должны рассматриваться как **параметры политики**, а не жёстко захардкоженные константы навсегда:

- `decay` для кругов (0.1, 0.05 и т.д.).
- Минимальный индекс безопасности для SELLER: `T` (например, 8.0).
- Пороги для уровней активаторов и селлеров (`S_min`, допустимые `violationScore`, `MinSellerAge`).

**Рекомендация по governance:**

- На первом этапе — параметры задаются через архитектурные документы и код (константы, переменные окружения/конфига).
- В дальнейшем — могут управляться:
  - on-chain конфиг-контрактом, где голос LGOV-токенов определяет изменения ключевых параметров (включая `circleDecay` и порог `T`);
  - версионируемыми “policy-docs”, на которые явно ссылаются UI/клиенты.

Важно сохранить:

- **Прозрачность:** любые изменения параметров сопровождаются:
  - on-chain событиями;
  - обновлением публичных доков.
- **Справедливость:** изменения не должны задним числом резко ухудшать положение честных участников.
- **Безопасность:** в спорных кейсах приоритет отдаётся защите пользователей (покупателей) и уязвимых групп.

## 6. Связь с текущим кодом и задачами

Эта политика задаёт **целевое состояние**. Конкретные шаги реализации будут оформляться отдельными тасками:

- Для **SpiralEngineLogic**:
  - автоматическая выдача `ACTIVATOR_ROLE` и `ACTIVITY_CREATOR_ROLE` в `activateUser`;
  - админский `grantActivityCreatorRole` + событие;
  - расширение логики SELLER (рекомендации, индексы) — отдельный набор тасков.

- Для **регистров** (ProductRegistry, OrganicComponentRegistry, ActivityRegistry):
  - привязка к ролям и метрикам, описанным здесь;
  - добавление статусов, репутации и санкций.

- Для **scripts** (`deploy_full`, ActionsManager):
  - ввод DEPLOY_ACTION’ов, учитывающих политику (например, подготовка активного ACTIVITY_CREATOR_ADDRESS, дальнейшие шаги для кандидатов в SELLER).

MVP может реализовать **подмножество** этой политики (например, авто-выдачу ACTIVITY_CREATOR_ROLE и базовый путь SELLER через админа), но этот документ остаётся **источником истины** для целевого дизайна безопасности ролей.
