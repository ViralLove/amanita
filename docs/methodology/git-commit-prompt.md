# Методика: работа с коммитами (промпт и процесс)

**Версия:** 1.1  
**Дата:** 2026-01-29  
**Связанные документы:** `docs/methodology/git-commit.md`, `@.cursor/commands/run-analysis.md`, `@.cursor/commands/run-phase.md`, `@.cursor/rules/test-qualification.mdc`

---

## 1. Назначение

Этот документ задаёт **методику работы с коммитами** при завершении тасков (контракты, тесты, документация):

- **Когда использовать:** после реализации фазы/таска, когда нужно зафиксировать изменения в git (группировка, сообщения коммитов, push).
- **Обязательное условие:** перед выполнением коммитов — **план коммита на согласование** с оператором; push — только после явного подтверждения оператора.

Алгоритм группировки файлов, фильтрация «что не коммитить», формат сообщений и примеры — в **docs/methodology/git-commit.md**.

## 2. Контекст: процесс для тасков (contracts: контракт + тесты + доки)

**Полный процесс работы над таском** (все этапы от анализа до пуша) — в **docs/methodology/task-execution-process.md**. Методика коммитов (этот документ + git-commit.md) используется на этапе **8** процесса. Ниже — краткая таблица этапов для контекста.

| Этап | Что делаем | Документ/команда |
|------|------------|-------------------|
| 1 | Анализ и рамки (gap, эталон) | run-analysis, документ таска |
| 2 | Решения до кода (decision-points) | Документ решений |
| 3 | Архитектура решения (фазы, шаги) | solution-architecture |
| **4** | **Реализация по фазам** | **@.cursor/commands/run-phase.md** — каждая фаза выполняется по этой команде (run-phase + документ с фазой N, шаги N.1 … N.K; ретроспективы по продукту и по процессу). |
| 5 | Опциональные шаги — явное «делаем» / «пропускаем» | run-phase, multi-step-phase-execution |
| **6** | **Квалификация тестов и отчёт** | **@.cursor/rules/test-qualification.mdc** — любой созданный/изменённый набор тестов проверяется по этому правилу (честность, логика, приоритеты P0/P1/P2). Итоговый отчёт квалификации дорабатывается с учётом требований **@.cursor/commands/run-phase.md** (ретроспектива по продукту, маркеры Выполнено по замечаниям, сводная таблица). |
| 7 | Документация в перманентной зоне `<контекст>/docs` (contracts/docs, scripts/docs и т.д.); по типу контента (архитектура, продукт, тех) создать или интегрировать; CHANGELOG в папку таска | solution-architecture, CHANGELOG в папке таска |
| **8** | **Коммиты и push** | **Методика @docs/methodology/git-commit-prompt.md и @docs/methodology/git-commit.md**: план коммита — на согласование; после одобрения — выполнение коммитов; push только по явному разрешению оператора. |

## 3. Алгоритм работы с коммитами (для агента/диалога)

Использовать **методологию и мышление @.cursor/commands/run-analysis.md** для анализа изменений (только факты из кода, без предположений). Для группировки и формата сообщений — **docs/methodology/git-commit.md**.

### Шаг 1: Анализ изменённых файлов

- Команды и фильтры — по **git-commit.md**, шаг 1 и шаг 2 (исключить сгенерированные, временные, логи, приватные данные, кэш и т.д.).
- Для новых файлов (untracked): проверить, что они контекстно связаны с задачей и их назначение понятно.

### Шаг 2: Группировка по функциональным категориям

- По **git-commit.md**, шаг 3: Core Feature, Tests, Documentation и т.д.; порядок групп с учётом зависимостей.

### Шаг 3: Описание изменений (CHANGELOG, опционально)

- Создать или обновить `contracts/docs/analysis/CHANGELOG-<feature-name>.md` (или аналог для другой директории) по структуре из **git-commit.md**, шаг 4.
- **В описании коммитов и CHANGELOG не перечислять файлы из папок тасков** (tasks/task-*/) — указывать только канонические документы, зеркала, CHANGELOG, группы изменений.

### Шаг 4: План коммита на согласование (обязательно)

- Сформировать **план коммита** и представить оператору **до выполнения коммитов**:
  - какие файлы в какую группу;
  - сколько коммитов и с какими сообщениями (type(scope): subject);
  - при необходимости — краткий body по группам.
- Дождаться **явного согласования** оператора («подходит», «исправить …», «разбить иначе»).
- **Не выполнять** `git commit` и `git add` до согласования плана (кроме случаев, когда оператор явно просит «сразу коммитить»).

### Шаг 5: Выполнение коммитов

- После согласования плана: для каждой группы выполнить `git add` и `git commit` с согласованным сообщением.
- Формат сообщений — по **git-commit.md**, шаг 5 (conventional commits: type(scope): subject; body при необходимости).

### Шаг 6: Push — только по разрешению оператора

- **Не выполнять** `git push` по умолчанию после коммитов.
- Сообщить оператору: коммиты созданы, список коммитов (например, `git log origin/dev..HEAD --oneline`); push выполнить после проверки или по команде оператора.
- Push выполняет оператор вручную или явно просит агента выполнить push после проверки.

## 4. Пример формулировки для диалога

```
Проанализируй изменённые файлы в <contracts|bot|…> по методике @docs/methodology/git-commit.md (шаги 1–2: фильтр, группировка).

Действия:
1. Выведи список изменённых файлов после фильтрации и группировку по категориям.
2. Предложи план коммитов: группы и сообщения (type(scope): subject) — на согласование.
3. После моего «подходит» выполни коммиты; push не делай — я проверю и запушу сама.
```

Для анализа использовать **@.cursor/commands/run-analysis.md** (только факты из кода).

## 6. Чеклист перед коммитами (напоминание)

- [ ] План коммита представлен оператору и согласован.
- [ ] Исключены файлы из категорий «НЕ коммитить» (git-commit.md, шаг 2).
- [ ] Группы логически целостны; порядок коммитов учтён.
- [ ] Сообщения коммитов на английском, conventional commits; в описании не перечислять внутренние файлы тасков.
- [ ] Push не выполнять без явного разрешения оператора.
