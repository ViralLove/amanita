# Методология обработки ошибок через анализ и тестирование гипотез

**Версия:** 1.0  
**Дата создания:** 2026-01-02  
**Методология:** @analysis.mdc  
**Статус:** ✅ Проверено на практике

---

## 🎯 Цель методологии

Систематический подход к обработке технических ошибок через:
1. **Генерацию гипотез** о возможных причинах
2. **Приоритизацию гипотез** по вероятности и влиянию
3. **Изолированное тестирование** каждой гипотезы
4. **Подтверждение/опровержение** через доказательства
5. **Документирование** процесса и результатов

**Применимость:** Любые технические контексты (код, инфраструктура, данные, интеграции)

---

## 📋 Область применения

### ✅ Когда использовать

- Ошибка не имеет очевидной причины
- Симптомы указывают на несколько возможных источников
- Нужно избежать "исправления вслепую"
- Требуется доказательное решение
- Важна воспроизводимость диагностики

### ❌ Когда НЕ использовать

- Ошибка тривиальна (опечатка, синтаксис)
- Причина очевидна из стека вызовов
- Время критично (hotfix в продакшене)
- Ошибка уже известна и задокументирована

## 🔄 Процесс (7 этапов)

### Этап 1: Описание ошибки

**Цель:** Зафиксировать симптомы и контекст

**Действия:**
1. Записать точное сообщение об ошибке (текст, код, стек)
2. Зафиксировать контекст:
   - Компонент/модуль/файл
   - Входные данные
   - Условия воспроизведения
   - Ожидаемое vs фактическое поведение
3. Собрать диагностическую информацию:
   - Логи
   - Метаданные (версии, окружение)
   - Связанные файлы/данные

**Артефакт:** Секция "Описание ошибки" в worklog

**Пример:**
```markdown
## 1. Описание ошибки

### Симптомы
```
ERROR: ❌ Ошибка при чтении CSV файла: Отсутствуют обязательные колонки: ID
```

### Контекст
- Скрипт: `bot/utility/generate_woo_id_mapping.py`
- Входной файл: `data/sellers/iveta/catalog/wc-product-export-*.csv`
- Лог показывает: "✅ Заголовки CSV: 12 колонок" — значит заголовки читаются
- Но проверка `'ID' not in reader.fieldnames` возвращает True
```

---

### Этап 2: Генерация гипотез

**Цель:** Создать список возможных причин ошибки

**Действия:**
1. **Мозговой штурм:** Перечислить все возможные причины
2. **Исследование кодовой базы:**
   - Поиск похожих проблем в истории
   - Анализ паттернов обработки данных
   - Проверка документации и примеров
3. **Анализ зависимостей:**
   - Внешние библиотеки/сервисы
   - Форматы данных
   - Кодировки, форматы файлов
4. **Категоризация:**
   - Проблемы с данными (формат, кодировка, структура)
   - Проблемы с кодом (логика, обработка)
   - Проблемы с инфраструктурой (окружение, зависимости)

**Артефакт:** Список гипотез с обоснованием

**Пример:**
```markdown
## 2. Анализ возможных источников проблемы

### 2.1 BOM (Byte Order Mark) в начале файла
**Гипотеза:** CSV файл может содержать BOM (`\ufeff`) в начале...
**Обоснование:**
- В коде проекта есть примеры обработки BOM
- WooCommerce может экспортировать CSV с BOM для Excel
- `csv.DictReader` не обрабатывает BOM автоматически

### 2.2 Пробелы в названиях колонок
**Гипотеза:** Названия колонок могут содержать ведущие/замыкающие пробелы...
**Обоснование:**
- CSV может быть отформатирован с пробелами
- `csv.DictReader` по умолчанию не обрезает пробелы
```

---

### Этап 3: Приоритизация гипотез

**Цель:** Определить порядок проверки гипотез

**Критерии приоритизации:**

1. **Вероятность** (🔴 Высокая / 🟡 Средняя / 🟢 Низкая)
   - Основана на обосновании и опыте
   - Учитывает частоту подобных проблем

2. **Влияние** (P0 / P1 / P2)
   - P0: Критично, блокирует выполнение
   - P1: Важно, влияет на функциональность
   - P2: Желательно, улучшает качество

3. **Сложность проверки** (Быстрая / Средняя / Долгая)
   - Быстрая: простой тест, изолированная проверка
   - Средняя: требует настройки окружения
   - Долгая: требует интеграции или сложной диагностики

**Правило:** Проверять гипотезы в порядке убывания приоритета (высокая вероятность + P0 → низкая вероятность + P2)

**Артефакт:** Приоритизированный список гипотез

**Пример:**
```markdown
### 2.1 BOM (Byte Order Mark)
**Вероятность:** 🔴 Высокая (наиболее вероятная причина)
**Влияние:** P0 (критично, блокирует выполнение)
**Сложность проверки:** Быстрая (простой бинарный тест)

### 2.2 Пробелы в названиях колонок
**Вероятность:** 🟡 Средняя
**Влияние:** P0 (критично, блокирует выполнение)
**Сложность проверки:** Быстрая (проверка через repr())
```

---

### Этап 4: Планирование теста гипотезы

**Цель:** Спроектировать изолированный тест для проверки гипотезы

**Действия:**

1. **Определить цель теста:**
   - Что именно проверяем?
   - Какие данные/файлы нужны?
   - Какие инструменты/методы использовать?

2. **Спроектировать шаги теста:**
   - Шаг 1: Подготовка (чтение данных, настройка)
   - Шаг 2: Выполнение (применение гипотезы)
   - Шаг 3: Сравнение (ожидаемое vs фактическое)
   - Шаг 4: Вывод (подтверждение/опровержение)

3. **Определить ожидаемые результаты:**
   - Если гипотеза верна: что должно произойти?
   - Если гипотеза неверна: что должно произойти?

4. **Выбрать локацию теста:**
   - Изолированная папка (`.test_isolated/` для временных тестов)
   - Или существующая тестовая структура (если тест постоянный)

**Артефакт:** Секция "Тест гипотезы" в worklog с логикой теста

**Пример:**
```markdown
## 2.1.1 Тест гипотезы BOM

### Локация теста
**Папка:** `.test_isolated/` (временные тесты, не коммитить в git)

### Логика теста

#### Цель теста
Проверить, содержит ли реальный CSV файл BOM в начале...

#### Шаги теста
**Шаг 1:** Проверка наличия BOM в файле (бинарный режим)
**Шаг 2:** Чтение заголовков без обработки BOM (encoding='utf-8')
**Шаг 3:** Чтение заголовков с обработкой BOM (encoding='utf-8-sig')
**Шаг 4:** Сравнение результатов

#### Ожидаемые результаты
**Если гипотеза верна:**
- Шаг 1: BOM обнаружен
- Шаг 2: Первая колонка содержит BOM символ
- Шаг 3: Первая колонка без BOM
- Шаг 4: Гипотеза подтверждена
```

### Этап 5: Реализация и выполнение теста

**Цель:** Создать и запустить тест для проверки гипотезы

**Методология:** Использовать @unit-test-build.mdc для структурирования теста

**Структура теста:**

1. **Phase 1: Infrastructure**
   - Создать структуру (папка, файл)
   - Настроить зависимости

2. **Phase 2.1: Smoke Tests**
   - Базовые функции проверки
   - Изолированные проверки компонентов

3. **Phase 2.2: Real Tests**
   - Полная логика проверки гипотезы
   - Диагностический вывод
   - Чёткий вывод: подтверждена / не подтверждена

- ✅ Изолирован (не влияет на основной код)
- ✅ Проверяет реальные данные/файлы (не моки, если возможно)

- ✅ Даёт чёткий ответ: гипотеза подтверждена / не подтверждена
- ✅ Результаты записываются в логи для анализа

### Этап 6: Анализ результатов

**Цель:** Интерпретировать результаты теста и принять решение

**Действия:**

1. **Если гипотеза подтверждена:**
   - Задокументировать доказательства
   - Определить решение (как исправить)
   - Применить решение
   - Протестировать исправление

2. **Если гипотеза не подтверждена:**
   - Задокументировать опровержение
   - Исключить эту причину
   - Перейти к следующей гипотезе (если есть)
   - Рассмотреть другие возможные причины

3. **Если результаты неоднозначны:**
   - Уточнить тест (добавить диагностику)
   - Проверить дополнительные аспекты
   - Рассмотреть комбинированные причины

**Артефакт:** Секция "Результаты теста" в worklog

**Пример:**
```markdown
## 2.1.2 Результаты теста гипотезы BOM

**Шаг 1:** ✅ BOM обнаружен: первые 3 байта = b'\xef\xbb\xbf'
**Шаг 2:** ⚠️ Первая колонка СОДЕРЖИТ BOM символ: '\ufeffID'
**Шаг 3:** ✅ Первая колонка НЕ содержит BOM: 'ID'
**Шаг 4:** ✅ ГИПОТЕЗА ПОДТВЕРЖДЕНА

### Вывод
1. Файл содержит BOM (\ufeff) в начале
2. При чтении с encoding='utf-8' первая колонка содержит BOM
3. При чтении с encoding='utf-8-sig' первая колонка корректна
4. Это объясняет ошибку "Отсутствуют обязательные колонки: ID"

### Рекомендация
✅ Применить Решение 1: использовать encoding='utf-8-sig' в read_woo_export()
```

### Этап 7: Документирование и применение решения

**Цель:** Зафиксировать решение и применить исправление

**Действия:**

1. **Документировать решение:**
   - Описать исправление
   - Указать файлы/методы для изменения
   - Привести пример кода (если применимо)

2. **Применить исправление:**
   - Внести изменения в код
   - Протестировать на реальных данных
   - Проверить, что ошибка устранена

3. **Обновить документацию:**
   - Worklog с результатами
   - Код с комментариями (если нужно)
   - README/документация (если применимо)

4. **Если есть другие гипотезы:**
   - Решить: проверять дальше или остановиться
   - Если решение работает, можно отложить проверку остальных
   - Если решение неполное, продолжить с следующей гипотезой

**Артефакт:** Исправленный код + обновлённый worklog

**Пример:**
```markdown
## 4. Рекомендуемое решение

### Решение 1: Обработка BOM (приоритет: P0)

**Действие:** Добавить обработку BOM перед чтением CSV.

**Реализация:**
```python
# Чтение файла с обработкой BOM
with open(csv_path, 'r', encoding='utf-8-sig', newline='') as f:
    reader = csv.DictReader(f)
```

**Преимущества:**
- ✅ Решает проблему BOM (наиболее вероятная причина)
- ✅ Минимальные изменения в коде
- ✅ Использует стандартную обработку Python
```

## 🎓 Принципы методологии

### 1. Доказательность (Evidence-Based)
- Каждая гипотеза проверяется через тест
- Решения основаны на доказательствах, а не на предположениях
- Все результаты документируются

### 2. Систематичность (Systematic)
- Структурированный процесс (7 этапов)
- Приоритизация гипотез
- Последовательная проверка

### 3. Изоляция (Isolation)
- Тесты изолированы от основного кода
- Проверка одной гипотезы за раз
- Минимальное влияние на систему

### 4. Документирование (Documentation)
- Весь процесс фиксируется в worklog
- Результаты тестов сохраняются
- Решения обосновываются

### 5. Итеративность (Iterative)
- Если гипотеза не подтверждена → следующая
- Если решение неполное → дополнительные гипотезы
- Цикл продолжается до решения проблемы
