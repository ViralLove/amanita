# Методика выполнения многошаговых фаз (Multi-Step Phase Execution)

**Версия:** 1.0  
**Дата создания:** 2026-01-29  
**Основа:** опыт фазы 3 ActivityRegistry (solution-architecture, runitem/run-task, ретроспективы)  
**Статус:** Инструкция для передачи в диалог вместе с шагами фазы

---

## 1. Цель методики

Обеспечить **полную, чистую реализацию заданной фазы** (набора шагов) без пропусков, искажений и галлюцинаций за счёт:

1. **Явного списка шагов в TODO** — каждый шаг фазы = один TODO item; прогресс виден и проверяем.
2. **Единого алгоритма выполнения каждого шага** — по @runitem (run-task): 7 фаз с логированием и валидацией.
3. **Обязательных отчётов по итогу фазы** — ретроспектива по продукту (что сделано vs план) и ретроспектива по процессу (как работали, что улучшить).
4. **Контрольных точек и чеклистов** — маркеры завершения шагов и краткий итог в начале/конце ответа, чтобы при обрезке лога не терялась уверенность в полноте.

**Применимость:** любые многошаговые фазы (архитектурные планы, TDD-фазы, миграции, последовательные релизы). Передаётся в диалог вместе с документом, содержащим шаги фазы (например, solution-architecture, раздел «Фаза N»).

---

## 1.1. Накопленные уроки (интегрированы из ретроспектив по процессу)

Ниже — уроки, перенесённые из ретроспектив по процессу; использовать при выполнении фаз и при обновлении методики.

**Видимость прогресса и защита от обрезки**
- В начале или в конце ответа давать краткий чеклист: «N.1 ✓, N.2 ✓, … N.K ✓» и одну строку проверки («N тестов, compile OK»). При обрезке середины остаётся видно, что фаза завершена.
- После каждого шага добавлять маркер `[Phase N.X DONE]` или `--- N.X OK ---`.
- Фазы из 3–5 шагов удобно выполнять в одном ответе с маркерами и итоговым чеклистом. Один длинный ответ на все пункты создаёт риск: при обрезке оператор видит только часть лога; маркеры и чеклист снижают этот риск.

**Опциональные шаги**
- Для пунктов «при необходимости» / «опционально» в начале шага фиксировать: «выполняем» или «пропускаем, причина». В ретроспективе по продукту — статус и комментарий. Не реализовывать опциональное без фиксации решения.
- Фазу можно формировать из списка замечаний (например, отчёт квалификации): шаги P1.1–P1.K; опциональный шаг — явно «выполняем» или «пропускаем, причина».
- Опциональная фаза из двух шагов (артефакт + прогон) может быть целиком верификационной, если артефакт уже создан в предыдущей фазе; в ретроспективе по продукту явно указывать «сделано ранее, валидация — …».

**Валидация и верификация**
- Не переходить к следующему шагу без валидации текущего. После каждого изменения — компиляция или прогон тестов; при провале — исправить, не переходить дальше.
- Шаг «убедиться, что …» можно выполнять чисто верификацией с фиксацией в ретроспективе («порядок проверен, изменений не потребовалось»).
- Если шаг плана уже выполнен ранее — явно зафиксировать в ретроспективе по продукту: «сделано ранее, валидация — прогон тестов»; не дублировать код.
- При тяжёлой компиляции сразу задавать увеличенный таймаут.

**План и критерии**
- Шаги из таблицы «Фаза N» должны быть однозначны. Для более крупных шагов явно выписывать acceptance criteria до валидации (улучшает воспроизводимость).
- Фаза может задаваться «из отчёта» (замечания квалификации и т.п.): шаги из списка замечаний при чёткой нумерации и рекомендациях.
- После отработки замечаний обновлять сам отчёт (Выполнено, сводная таблица), чтобы не оставалось впечатления незакрытых пунктов.

**Рефакторинг и артефакты**
- Рефакторинг «к стилю X» — пошагово: сначала секции и заголовки, затем NatSpec; верификация после каждого блока правок.
- Метрики (например, газа) фиксировать в отдельном файле в директории задачи (phaseN-gas-metrics.md) для сравнения при следующих изменениях.
- Общие хелперы тестов выносить в отдельный файл (например, helpers/testHelpers.js); при новых тестах подключать общий файл вместо копирования кода.

**Ретроспективы**
- Ретроспектива по продукту и по процессу — отдельные документы; в ретроспективе по процессу раздел «Уроки для следующих фаз».
- Уроки из ретроспективы по процессу накапливаются в буфере (phase-execution-lessons-cross-task.md) и периодически интегрируются в этот раздел методики (п. 1.1); после интеграции буфер очищается.

**Использование образцов**
- Использовать существующие образцы (структура Logic/Proxy по образцу других контрактов проекта) для уменьшения расхождений со стилем. При рефакторинге секций и заголовков — сравнение с эталонным артефактом.

## 2. Входы и выходы

| Вход | Описание |
|------|----------|
| Документ с фазой | Файл (например, solution-architecture-task1-activity-registry.md) с разделом «Фаза N» и таблицей шагов N.1, N.2, … N.K. |
| Команда | «Выполни фазу N по методике multi-step-phase-execution: вынеси шаги в TODO, выполняй каждый по runitem, по итогу сформируй отчёты». |

| Выход | Описание |
|-------|----------|
| Реализация | Код/артефакты по всем шагам; компиляция и тесты проходят. |
| TODO | Все пункты фазы N отмечены completed (или явно cancelled с причиной). |
| Ретроспектива по продукту | Документ: по каждому шагу — что задано, что сделано, расхождения, качество. |
| Ретроспектива по процессу | Документ: как работали (подход, структура), что сработало, что нет, уроки. |

## 3. Алгоритм (инструкция для диалога)

Выполнять **строго по шагам**. После каждого шага — проверка (компиляция/тесты/критерии); переход к следующему только после успеха.

### 3.0. Подготовка

- Прочитать документ с фазой; выписать шаги N.1, N.2, … N.K (нумерация и формулировки из плана).
- Убедиться, что есть однозначный источник истины (таблица в документе). Если шаги размыты — уточнить у оператора перед стартом.

### 3.1. Вынести шаги фазы в TODO

- Создать TODO items: по одному на каждый шаг N.1 … N.K.
- Идентификаторы: например `phaseN-1`, `phaseN-2`, … `phaseN-K`.
- Текст каждого TODO: краткая формулировка шага из плана (достаточно для напоминания, что делать).
- Статус всех: `pending`.
- **Контрольная точка:** список TODO виден в интерфейсе; количество пунктов = количеству шагов в плане.

### 3.2. Выполнять каждый TODO по алгоритму runitem (run-task)

Для **каждого** TODO item (по одному за раз):

1. **Understanding** — анализ текущего состояния (код, тесты, артефакты): что уже есть, чего не хватает для этого шага.
2. **Knowledge Check** — при необходимости: образцы в проекте, конвенции, внешние знания (без галлюцинаций; ссылки на файлы/документы).
3. **Acceptance Criteria** — явный список критериев приёмки для этого шага (по плану + при необходимости уточнения). Желательно коротко зафиксировать в ответе (например, маркированный список).
4. **Planning** — план изменений (какие файлы, какие правки); без перехода к реализации до согласования плана с планом фазы.
5. **Implementation** — внесение изменений; минимальный объём, только в рамках шага.
6. **Validation** — проверка по критериям: компиляция, тесты, или явный чеклист (например, «критерий 1 — да, критерий 2 — да»). При провале — исправить, не переходить к следующему TODO.
7. **Retrospective** — одна-две фразы: что сделано, что сработало/не сработало в этом шаге.

После успешной валидации: отметить TODO как `completed`; при необходимости — краткий маркер в ответе: `[Phase N.X DONE]`.

**Опциональные шаги:** если в плане шаг помечен «опционально» / «при необходимости» — перед реализацией кратко зафиксировать: «выполняем» или «пропускаем, причина». Тогда в отчёте не будет неопределённости.

**Контрольная точка:** перед переходом к следующему TODO — убедиться, что тесты/компиляция проходят и критерии шага выполнены.

### 3.3. Итоговый чеклист в ответе (защита от обрезки лога)

После выполнения всех TODO — в **начале** или **конце** ответа дать краткий блок:

```text
Фаза N — итог: N.1 ✓, N.2 ✓, … N.K ✓. Проверка: [команда] — [результат, например: 37 тестов, compile OK].
```

Так при обрезке середины ответа остаётся видно, что фаза завершена полностью.

### 3.4. Ретроспектива по продукту

Создать документ (например, `phaseN-retrospective-<контекст>.md` в той же директории, что и план):

- По **каждому** шагу N.1 … N.K:
  - **Задано по плану** — дословно или кратко из таблицы плана.
  - **Сделано** — что реально сделано (файлы, функции, тесты).
  - **Расхождения** — есть/нет; если есть — как согласовано (или оставить на доработку).
  - **Качество** — кратко (соответствие образцам, стилю, критериям).
  - **Выводы** — одна-две фразы.
- Сводная таблица: шаг | статус | расхождения.
- Итоговая проверка: команда запуска тестов/компиляции и результат.

Цель: исключить пропуски и искажения — любое расхождение между планом и фактом явно зафиксировано.

### 3.5. Ретроспектива по процессу

Создать документ (например, `phaseN-process-retrospective.md`):

- **Исходный запрос и выбор способа работы** — как сформулирована задача, как выбран run-task/TODO.
- **Что сработало хорошо** — структура, проверки, образцы, отчёты.
- **Что сработало плохо или создало риски** — длинный ответ, отсутствие маркеров, опциональные шаги без явного решения и т.п.
- **Как отреагировали на сбои** — если были вопросы оператора (например, «вижу только до N.2») — что сделали и какой вывод.
- **Уроки для следующих фаз** — конкретные рекомендации (чеклист в начале/конце, маркеры `[N.X DONE]`, по одному шагу за ответ при необходимости, явное решение по опциональным пунктам).

Цель: улучшать процесс на следующих фазах и не повторять проблемы видимости/коммуникации.

### 3.6. Буфер уроков (перенос в методику)

После формирования ретроспективы по процессу **дополнить буфер** **docs/methodology/phase-execution-lessons-cross-task.md**:

- Взять пункты из раздела «Уроки для следующих фаз» ретроспективы по процессу.
- Добавить их в буфер (кратко, с указанием источника: фаза N, задача).

**Интеграция:** периодически уроки из буфера переносятся в раздел **1.1** этой методики; после переноса буфер очищается (остаётся только описание роли буфера). См. команду run-phase.

## 4. Обязательные правила (защита от пропусков и галлюцинаций)

1. **Не переходить к следующему шагу без валидации текущего.** Если тесты падают или критерии не выполнены — исправить, затем переходить.
2. **Каждый шаг плана = ровно один TODO.** Не объединять два шага в один TODO без явного согласования с планом (риск пропуска части).
3. **Ретроспектива по продукту ссылается на план дословно.** Цитаты или краткое воспроизведение «задано по плану» из документа фазы — чтобы нельзя было подменить формулировку.
4. **Опциональные шаги — явное решение.** Либо «выполняем», либо «пропускаем, причина»; в ретроспективе по продукту — статус и комментарий.
5. **Итоговый чеклист обязателен.** Хотя бы одна строка в ответе после фазы: «N.1 ✓ … N.K ✓. Проверка: …».

## 5. Шаблон промпта для запуска фазы

Ниже — шаблон, который можно вставить в диалог, подставив путь к документу и номер фазы.

```markdown
Выполни фазу [N] по методике docs/methodology/multi-step-phase-execution.md.

- Источник шагов: [путь к документу, например contracts/docs/analysis/tasks/task-Activities-1/solution-architecture-task1-activity-registry.md], раздел «Фаза [N]» (шаги [N].1–[N].K).
- Действия:
  1. Вынеси все шаги фазы в TODO (phase[N]-1 … phase[N]-K).
  2. Выполняй каждый TODO по алгоритму @.cursor/commands/runitem.md (run-task: 7 фаз с логированием).
  3. После каждого шага — валидация (компиляция/тесты); маркер [Phase N.X DONE] при успехе.
  4. В конце ответа — итоговый чеклист: N.1 ✓ … N.K ✓, команда проверки и результат.
  5. Сформируй два отчёта: ретроспектива по продукту (что задано / что сделано / расхождения по каждому шагу), ретроспектива по процессу (как работали, что сработало, что нет, уроки).

Цель: полная, чистая реализация фазы без пропусков и искажений; отчёты — для проверки и для следующих фаз.
```

## 7. Краткая памятка (для вставки в контекст)

- **Вход:** документ с фазой (таблица шагов N.1 … N.K).
- **Шаги методики:** (1) TODO из шагов → (2) каждый TODO по run-task с валидацией и маркером [N.X DONE] → (3) итоговый чеклист в ответе → (4) ретроспектива по продукту → (5) ретроспектива по процессу → (6) добавить уроки в буфер phase-execution-lessons-cross-task.md (при интеграции — перенос в п. 1.1 методики, буфер очистить).
- **Защита:** не переходить к следующему шагу без валидации; один шаг плана = один TODO; опциональные шаги — явное «делаем/пропускаем»; ретроспектива продукта — цитаты из плана.
- **Выход:** реализация фазы, все TODO completed, два отчёта (продукт + процесс), уроки добавлены в буфер (или интегрированы в п. 1.1).
