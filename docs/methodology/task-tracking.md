# Методология организации и отслеживания задач (Task Tracking)

**Версия:** 1.0  
**Дата создания:** 2026-01-13  
**Методология:** @analysis.mdc  
**Статус:** ✅ Проверено на практике

---

## 🎯 Цель методологии

Создать **прозрачную, масштабируемую систему отслеживания задач** через:
1. **Единый issues tracker** — централизованный список всех задач в формате Jira-style
2. **Статусы задач** — понятная классификация состояния (DONE/PARTIAL/TODO/READY/CHECK)
3. **Краткие комментарии** — быстрая ориентация по каждой задаче без чтения полного файла
4. **Автоматическую актуализацию** — регулярное обновление статусов на основе кода

**Применимость:** Все директории с задачами в формате `*/docs/analysis/tasks/`

---

## 📋 Область применения

### ✅ Когда использовать

- Для организации задач в любой директории `*/docs/analysis/tasks/`
- Для создания единой точки входа (README.md) для обзора всех задач
- Для быстрой навигации по задачам без открытия каждого файла
- Для отслеживания прогресса выполнения задач
- Для планирования спринтов/итераций

### ❌ Когда НЕ использовать

- Для задач, которые уже выполнены и удалены (см. раздел об удалении)
- Для временных worklog файлов (они удаляются после завершения работы)
- Для аналитических документов (они перечисляются отдельным разделом)

## 📐 Структура README.md

### Формат файла

Файл `README.md` в директории `*/docs/analysis/tasks/` является **issues tracker** в формате Jira-style.

### Обязательные секции

#### 1. Заголовок и метаданные
```markdown
# Tasks — список задач (Issues Tracker)

**Формат:** Jira-style issues list  
**Последнее обновление:** YYYY-MM-DD  
**Метод:** @analysis.mdc
```

#### 2. Активные задачи (по статусам)

Задачи группируются по статусам:

```markdown
### ⚠️ PARTIAL (частично выполнено)

- [⚠️ PARTIAL] [`task-name.md`](task-name.md)  
  *Осталось:* Краткое описание что осталось сделать

### ❌ TODO (не выполнено)

- [❌ TODO] [`task-name.md`](task-name.md)  
  *Осталось:* Краткое описание что нужно сделать

### ⚠️ READY (готово к выполнению)

- [⚠️ READY] [`task-name.md`](task-name.md)  
  *Осталось:* Краткое описание что готово к реализации

### ⚠️ CHECK (требует проверки)

- [⚠️ CHECK] [`task-name.md`](task-name.md)  
  *Комментарий:* Почему требуется проверка
```

#### 3. Аналитические документы

```markdown
## 📊 Аналитические документы (не задачи)

- [`analysis-doc.md`](analysis-doc.md) — краткое описание назначения
```

#### 4. Статистика

```markdown
## 📈 Статистика

- **Всего активных задач:** N
  - ⚠️ PARTIAL: X
  - ❌ TODO: Y
  - ⚠️ READY: Z
  - ⚠️ CHECK: W

- **Аналитические документы:** M
```

#### 5. Легенда статусов (опционально)

```markdown
**Формат статусов:**
- ✅ DONE — выполнено и удалено из списка
- ⚠️ PARTIAL — частично выполнено, требуется доработка
- ❌ TODO — не выполнено, требует реализации
- ⚠️ READY — готово к выполнению, все зависимости выполнены
- ⚠️ CHECK — требует дополнительной проверки (дубликат/уточнение)
```

## 🏷️ Статусы задач

### ✅ DONE

**Определение:** Задача полностью выполнена, все AC/DoD закрыты, изменения в коде проверены.

**Действия:**
- ✅ Удалить файл задачи из директории
- ✅ Обновить README.md (убрать из списка)
- ✅ Обновить статистику
- ✅ Задокументировать удаление в логе (опционально)

**Как определить:**
- Проверить код на наличие реализации (grep, codebase_search)
- Проверить тесты на наличие покрытия (для тестовых задач)
- Проверить AC/DoD в файле задачи (все чекбоксы должны быть `[x]`)

---

### ⚠️ PARTIAL

**Определение:** Задача частично выполнена, но не все AC/DoD закрыты.

**Критерии:**
- Основная функциональность реализована
- Часть AC/DoD не выполнена (тесты, документация, edge cases)
- Статус в файле задачи "draft" или не обновлён

**Действия:**
- ✅ Оставить в списке с статусом PARTIAL
- ✅ В комментарии указать что конкретно осталось сделать
- ⚠️ Обновить статус в самом файле задачи (опционально)

**Пример комментария:**
```
*Осталось:* Проверить все AC/DoD, обновить статус с "draft" на "done", добавить тесты если нужно
```

---

### ❌ TODO

**Определение:** Задача не выполнена, требует реализации.

**Критерии:**
- Функциональность не реализована
- Тесты отсутствуют (для тестовых задач)
- Код не изменён (или изменения минимальны)

**Действия:**
- ✅ Оставить в списке с статусом TODO
- ✅ В комментарии кратко описать что нужно сделать

**Пример комментария:**
```
*Осталось:* Реализовать функцию `format_product_short_description()`, добавить unit-тесты, заполнить `Short description` в CSV экспорте (сейчас пустой)
```

---

### ⚠️ READY

**Определение:** Задача готова к выполнению, все зависимости выполнены.

**Критерии:**
- Все зависимости (другие задачи) выполнены
- Контент/спецификация готовы
- Архитектура решения согласована
- Блокеров нет

**Действия:**
- ✅ Оставить в списке с статусом READY
- ✅ В комментарии указать что готово и что осталось сделать

**Пример комментария:**
```
*Осталось:* Реализовать контент-стратегию для Short Description (CMO задача, контент готов, требуется интеграция)
```

---

### ⚠️ CHECK

**Определение:** Задача требует дополнительной проверки (дубликат, уточнение scope, etc).

**Критерии:**
- Подозрение на дубликат другой задачи
- Неясность scope или требований
- Конфликт с другими задачами

**Действия:**
- ✅ Оставить в списке с статусом CHECK
- ✅ В комментарии указать почему требуется проверка

**Пример комментария:**
```
*Комментарий:* Возможно дубликат worklog файла (который уже удалён). Проверить, отличается ли от worklog версии
```

## 🔄 Процесс обновления README.md

### Периодичность

- **После завершения задачи:** немедленно
- **После анализа задач:** после каждого анализа (см. `task-status-report.md`)
- **Перед планированием спринта:** обязательно

### Шаги обновления

1. **Собрать информацию о статусах:**
   - Проверить код на наличие реализации
   - Проверить тесты на наличие покрытия
   - Проверить AC/DoD в файлах задач

2. **Определить статус каждой задачи:**
   - DONE → удалить файл и строку из README
   - PARTIAL → обновить комментарий "Осталось"
   - TODO → проверить актуальность комментария
   - READY → проверить готовность
   - CHECK → проверить необходимость проверки

3. **Обновить README.md:**
   - Переместить задачи между секциями если статус изменился
   - Обновить комментарии "Осталось" для точности
   - Обновить статистику

4. **Двойная валидация:**
   - Проверить что все файлы задач из директории перечислены (кроме удалённых)
   - Проверить что все ссылки работают
   - Проверить что статистика совпадает с реальным количеством

## 📝 Формат комментариев "Осталось"

### Правила

1. **Краткость:** максимум 1-2 предложения
2. **Конкретность:** что именно нужно сделать (функции, тесты, изменения)
3. **Фокус на результате:** что будет достигнуто
4. **Технические детали:** при необходимости указать конкретные файлы/методы

### Примеры хороших комментариев

✅ **Хорошо:**
```
*Осталось:* Реализовать функцию `format_product_short_description()`, добавить unit-тесты, заполнить `Short description` в CSV экспорте (сейчас пустой)
```

✅ **Хорошо:**
```
*Осталось:* Добавить handler для `product:cart:*` или явно зафиксировать тестом как "в разработке"
```

✅ **Хорошо:**
```
*Осталось:* Проверить все AC/DoD, обновить статус с "draft" на "done", добавить тесты если нужно
```

❌ **Плохо:**
```
*Осталось:* Доделать
```

❌ **Плохо:**
```
*Осталось:* Много чего осталось сделать по задаче, нужно проверить код и добавить реализацию, возможно тесты тоже нужны
```

## 🗑️ Удаление выполненных задач

### Когда удалять

- ✅ Задача полностью выполнена (все AC/DoD закрыты)
- ✅ Реализация проверена в коде
- ✅ Тесты добавлены (для тестовых задач)
- ✅ Статус задачи обновлён на "done" (опционально)

### Процесс удаления

1. **Двойная валидация:**
   - Проверить код на наличие реализации
   - Проверить тесты на наличие покрытия
   - Проверить AC/DoD

2. **Удалить файл:**
   ```bash
   rm path/to/task-file.md
   ```

3. **Обновить README.md:**
   - Убрать задачу из списка
   - Обновить статистику

4. **Задокументировать удаление (опционально):**
   - Создать `tasks-deletion-log.md` с датой удаления и доказательствами

### Worklog файлы

Worklog файлы удаляются **после завершения работы** и проверки что все изменения применены.

**Критерии удаления worklog:**
- Анализ завершён
- Реализация выполнена (если применимо)
- Информация перенесена в основной таск (если применимо)

## 📊 Интеграция с другими методологиями

### Связь с Task Standard

- `task-standard.md` определяет **формат задач**
- `task-tracking.md` определяет **организацию списка задач**

**Использование:**
1. Создать задачу по `task-standard.md`
2. Добавить в README.md по `task-tracking.md`
3. Обновлять статус в README.md при прогрессе

### Связь с Task Status Report

- `tasks-status-report.md` — результат анализа всех задач
- `README.md` — актуальный issues tracker

**Процесс:**
1. Создать `tasks-status-report.md` через анализ
2. Обновить `README.md` на основе отчёта
3. Удалить выполненные задачи

## 🎯 Примеры использования

### Пример 1: Добавление новой задачи

1. Создать файл `task-implement-new-feature.md` по `task-standard.md`
2. Добавить в README.md:
   ```markdown
   ### ❌ TODO (не выполнено)
   
   - [❌ TODO] [`task-implement-new-feature.md`](task-implement-new-feature.md)  
     *Осталось:* Реализовать новую фичу согласно AC/DoD
   ```
3. Обновить статистику

### Пример 2: Завершение задачи

1. Проверить выполнение через анализ кода
2. Удалить файл задачи
3. Убрать из README.md
4. Обновить статистику

### Пример 3: Частичное выполнение

1. Проверить что реализовано в коде
2. Обновить статус в README.md на PARTIAL
3. Обновить комментарий "Осталось" с конкретными пунктами
