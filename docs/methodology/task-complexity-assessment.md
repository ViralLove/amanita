# Методология оценки сложности задач (Task Complexity Assessment)

**Версия:** 1.0  
**Дата создания:** 2026-01-07  
**Методология:** @analysis.mdc  
**Статус:** ✅ Проверено на практике

---

## 🎯 Цель методологии

Систематический подход к оценке сложности задач через:
1. **Многокритериальный анализ** — оценка по 7 независимым критериям
2. **Количественная шкала** — единая 10-балльная шкала для всех критериев
3. **Категоризация** — автоматическое определение размера (XS/S/M/L/XL)
4. **Прогнозирование времени** — реалистичные оценки на основе категории
5. **Документирование** — обоснование каждой оценки

**Применимость:** Все задачи в проекте (fix, implement, refactor, tests, data)

---

## 📋 Область применения

### ✅ Когда использовать

- При создании новых задач (оценка до начала работы)
- При планировании спринта/итерации
- При пересмотре оценок в процессе работы
- При ретроспективе (сравнение оценки vs реальность)
- При обосновании сроков для стейкхолдеров

### ❌ Когда НЕ использовать

- Для тривиальных задач (< 5 минут)
- Для экстренных hotfix (времени нет на оценку)
- Для исследовательских задач (неопределённость > 80%)

---

## 📊 Критерии оценки (7 критериев)

### 1. Объём изменений кода (Code Volume)

**Что измеряем:** Количество файлов, функций, строк кода для изменения

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Минимальные изменения | 1 файл, 1-2 функции, < 20 строк |
| 3-4 | Небольшие изменения | 2-3 файла, 3-5 функций, 20-50 строк |
| 5-6 | Средние изменения | 4-6 файлов, 5-10 функций, 50-150 строк |
| 7-8 | Значительные изменения | 7-10 файлов, 10-20 функций, 150-300 строк |
| 9-10 | Масштабные изменения | > 10 файлов, > 20 функций, > 300 строк |

**Вопросы для оценки:**
- Сколько файлов нужно изменить?
- Сколько функций/методов затрагивается?
- Сколько строк кода примерно добавится/изменится?

---

### 2. Архитектурная сложность (Architectural Complexity)

**Что измеряем:** Влияние на архитектуру системы

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Локальные изменения | Изменение внутри одной функции |
| 3-4 | Изменения в модуле | Новый helper, изменение класса |
| 5-6 | Изменения между модулями | Новый интерфейс, изменение контракта |
| 7-8 | Архитектурные изменения | Новый слой, паттерн, сервис |
| 9-10 | Системные изменения | Миграция, рефакторинг ядра |

**Вопросы для оценки:**
- Нужны ли новые классы/модули?
- Меняются ли интерфейсы/контракты?
- Затрагивается ли data flow?
- Нужны ли новые абстракции?

---

### 3. Риск регрессии (Regression Risk)

**Что измеряем:** Вероятность сломать существующую функциональность

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Минимальный риск | Изолированный код, нет зависимостей |
| 3-4 | Низкий риск | Локальные изменения, хорошее покрытие тестами |
| 5-6 | Средний риск | Изменения в shared-коде, частичное покрытие |
| 7-8 | Высокий риск | Критический путь, много зависимостей |
| 9-10 | Критический риск | Ядро системы, продакшен-критичный код |

**Вопросы для оценки:**
- Сколько компонентов зависит от изменяемого кода?
- Есть ли тесты для затрагиваемого кода?
- Насколько критичен этот код для бизнеса?

---

### 4. Необходимость тестирования (Testing Effort)

**Что измеряем:** Объём тестирования для валидации изменений

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Минимальное | Ручной smoke-тест, 1 команда |
| 3-4 | Базовое | Несколько ручных тестов или 1-2 unit-теста |
| 5-6 | Стандартное | Unit + integration тесты |
| 7-8 | Расширенное | E2E тесты, тестирование на реальных данных |
| 9-10 | Комплексное | Нагрузочное, security, multi-environment |

**Вопросы для оценки:**
- Достаточно ли ручного теста?
- Нужны ли новые unit/integration тесты?
- Требуется ли тестирование на реальных данных?

---

### 5. Понимание контекста (Context Knowledge)

**Что измеряем:** Необходимый уровень понимания системы/домена

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Очевидно | Стандартный код, документация есть |
| 3-4 | Базовое понимание | Нужно прочитать 1-2 связанных файла |
| 5-6 | Среднее понимание | Нужно изучить модуль/компонент |
| 7-8 | Глубокое понимание | Нужно понимать архитектуру системы |
| 9-10 | Экспертное понимание | Нужно знание домена, внешних систем |

**Вопросы для оценки:**
- Насколько хорошо задокументирован затрагиваемый код?
- Сколько контекста нужно изучить?
- Требуется ли знание внешних систем/API?

---

### 6. Зависимости (Dependencies)

**Что измеряем:** Внешние и внутренние зависимости задачи

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Нет зависимостей | Полностью автономная задача |
| 3-4 | Минимальные | Зависит от 1-2 внутренних компонентов |
| 5-6 | Умеренные | Зависит от нескольких модулей |
| 7-8 | Значительные | Внешние API, базы данных, сервисы |
| 9-10 | Критические | Блокирующие зависимости, внешние команды |

**Вопросы для оценки:**
- Есть ли блокирующие задачи?
- Нужны ли внешние библиотеки/сервисы?
- Требуется ли координация с другими командами?

---

### 7. Неопределённость (Uncertainty)

**Что измеряем:** Уровень неизвестности в задаче

| Оценка | Описание | Примеры |
|--------|----------|---------|
| 1-2 | Полная ясность | Чёткие требования, известное решение |
| 3-4 | Небольшая неясность | 1-2 открытых вопроса |
| 5-6 | Умеренная неясность | Несколько вариантов решения |
| 7-8 | Значительная неясность | Нужно исследование, прототипирование |
| 9-10 | Высокая неопределённость | Неизвестно, возможно ли решение |

**Вопросы для оценки:**
- Насколько чёткие требования?
- Известно ли решение?
- Нужно ли исследование/эксперименты?

## 📐 Формула расчёта

### Средняя сложность

```
Средняя сложность = (K1 + K2 + K3 + K4 + K5 + K6 + K7) / 7
```

Где:
- K1 = Объём изменений кода
- K2 = Архитектурная сложность
- K3 = Риск регрессии
- K4 = Необходимость тестирования
- K5 = Понимание контекста
- K6 = Зависимости
- K7 = Неопределённость

### Взвешенная сложность (опционально)

Для проектов с особыми приоритетами можно использовать веса:

```
Взвешенная сложность = (w1×K1 + w2×K2 + w3×K3 + w4×K4 + w5×K5 + w6×K6 + w7×K7) / Σw
```

**Рекомендуемые веса для разных контекстов:**

| Контекст | K1 | K2 | K3 | K4 | K5 | K6 | K7 |
|----------|----|----|----|----|----|----|-----|
| Стандартный | 1 | 1 | 1 | 1 | 1 | 1 | 1 |
| Критичный продакшен | 1 | 1 | 2 | 2 | 1 | 1 | 1 |
| Исследование | 1 | 1 | 0.5 | 0.5 | 1 | 1 | 2 |
| Рефакторинг | 1 | 2 | 2 | 1 | 1 | 1 | 0.5 |

## 📏 Категории размера

### Определение категории

| Категория | Диапазон | Время | Описание |
|-----------|----------|-------|----------|
| **XS** | 1.0 - 2.0 | 15-30 мин | Тривиальная задача |
| **S** | 2.1 - 4.0 | 30-60 мин | Небольшая задача |
| **M** | 4.1 - 6.0 | 1-3 часа | Средняя задача |
| **L** | 6.1 - 8.0 | 0.5-1 день | Большая задача |
| **XL** | 8.1 - 10.0 | 1-3 дня | Очень большая задача |

### Рекомендации по категориям

| Категория | Рекомендации |
|-----------|--------------|
| **XS** | Выполнять сразу, без детального планирования |
| **S** | Краткий план, можно совмещать несколько в день |
| **M** | Детальный план, выделить отдельный блок времени |
| **L** | Декомпозировать на подзадачи, планировать на день |
| **XL** | Обязательная декомпозиция, review плана, буфер времени |

## 📝 Шаблон оценки

```markdown
## Оценка сложности: [Название задачи]

### Критерии оценки (шкала 1-10)

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| **Объём изменений кода** | X/10 | [Кратко: файлы, функции, строки] |
| **Архитектурная сложность** | X/10 | [Кратко: новые абстракции?] |
| **Риск регрессии** | X/10 | [Кратко: что может сломаться?] |
| **Необходимость тестирования** | X/10 | [Кратко: какие тесты нужны?] |
| **Понимание контекста** | X/10 | [Кратко: что нужно изучить?] |
| **Зависимости** | X/10 | [Кратко: от чего зависит?] |
| **Неопределённость** | X/10 | [Кратко: что неясно?] |

### Итоговая оценка

**Средняя сложность:** X.X / 10
**Категория:** XS/S/M/L/XL
**Оценка времени:** X-Y минут/часов/дней

### Рекомендации

- [Рекомендация 1]
- [Рекомендация 2]
```

## 🔄 Процесс оценки (5 шагов)

### Шаг 1: Изучение задачи

**Действия:**
1. Прочитать описание задачи
2. Определить затрагиваемые файлы/модули
3. Понять ожидаемый результат

**Время:** 2-5 минут

### Шаг 2: Оценка каждого критерия

**Действия:**
1. Пройти по каждому из 7 критериев
2. Задать себе вопросы для оценки
3. Выставить оценку 1-10 с обоснованием

**Время:** 5-10 минут

### Шаг 3: Расчёт средней сложности

**Действия:**
1. Сложить все оценки
2. Разделить на 7
3. Округлить до 1 знака после запятой

**Время:** 1 минута

### Шаг 4: Определение категории

**Действия:**
1. Сопоставить среднюю сложность с диапазоном
2. Определить категорию (XS/S/M/L/XL)
3. Оценить время выполнения

**Время:** 1 минута

### Шаг 5: Корректировка и документирование

**Действия:**
1. Проверить адекватность оценки (здравый смысл)
2. При необходимости скорректировать
3. Задокументировать в задаче

**Время:** 2-3 минуты

**Общее время на оценку:** 10-20 минут

## 📊 Примеры оценок

### Пример 1: Тривиальная задача (XS)

**Задача:** Убрать генерацию SKU для вариаций в WooCommerce экспорте

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Объём изменений кода | 2/10 | 2 функции, ~6-7 строк |
| Архитектурная сложность | 1/10 | Локальные изменения, без новых абстракций |
| Риск регрессии | 3/10 | Затрагивает CSV экспорт, но изолировано |
| Необходимость тестирования | 2/10 | Достаточно ручного теста |
| Понимание контекста | 4/10 | Нужно понимать WooCommerce формат |
| Зависимости | 1/10 | Нет внешних зависимостей |
| Неопределённость | 2/10 | Чёткое понимание что делать |

**Средняя:** (2+1+3+2+4+1+2) / 7 = **2.1 / 10**  
**Категория:** **XS**  
**Время:** 15-30 минут

---

### Пример 2: Средняя задача (M)

**Задача:** Добавить поддержку вариаций в WooCommerce mapping

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Объём изменений кода | 5/10 | 1 файл, 3-4 новые функции, ~100 строк |
| Архитектурная сложность | 4/10 | Новые структуры данных, расширение формата |
| Риск регрессии | 4/10 | Может сломать существующий mapping |
| Необходимость тестирования | 5/10 | Нужны тесты на реальных данных |
| Понимание контекста | 6/10 | Нужно понимать WooCommerce вариации |
| Зависимости | 3/10 | Зависит от формата WooCommerce экспорта |
| Неопределённость | 4/10 | Несколько вариантов структуры |

**Средняя:** (5+4+4+5+6+3+4) / 7 = **4.4 / 10**  
**Категория:** **M**  
**Время:** 1-3 часа

---

### Пример 3: Большая задача (L)

**Задача:** Рефакторинг системы цен (weight/volume → quantity/unit)

| Критерий | Оценка | Обоснование |
|----------|--------|-------------|
| Объём изменений кода | 7/10 | 10+ файлов, модели, сервисы, тесты |
| Архитектурная сложность | 6/10 | Изменение модели данных |
| Риск регрессии | 7/10 | Затрагивает много компонентов |
| Необходимость тестирования | 7/10 | Нужны unit + integration тесты |
| Понимание контекста | 6/10 | Нужно понимать всю систему цен |
| Зависимости | 5/10 | Зависит от нескольких модулей |
| Неопределённость | 4/10 | План есть, но детали выясняются |

**Средняя:** (7+6+7+7+6+5+4) / 7 = **6.0 / 10**  
**Категория:** **L**  
**Время:** 0.5-1 день

## 🎓 Принципы методологии

### 1. Объективность (Objectivity)

- Оценки основаны на измеримых критериях
- Каждая оценка имеет обоснование
- Минимум субъективности

### 2. Консистентность (Consistency)

- Одинаковые критерии для всех задач
- Единая шкала 1-10
- Стандартные категории

### 3. Практичность (Practicality)

- Быстрая оценка (10-20 минут)
- Простая формула
- Понятные категории

### 4. Итеративность (Iterativity)

- Оценка может корректироваться
- Ретроспектива: план vs факт
- Улучшение точности со временем

## 📈 Метрики качества оценок

### Точность оценки

```
Точность = 1 - |Оценка - Факт| / Факт
```

**Целевые показатели:**
- XS/S задачи: ±30% от оценки
- M задачи: ±50% от оценки
- L/XL задачи: ±100% от оценки

### Ретроспектива

После выполнения задачи:
1. Записать фактическое время
2. Сравнить с оценкой
3. Проанализировать расхождения
4. Скорректировать подход к оценке

---

## ✅ Definition of Done

Оценка выполнена корректно, когда:

- [ ] Все 7 критериев оценены (1-10)
- [ ] Каждая оценка имеет обоснование
- [ ] Рассчитана средняя сложность
- [ ] Определена категория (XS/S/M/L/XL)
- [ ] Оценено время выполнения
- [ ] Оценка задокументирована в задаче
- [ ] Оценка соответствует здравому смыслу
