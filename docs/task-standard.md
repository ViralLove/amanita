# Стандарт Форматирования Задач (Task Standard)

**Версия:** 1.0
**Дата создания:** 2025-12-25
**Применение:** Все новые задачи в директориях `*/docs/analysis/tasks/`
**Методология:** Основан на анализе существующих тасков согласно @.cursor/rules/analysis.mdc

## Цель Стандарта

Создать **единообразный, эффективный формат** постановки задач, который:
- Гарантирует полноту анализа и планирования
- Минимизирует неоднозначности в понимании
- Ускоряет выполнение через четкие AC/DoD и планы
- Обеспечивает traceability (связи между задачами)
- Поддерживает масштабирование команды

## Общие Принципы

### 1. Истинность (Truth-First)
- **Только факты из кода** - никаких предположений или "должно быть"
- **Цитаты с номерами строк** - каждая претензия подкреплена кодом
- **Воспроизводимость** - все команды/факты проверяемы

### 2. Атомарность (One Task = One Gap)
- Одна задача = один конкретный gap/issue
- Если задача разрастается → декомпозировать на подзадачи
- Связи между задачами указывать явно

### 3. Практичность (Actionable)
- Конкретные файлы/методы для изменений
- Проверяемые AC/DoD с чекбоксами
- Рабочие команды проверки
- Оценки сложности и времени

## Структура Задачи (Обязательные Секции)

### 1. Заголовок
```markdown
## Task: <тип_действия> — <краткое_описание_результата>
```

**Правила:**
- `<тип_действия>`: `tests`, `fix`, `implement`, `add`, `refactor`, `data`, `analyze`
- `<краткое_описание>`: 5-15 слов, фокус на результате
- **Примеры:**
  - `## Task: tests — реальный вывод каталога через CatalogService.send_catalog_to_user()`
  - `## Task: fix — Action 42 загружает заглушки вместо реальных переводов`
  - `## Task: implement — генерация Short description для WooCommerce CSV`

### 2. Цель (Purpose)
**Что должно быть достигнуто и почему это важно.**

**Обязательные элементы:**
- Четкий результат (что будет работать/доступно)
- Бизнес/технический риск при отсутствии решения
- Границы задачи (что НЕ входит в scope)

**Пример:**
```markdown
### Цель
Добавить тесты, которые проверяют **реальную бизнес-логику отправки каталога**, а не только факт вызова DI/handler.

### Почему это важно (риск)
Сейчас Telegram-каталог может "визуально работать" при моках, но **сломаться на реальной связке** formatter→image→keyboard.
```

### 3. Факты из Кода (Code Facts / SSOT)
**Источники истины - реальный код с цитатами.**

**Структура:**
- Нумерованный список фактов
- Каждый факт = ссылка на файл + цитата кода
- Пояснение к цитате (что она доказывает)

**Пример:**
```markdown
### 1) Handler вызывает сервис
- `bot/handlers/catalog/catalog_handlers.py`
  - `CatalogHandler.handle_show_catalog()`:
    - получает `catalog_service = get_catalog_service()`
    - `catalog_service.send_catalog_to_user(callback, products, loc)`

### 2) Сервис отправляет каждый продукт
- `bot/services/application/catalog/catalog_service.py`
  - `CatalogService.send_catalog_to_user(...)`:
    - для каждого продукта: `await self._send_single_product(callback, product, loc)`
```

### 4. Gap / Проблема (Gap Analysis)
**Что именно сломано/отсутствует в текущей реализации.**

**Фокус:** Конкретные проявления проблемы, а не общие жалобы.

### 5. AC/DoD (Acceptance Criteria / Definition of Done)
**Конкретные, проверяемые критерии успеха.**

**Формат:**
- Чеклисты с `[ ]` для каждого критерия
- Приоритизация: `(P0)`, `(P1)`, `(P2)`
- Измеримые результаты

**Пример:**
```markdown
### AC/DoD
- [ ] Тест вызывает **реальную** `CatalogService.send_catalog_to_user()`.
- [ ] При наличии `formatter_service`:
  - [ ] `formatter_service.format_product_for_telegram(product, loc)` вызывается 1 раз на продукт.
  - [ ] `ImageService.send_product_with_image(...)` получает корректный `product_text`.
```

### 6. Где Менять Код (Code Changes Location)
**Конкретные файлы, методы, функции для модификации.**

**Структура:**
- Файлы сгруппированы по роли (runtime, tests, data)
- Конкретные методы/классы
- Примеры изменений (diff-style)

### 7. План Выполнения (Execution Plan)
**Пошаговый план с мини-шагами и проверками.**

**Структура:**
- Нумерованные шаги
- Каждый шаг имеет "мини-детализацию" для точности
- Проверяемые критерии на каждом шаге

### 8. Команды Проверки (Verification Commands)
**Рабочие команды для тестирования результата.**

**Обязательно:**
- Команды до/после изменений
- Проверка на реальной среде (если применимо)
- Логи/вывод для анализа

## Типы Задач и Их Особенности

### Tests Tasks (Тестовые Задачи)
**Фокус:** Добавление недостающих тестов для покрытия gaps.

**Особенности:**
- Детальное описание моков/тестовых данных
- Фокус на "почему эти тесты важны"
- Архитектура тестов (unit/integration/e2e)

### Fix Tasks (Исправление Багов)
**Фокус:** Исправление конкретных багов с доказательствами.

**Особенности:**
- Воспроизводимые шаги для демонстрации бага
- Текущий vs ожидаемый результат
- Минимальные изменения (surgical fixes)

### Implement Tasks (Новые Фичи)
**Фокус:** Добавление новой функциональности.

**Особенности:**
- Детальная архитектура решения
- API контракты
- Backward compatibility

### Refactor Tasks (Рефакторинг)
**Фокус:** Улучшение кода без изменения поведения.

**Особенности:**
- "Что меняем" vs "что не меняем"
- Миграционные стратегии
- Тесты на preservation of behavior

## Правила Именования Файлов

### Формат
```
task-<тип_действия>-<краткое_описание>.md
```

### Примеры
- `task-tests-telegram-catalog-service-send-catalog.md`
- `task-fix-action42-productname-real-translations.md`
- `task-implement-woocommerce-short-description-export.md`

### Правила
- `<тип_действия>`: tests, fix, implement, add, refactor, data
- `<краткое_описание>`: kebab-case, 3-8 слов
- Максимальная длина имени файла: 80 символов

## Качество и Валидация

### Обязательные Проверки (Pre-Commit)
- [ ] Все AC/DoD начинаются с глагола действия
- [ ] Минимум 3 факта из кода с цитатами
- [ ] Имеются рабочие команды проверки
- [ ] Нет предположений ("должно быть", "вероятно")
- [ ] Все ссылки на код проверены (существующие файлы/методы)

### Рекомендации по Качеству
- **Конкретность:** Избегать слов "улучшить", "оптимизировать" без метрик
- **Тестируемость:** Каждый AC должен иметь способ проверки
- **Атомарность:** Задача должна решаться за 1-3 дня
- **Документированность:** Все термины/концепции объяснены

## Примеры Полных Задач

### Минимальная Задача (Tests)
```markdown
## Task: tests — CatalogService send_catalog_to_user orchestration

### Цель
Добавить unit-тест для проверки вызова formatter→ImageService в CatalogService.send_catalog_to_user().

### Факты из кода
1) `bot/services/application/catalog/catalog_service.py:260-270`
   - `send_catalog_to_user()` вызывает `_send_single_product()` для каждого продукта
   - `_send_single_product()` вызывает formatter и ImageService

### AC/DoD
- [ ] Тест проверяет вызовы formatter и ImageService с корректными аргументами

### Где менять код
`bot/tests/unit/test_catalog_service_send_catalog.py`

### План выполнения
1) Создать тест с моками formatter и image_service
2) Проверить вызовы после выполнения send_catalog_to_user()

### Команды проверки
```bash
cd bot && python -m pytest tests/unit/test_catalog_service_send_catalog.py -v
```
```

### Сложная Задача (Implement)
```markdown
## Task: implement — WooCommerce Short description генерация

### Цель
Реализовать автоматическую генерацию Short description для WooCommerce CSV на основе product metadata.

### Факты из кода
1) `bot/services/woocommerce/export.py:486` - поле захардкожено пустым
2) `bot/model/product.py` - содержит species, forms, categories, prices

### AC/DoD
- [ ] Short description генерируется из species + form + цена
- [ ] Длина <= 160 символов
- [ ] Fallback на пустую строку при отсутствии данных

### Где менять код
- `bot/services/woocommerce/export.py` - добавить функцию генерации
- `bot/services/woocommerce/export.py` - интегрировать в generate_*_row()

### План выполнения
1) Создать функцию format_short_description()
2) Интегрировать в экспорт
3) Добавить unit-тесты

### Команды проверки
```bash
cd bot && python utility/export_to_woocommerce.py --language ru --output test.csv
# Проверить колонку Short description
```
```

## Миграция Существующих Задач

### План Перехода
1. **Аудит существующих** - проверить compliance с новым стандартом
2. **Приоритизация** - начать с новых задач
3. **Градуальная миграция** - обновлять задачи при модификации
4. **Обучение** - документировать изменения для команды

### Совместимость
- Старые задачи остаются валидными
- Новые задачи следуют новому стандарту
- Инструменты работают с обоими форматами

## Заключение

Этот стандарт обеспечивает **систематический, проверяемый подход** к постановке задач, который:
- Сокращает время на анализ и планирование
- Минимизирует недопонимания в команде
- Обеспечивает traceability и accountability
- Поддерживает рост сложности проекта
