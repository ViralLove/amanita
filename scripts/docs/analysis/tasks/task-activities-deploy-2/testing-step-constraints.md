## 1. Что говорит методика

- **Этап 5 (реализация):** «Не считать этап 5 завершённым, пока не выполнена **фаза с тестами**», если она есть в плане.
- **Этап 7:** Квалификация тестов (test-qualification.mdc) — для **любого созданного/изменённого** набора тестов; отчёт в папку таска.
- **Этап 8:** **Верификация по критериям приёмки** — обязательна **перед коммитами**: прогон тестов (все зелёные) + сверка кода и тестов с AC таска; документ **acceptance-verification-*.md** в папку таска.

То есть в процессе заложено: (1) при наличии в плане фазы с тестами — её выполнить; (2) изменённые тесты проверить по test-qualification и зафиксировать в отчёте; (3) перед коммитами — верификация по AC и документ acceptance-verification.

## 2. Что есть у нас по деплою

- **Unit-тесты:** `scripts/tests/unit/actions/DeployActions.test.js`
  - **action1:** проверяют, что вызывается `deploySingleContract` для MagicRegistry, SpiralEngine, ProductRegistry, OrganicComponentRegistry, AmanitaInternational, SBT. Список UUPS **захардкожен** в тесте (четыре контракта).

## 3. Суть ограничений шага тестирования

### 3.1 Прогон существующих тестов

- После наших правок (ActivityRegistry в action1, action5, ContractManager) **unit-тесты DeployActions не проверяют** вызов `deploySingleContract('ActivityRegistry')`: в тесте перечислены только четыре UUPS без ActivityRegistry.
- **Тесты при этом не падают:** мы добавили ещё один вызов `deploySingleContract`, но тест не проверяет ни точное число вызовов, ни полный список контрактов — только наличие вызовов для четырёх имён. То есть **тесты остаются зелёными**, но **новое поведение (деплой ActivityRegistry) тестом не зафиксировано**.

**Ограничение:** если ничего не менять в тестах — формально «всё зелёное», но при рефакторинге кто-то может убрать ActivityRegistry из action1, и тесты этого не поймают.

### 3.2 Обновление тестов (рекомендуемый уровень)

- В тесте **«должен деплоить все UUPS контракты»** добавить одну строку:  
  `expect(mockContractManager.deploySingleContract.calledWith('ActivityRegistry')).to.be.true`.
- Тогда: (1) тест явно требует, чтобы action1 деплоил ActivityRegistry; (2) при удалении ActivityRegistry из action1 тест покраснеет.
- **Это считается изменением набора тестов** → по методике попадает под этап 7 (квалификация по test-qualification: честность, логика, приоритеты) и краткий отчёт в папку таска. Объём маленький: один новый expect, ложных успехов не добавляет.

**Ограничение:** нужно не забыть прогнать unit-тесты после правки и при желании оформить короткую квалификацию/отметку в отчёте.

### 3.3 Верификация по AC (этап 8) — обязательна перед коммитами

- Независимо от того, обновляли мы тесты или нет, **перед коммитами** по методике нужна **верификация по критериям приёмки таска** и документ **acceptance-verification-*.md**.
- В нём по каждому пункту AC (источник SpiralEngine, скрипт/деплой, localhost, проверка контракта) — как закрыто: код, вызов action1/action5, при необходимости ручная проверка на localhost; статус (выполнено / N/A с обоснованием).

**Ограничение:** без этого документа этап 10 (коммиты) по процессу не стартуем.

## 4. Варианты решения

| Вариант | Действия | Плюсы | Минусы |
|--------|----------|--------|--------|
| **A. Минимум** | Только прогнать существующие unit-тесты; верификация по AC (acceptance-verification) перед коммитами. Тесты в коде не трогать. | Быстро, тесты зелёные. | Деплой ActivityRegistry в action1 тестом не зафиксирован; рефакторинг может убрать контракт без красного теста. |
| **B. Рекомендуемый** | Добавить в тест action1 проверку `deploySingleContract('ActivityRegistry')`; прогнать unit-тесты; кратко зафиксировать в отчёте квалификации (или в acceptance-verification), что тест обновлён под новый контракт; верификация по AC перед коммитами. | Явное покрытие нового поведения; этап 7 выполнен. | Один правка в тесте + прогон + пара строк в отчёте. |
| **C. Расширенный** | Как B, плюс при необходимости отдельный тест для action5 с `DEPLOY_CONTRACT=ActivityRegistry` или проверка в E2E; при изменении тестов — квалификация по test-qualification с отчётом в папку таска. | Максимальное покрытие. | Больше времени и объём отчёта. |

---

## 5. Итог для решения

- **Constraint 1:** Перед коммитами в любом случае нужна **верификация по AC** и документ **acceptance-verification-*.md** (этап 8 методики).
- **Constraint 2:** Если **меняем/добавляем тесты** (вариант B или C), по методике это попадает под **квалификацию тестов** (этап 7): проверка по test-qualification и фиксация в отчёте.
- **Constraint 3:** Если тесты **не обновлять** (вариант A), новый контракт в action1 **не покрыт** unit-тестом — остаётся риск при рефакторинге.

**Рекомендация:** вариант **B** — одна строка в тесте action1 + прогон + краткая отметка в acceptance-verification (или в отдельном коротком отчёте квалификации), чтобы и процесс соблюсти, и поведение зафиксировать тестом.

Напиши, какой вариант выбираешь (A / B / C), и дальше выполню шаг тестирования соответственно.
