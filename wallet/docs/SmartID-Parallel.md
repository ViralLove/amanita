Amanita DApp
Account & Key Ownership Model

(Dynamic + External + Local wallets, Smart-ID-like UX)

Статус

Draft / Working document
Назначение: архитектурный и UX-якорь для всей системы аккаунтов Amanita

1. Цель документа

Зафиксировать честную, этичную и технически корректную модель владения аккаунтом и ключами в Amanita DApp, которая:

даёт smooth UX для новичков,

остаётся комфортной для web3-native пользователей,

не делает Amanita кастодианом,

не создаёт vendor lock-in,

повторяет фактические поведенческие паттерны Smart-ID, знакомые пользователям в Эстонии,

позволяет масштабировать систему и интегрировать её в другие e-commerce решения.

2. Базовый принцип (non-negotiable)

Amanita никогда не владеет ключами пользователя.

приватные ключи не хранятся на стороне Amanita,

Amanita не может подписывать действия за пользователя,

пользователь всегда имеет право:

подключить внешний кошелёк,

экспортировать ключ (если используется embedded),

уйти с активами и адресом без потери собственности.

3. Модель входа: выбор, а не навязывание
3.1 Экран выбора способа владения ключом

При первом входе пользователь осознанно выбирает, как он хочет работать с Amanita:

Быстро и просто
(через Dynamic: email / social / passkey / embedded wallet)

Подключить свой кошелёк
(MetaMask / WalletConnect / Phantom / др.)

Создать или восстановить адрес вручную
(self-custody, без участия Dynamic)

Важно:

варианты подаются без иерархии “умных” и “глупых”,

язык нейтральный, спокойный, как в e-gov интерфейсах,

пользователь понимает последствия каждого выбора.

4. Типы происхождения аккаунта (Account Origin)

В системе Amanita хранится тип происхождения ключа, а не “тип пользователя”.

account_origin:
  - dynamic_embedded
  - dynamic_external
  - external_wallet
  - local_wallet

Назначение account_origin:

корректный UX (что показывать / не показывать),

корректные подсказки по безопасности,

отсутствие скрытых ожиданий,

уважение к self-custody.

Account origin не используется для дискриминации в доступе к функционалу.

5. Роль Dynamic в системе Amanita

Dynamic используется исключительно как Identity & Wallet Onboarding Layer.

Dynamic обеспечивает:

аутентификацию пользователя,

доказательство контроля над ключом,

embedded wallets для новичков,

подключение внешних кошельков.

Dynamic не:

не делает Amanita кастодианом,

не даёт Amanita доступ к ключам,

не ограничивает право пользователя уйти.

Embedded wallets (Dynamic)

Если используется embedded wallet:

ключ хранится в MPC/TEE у Dynamic,

подпись всегда инициируется пользователем,

экспорт ключа обязателен в UX (escape hatch).

6. Local / External wallet путь (без Dynamic)

Для web3-native пользователей Amanita предоставляет путь:

создать новый адрес,

или восстановить существующий (seed / private key),

использовать его напрямую как external wallet.

В этом случае:

Dynamic не участвует,

адрес не появляется в Dynamic dashboard,

полная self-custody остаётся у пользователя.

7. Smart-ID-like модель подтверждений (ключевой UX-якорь)

Amanita Wallet/Profile реализует фактический функционал Smart-ID, а не его бренд.

7.1 Два уровня подтверждений (аналог PIN1 / PIN2)
Уровень A — “PIN1” (Authentication / Consent)

Назначение:

вход в систему,

подтверждение личности,

управление сессией,

просмотр приватных данных,

согласия без изменения публичного состояния.

Характеристики:

низкий friction,

частые действия,

не меняют публичное состояние,

не влияют на других пользователей.

Уровень B — “PIN2” (Commit / Signature)

Назначение:

on-chain транзакции,

действия, влияющие на других,

репутационные и рейтинговые изменения,

публикация товаров/активити,

выдача рекомендаций с весом,

делегирование прав,

экспорт ключа.

Характеристики:

повышенная строгость UX,

обязательное объяснение смысла подписи,

квитанция после выполнения,

логирование.

8. Принцип показа “ЧТО ИМЕННО ПОДПИСЫВАЕТСЯ”

Перед любым действием уровня PIN2 Amanita обязана показать пользователю человеко-понятное описание, а не сухую крипто-формулировку.

8.1 Стандарт экрана подтверждения

Экран подтверждения должен содержать:

Человекопонятный заголовок

“Опубликовать продукт в Amanita”

“Подтвердить покупку”

“Отправить рекомендацию”

Что изменится

какое состояние будет создано/изменено,

кто это увидит,

какие метрики затронуты.

Цена и риск

кто платит gas,

сумма (если есть),

обратимость / необратимость действия.

Технические детали (вторым слоем)

сеть,

контракт,

адрес пользователя.

Verification code / phrase

короткий код для сверки между экраном DApp и экраном подписи,

защита от подмены контекста (Smart-ID паттерн).

Явный выбор

“Подтвердить (PIN2)”

“Отмена”

Запрещено:

“Sign message” без объяснения смысла,

скрывать последствия действия,

маскировать approve/commit под “безопасное подтверждение”.

9. Профиль и метрики: честность и этика
9.1 Классы метрик — пока очень обще абстрактно, еще не адаптировано под реальное профилирование применимое для подбора рекомендаций

Self-claims (редактируемые)

самоописание,

предпочтения,

приватные настройки.

Derived metrics (нередактируемые напрямую)

надёжность,

качество рекомендаций,

поведенческие сигналы.

Attested metrics

подтверждённые действия,

VC / ZK-аттестации,

результаты арбитражей.

9.2 Этические принципы

пользователь видит, почему метрика такая,

пользователь знает, что на неё влияет,

есть процедура оспаривания,

нет “скрытого профайлинга”.

10. Децентрализация и право на выход

Amanita считается архитектурно честной, если:

пользователь может:

подключить внешний кошелёк,

экспортировать ключ,

использовать другой фронтенд,

Amanita не является единственной точкой контроля,

backend — оркестратор, а не источник истины,

ключевые состояния могут быть проверены независимо.

11. Итоговая формула

Dynamic — удобный вход, не тюрьма.

External / Local wallets — уважение к self-custody.

Smart-ID-like UX — безопасность через ясность, а не страх.

PIN1 / PIN2 модель — психологически и культурно понятная.

Чёткое объяснение подписи — обязательное правило.
