Amanita ID (Dynamic JS SDK) — Supporting Documentation
0) Что это такое

Amanita ID — это white-label страница авторизации (auth.amanita...) с Dynamic внутри, которую вызывает ваш Custom GPT через backend-сгенерированный redirect URL.

Dynamic закрывает:

social/email логин,

подключение внешних кошельков (MetaMask/WalletConnect/Phantom и т.п.),

embedded wallets (если включите),

выдачу сессионного состояния/токена на фронте, которое вы далее подтверждаете на backend.

Dynamic JS SDK строится вокруг Dynamic Client: его нужно создать (createDynamicClient) и инициализировать (initializeClient).

1) Что нужно создать/настроить тебе как создателю DApp
1.1 Аккаунт Dynamic + Environment

Создай проект в Dynamic Dashboard.

Получи Environment ID (он нужен в createDynamicClient).

Где хранить Environment ID:

в переменной окружения для вашего auth-фронта (например, DYNAMIC_ENVIRONMENT_ID),

не вшивать “навсегда” в код публичного репозитория.

1.2 Разрешённые домены / redirect URLs

Для social login redirect-flow тебе нужно заранее прописать разрешённый redirect URL. В Dynamic JS SDK в вызове указывается redirectUrl, куда провайдер вернёт пользователя.

Рекомендация для white-label:

фиксированный callback: https://auth.amanita.app/callback
или даже корень https://auth.amanita.app/ (если логика callback на той же странице).

Почему фиксированный: OAuth провайдеры почти всегда требуют предварительно whitelist-ить redirect URIs (это общий security-принцип OAuth, иначе можно украсть коды/токены через подмену redirect).

1.3 Включить методы аутентификации в Dynamic

В dashboard включи:

Social providers, которые хочешь (Google/GitHub/Discord и т.д.). Провайдеры перечислены в доке social sign-in.

External wallets (если хочешь BYO wallet).

Embedded wallets (опционально). Если включаешь embedded — обязательно показывай экспорт ключа пользователям (см. 6).

2) Как это интегрируется в твой DApp (и как GPT входит в поток)
Высокоуровневая логика

Custom GPT — UI/оркестратор.

Ваш backend — единственный источник истины для state, TTL и политик.

auth.amanita (white-label page) — фронт, который делает реальный login/connect через Dynamic JS SDK.

Dynamic — identity/wallet layer, который возвращает user-объект и токен на фронт, а вы уже “обмениваете” это на вашу сессию.

3) Рекомендованный security-контракт: state + sid + one-time code

Ваш backend должен создавать короткоживущую AUTH_SESSION:

sid (случайный id),

state (криптографически случайный),

return_to (куда вернуться),

intent (login / link_wallet / export),

TTL 5–10 минут.

Redirect URL формируете вы (не Dynamic), например:

https://auth.amanita.app/login?sid=...&state=...&return_to=...&intent=login

Дальше ваша страница:

запускает social redirect (или wallet connect),

по результату шлёт на backend /auth/complete {sid,state,dynamicProof}
и backend выдаёт one-time code, который потом попадает обратно в GPT.

4) Социальный логин через JS SDK (redirect-flow)

Dynamic JS SDK для social redirect описывает прямой паттерн:

Инициировать редирект: signInWithSocialRedirect({ provider, redirectUrl })

На загрузке страницы проверить, вернулся ли пользователь от провайдера: detectOAuthRedirect({ url })

Завершить логин: completeSocialRedirectSignIn({ url })

Этот flow идеально подходит под вашу white-label страницу.

5) Подключение внешних кошельков (MetaMask/WalletConnect/Phantom)

JS SDK позволяет:

Получить список доступных провайдеров: getAvailableWalletProvidersData()

Подключить и сразу верифицировать: connectAndVerifyWithWalletProvider({ walletProviderKey })

Важная деталь: Dynamic различает “connect” и “verify”; и есть режимы:

connect+verify одним вызовом,

connect без verify (временная сессия),

verify уже подключенного.

Для честной модели e-commerce/репутации я бы по умолчанию делал connect+verify.

6) Embedded wallet (если включите) и обязательная “дверь наружу”

Если вы используете embedded wallet, Dynamic прямо говорит: пользователям нужно предоставить способ экспортировать ключ, чтобы они сохраняли полный контроль.

Экспорт у Dynamic устроен так, что приватный ключ/seed показывается через secure isolated iframe, который вы не контролируете — это ограничивает возможность разработчика/третьих лиц украсть ключ.

Тебе это идеально ложится на философию:

новичкам — embedded,

“занудам” — возможность вывести ключ и импортировать куда угодно.

7) “Я могу делать любой функционал над этим адресом?” — да, но…

Ты можешь строить любой функционал вокруг подписываемого адреса, но есть два “стоп-знака”:

Адрес ≠ человек (Sybil, мультиакки, фермы).

“Над адресом” можно делать только то, что:

пользователь подписал/подтвердил, или

что можно доказать on-chain / через верифицируемые креды (VC/ZK).

Правильная формула:
(Dynamic verified wallet) + (ваши правила доверия) → права и возможности.

8) Функционал 1: баланс и базовый DeFi
Что можно сразу

Показывать баланс по адресам (EVM/Solana), историю транзакций, позиции.

Делать “1-клик” действия через AA (у вас слой Biconomy) — swap, stake, approve и т.п.

Риски и как не сломаться

Любой “DeFi функционал” требует чёткой UX-защиты: что подписывается, какие allowances, предупреждения.

На уровне Amanita ID лучше ограничиться:

“подключить/проверить” адрес,

“посмотреть” (read-only),

а транзакции делать в основном приложении (после полноценного consent).

9) Функционал 2: вывод метрик профилирования (безопасность, честность, этичность)

Вот тут самое важное — ты правильно чувствуешь риск.

Какие метрики вообще можно показывать

Публичные и “мягкие” (предпочтения, интересы, резонансные кластеры) — можно показывать пользователю полностью.

Сигнальные/репутационные (надёжность, качество рекомендаций, “вклад”) — лучше показывать в виде:

что влияет на метрику (прозрачность),

как оспорить (процедура),

что является доказательством (источники).

Можно ли редактировать метрики?

Моё жёсткое правило (иначе всё превращается в фарм):

Редактировать нельзя то, что используется другими как trust-signal.

Можно редактировать только:

самоописание (bio, предпочтения “я люблю X”),

приватные настройки видимости,

исправления фактов, которые подтверждаются доказательствами (например, “это не мой кошелёк” → отзыв привязки через подпись).

Практический паттерн:

Метрики делим на Self-claims (редактируемые) и Derived/Attested (не редактируемые).

Derived строятся либо:

из on-chain фактов,

из подтверждённых действий в платформе,

из VC/ZK-аттестаций.

Этичность

Чтобы избежать “скрытого профайлинга”:

в UI явно говорим: какие сигналы собираются, зачем, и как отключить.

даём режим “privacy”: минимальный профиль, но тогда рекомендации менее точные.

10) Функционал 3: геймификация вокруг e-commerce

Тут Dynamic ID просто даёт вам “якорь” (верифицированный аккаунт). Дальше вы можете:

бейджи/уровни/стрики,

кредиты на gas (спонсируемые действия),

“репутация продавца/покупателя” как VC или on-chain score,

доступ к “премиальным” витринам по кластеру резонанса.

Критично: геймификация должна быть анти-sybil (иначе будут фармить). Это решается:

rate limits на backend,

staking/bond для “взрослых” действий,

репутация через социальную валидацию/Активаторов,

платные/ресурсные “пороги” на ключевые награды.

11) Короткий checklist “готовности” Amanita ID

В Dynamic:

 создан environmentId

 включены social providers

 включены external wallets

 (опц.) включены embedded wallets + экспорт ключа в UX

В вашем backend:

 /auth/init создаёт sid/state/TTL

 /auth/complete валидирует sid/state и принимает proof

 one-time code → /auth/exchange для Custom GPT

В white-label странице:

 signInWithSocialRedirect + detectOAuthRedirect + completeSocialRedirectSignIn
