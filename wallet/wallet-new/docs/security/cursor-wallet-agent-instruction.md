# Cursor Agent Instruction — Reference-driven wallet development

Ты работаешь над Amanita Wallet (React Native, EVM, non-custodial). В воркспейсе есть:
- `apps/amanita-wallet/` — целевой проект
- `reference/metamask-mobile/` — референс (read-only), нельзя в него вносить изменения

## Главная цель
Реализовать фичу быстро и безопасно, используя MetaMask как “атлас паттернов”, но НЕ копируя код слепо.

## Рабочий протокол на каждую фичу (обязателен)

### Step 1 — Определи срез
1) Открой `docs/wallet-slices.md`
2) Найди срез, к которому относится фича (например, `06_transactions_lifecycle`)

### Step 2 — Прочитай Spec
1) Открой `docs/spec/<slice>.md`
2) Выпиши:
- Инварианты безопасности
- MVP scope / Not in MVP
- Публичный API
- Edge cases
- Минимальные тесты

Если Spec недостаточен — сначала дополни Spec (коротко), затем продолжай.

### Step 3 — Используй Reference Map (только для поиска паттерна)
1) Открой `docs/reference/<slice>-metamask-map.md`
2) Выполни targeted search в `reference/metamask-mobile` по указанным ключевым словам.
3) Извлеки 3 вещи в заметку:
- PATTERN: как у них устроен поток данных/контроллер/пайплайн
- BOUNDARIES: какие trade-offs и почему так
- MIN-EQUIVALENT: самый простой эквивалент для Amanita Wallet (без лишних зависимостей)

Запрещено:
- копировать большие блоки кода из reference
- переносить UI/feature flags/сервисные зависимости

Разрешено:
- переписать паттерн под наш API
- использовать маленькие open-source библиотеки (scure/noble/viem/keychain)

### Step 4 — Реализация в нашем проекте
1) Реализуй модуль/сервис строго под API из Spec.
2) Держи TCB минимальным:
- секреты → только secure storage
- подписи → только локально
- RPC → не доверять данным, валидировать
3) Пиши код так, чтобы модуль можно было заменить (интерфейсы).

### Step 5 — Explain / Diff / Test (gate перед завершением)
Перед тем как считать фичу готовой, агент обязан создать короткий отчёт:

**Explain (2 абзаца):**
- как работает фича (поток данных)
- какие инварианты соблюдены

**Diff (bullet list):**
- чем мы отличаемся от MetaMask и почему (упрощение/безопасность/независимость)

**Test (минимум 3 проверки):**
- unit/integration тесты или проверяемые сценарии
- обязательно покрыть edge cases из Spec

### Step 6 — Обнови документы
Если во время реализации выяснились новые инварианты/edge cases:
- обнови `docs/spec/<slice>.md`
- обнови `docs/reference/<slice>-metamask-map.md` (ключевые запросы/наблюдения)

## Дополнительные правила
- Любой код, касающийся секретов: никаких логов.
- Любой сетевой ответ считается недоверенным.
- Любая подпись/tx требует approval.
- Никаких внешних wallet-as-a-service зависимостей.
