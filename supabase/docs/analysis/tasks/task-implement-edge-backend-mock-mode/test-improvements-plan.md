# План доработки тестов: режим мока Backend (Edge)

**Таск:** task-implement-edge-backend-mock-mode  
**Контекст:** выводы из test-qualification-report.md и ответов на вопросы о тестах.  
**Процесс:** @run-analysis.md — фаза тестов и верификация по AC.

---

## Цель доработки

Устранить пробелы квалификации: проверять не только «нет fetch» и код ответа handler, а **реальное поведение мока** (проверка секрета, использование env/заголовков, симулированный код 200/404/409) и явно зафиксировать в тестах: при выключенном моке бекенд вызывается.

---

## Исходное состояние (что уже есть)

- **backend-mock.test.ts:** 4 теста (мок включён → нет fetch; override через ALLOW_REQUEST_OVERRIDE; override через X-Backend-Mock-Secret; неверный секрет). Проверки: `res.status`, `json.code`, `fetchCalls.length === 0`. Логи мока (`simulatedStatus`, `putStatus simulated N`) в тестах не перехватываются и не проверяются.
- **publish-flow.test.ts:** 4 теста на контракт publish; при выключенном моке проверяется наличие вызова putStatus через подмену fetch. Отдельного явного теста «мок выключен → fetch вызывается» нет.

---

## План доработок (по приоритету)

### 1. Проверка секрета (неверный секрет → заголовок игнорируется)

| Шаг | Действие | Критерий приёмки |
|-----|----------|------------------|
| 1.1 | В тесте «без override, секрет не совпадает»: задать `BACKEND_MOCK_PUT_STATUS=404`, в запросе передать `X-Backend-Mock-Secret: wrong-secret` и `X-Backend-Mock-Put-Status: 409`. | — |
| 1.2 | Перехватить `console.log` (подмена на функцию, сохраняющую аргументы в массив). После вызова handler найти в логах строку, содержащую `simulatedStatus` (или объект с полем `simulatedStatus`). | — |
| 1.3 | Утвердить: значение симулированного кода равно `404` (из env), а не `409` (из заголовка). | Тест явно проверяет: при неверном секрете заголовок переопределения не используется, используется env. |

**Файл:** `supabase/functions/arweave-upload/tests/backend-mock.test.ts`.

---

### 2. Явный тест: мок выключен → бекенд вызывается

| Шаг | Действие | Критерий приёмки |
|-----|----------|------------------|
| 2.1 | Добавить тест: не задавать `BACKEND_USE_MOCK` (или явно удалить). Задать `BACKEND_URL`, `EDGE_TO_BACKEND_SECRET`. Подменить fetch, запрос с невалидным токеном (401). | — |
| 2.2 | Утвердить: `fetchCalls.length >= 1`, есть вызов с методом PUT и URL, содержащим `/uploads/` и `status` (или `body` содержит `token_invalid`). | В документации тестов явно зафиксировано: при выключенном моке бекенд вызывается. |

**Файл:** `supabase/functions/arweave-upload/tests/backend-mock.test.ts` или оставить в `publish-flow.test.ts` с явным названием, например «publish flow: mock off -> putStatus calls backend (fetch invoked)». При желании можно вынести в backend-mock.test.ts для единообразия.

---

### 3. Проверка вариантов ответа мока (200, 404, 409)

| Шаг | Действие | Критерий приёмки |
|-----|----------|------------------|
| 3.1 | Ввести хелпер перехвата `console.log`: сохранять вызовы (например, аргументы как строки или структуры) в массив; в teardown восстанавливать оригинальный `console.log`. | Хелпер переиспользуется в тестах 3.2–3.4. |
| 3.2 | Тест «мок 200»: `BACKEND_USE_MOCK=true`, без override. Вызвать handler (невалидный токен). В перехваченном логе найти сообщение putStatus с `simulatedStatus: 200` (или отсутствие строки «simulated 404/409»). Утвердить. | Проверен вариант ответа 200. |
| 3.3 | Тест «мок 404 из env»: `BACKEND_USE_MOCK=true`, `BACKEND_MOCK_PUT_STATUS=404`. Вызвать handler. В логе найти «putStatus simulated 404» или объект с `simulatedStatus: 404`. Утвердить. | Проверен вариант 404. |
| 3.4 | Тест «мок 409 из заголовка»: `BACKEND_USE_MOCK=true`, `BACKEND_MOCK_ALLOW_REQUEST_OVERRIDE=true`, заголовок `X-Backend-Mock-Put-Status: 409`. Вызвать handler. В логе найти «putStatus simulated 409» или `simulatedStatus: 409`. Утвердить. | Проверен вариант 409 и то, что значение берётся из заголовка при разрешённом override. |

**Файл:** `supabase/functions/arweave-upload/tests/backend-mock.test.ts`.

**Примечание:** postCallback в моке вызывается только после успешной публикации в Arweave (асинхронный путь). Для полноты можно добавить отдельный тест с перехватом лога при сценарии, где вызывается postCallback (если такой сценарий в тестах возможен без реального Arweave), либо зафиксировать в плане как опциональный шаг P2.

---

### 4. Опции включения мока (.env и секрет) — проверка по эффекту

| Шаг | Действие | Критерий приёмки |
|-----|----------|------------------|
| 4.1 | Тест с `BACKEND_MOCK_ALLOW_REQUEST_OVERRIDE=true` и заголовком `X-Backend-Mock-Put-Status: 409`: дополнить проверкой перехваченного лога — в логе фигурирует `simulatedStatus: 409`. | Опция «override через .env» проверена по реальному использованию значения из заголовка. |
| 4.2 | Тест с верным `X-Backend-Mock-Secret` и заголовком `X-Backend-Mock-Put-Status: 404`: дополнить проверкой лога — `simulatedStatus: 404`. | Опция «override через секрет» проверена по эффекту (значение из заголовка применено). |

**Файл:** `supabase/functions/arweave-upload/tests/backend-mock.test.ts`. Часть проверок может быть объединена с шагами 1 и 3 (один тест с перехватом лога проверяет и секрет, и значение).
