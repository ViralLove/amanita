# Инфраструктура микросервиса: SOLID, безопасность, реплицируемость

Постоянный документ: оценка инфраструктуры с точки зрения SOLID и безопасности, возможность репликации для других микросервисов и ограничения по типам задач (производительность, безопасность).

**Версия:** 0.1.0  
**Методология:** анализ по @analysis.mdc, run-analysis.

---

## 1. SOLID и структура кода

### 1.1 Single Responsibility (SRP)

| Компонент | Ответственность | Оценка |
|-----------|-----------------|--------|
| `config.js` | Загрузка и парсинг env, формирование конфига и JWK | ✅ Одна зона ответственности |
| `auth.js` | Проверка Bearer-токена (опционально) | ✅ |
| `arweave-client.js` | Инициализация arweave и jwk для bundleAndPublish | ✅ |
| `logging.js` | Форматирование логов и хеширование | ✅ |
| `server.js` | HTTP-маршруты /health и /v1/crystalize, оркестрация verifyToken → validateDataItem → bundleAndPublish | ⚠️ При росте можно вынести обработчики в отдельные модули |

**Вывод:** границы модулей в целом по одному признаку; при расширении API имеет смысл вынести обработчики в отдельные функции/модули.

### 1.2 Open/Closed (OCP)

- Добавление нового endpoint или нового типа payload потребует правок в `server.ts` и, при необходимости, новых валидаторов/клиентов. Расширение без изменения существующего кода ограничено.
- **Репликация:** для нового микросервиса с другой доменной логикой (не Arweave) шаблон можно копировать и менять только доменный слой (вместо ArweaveClient — другой адаптер), не трогая обвязку (config, auth, validation, logging, Fastify).

### 1.3 Liskov Substitution (LSP)

- `ArweaveClient` используется через интерфейс `UploaderClient` в `buildApp` (тип `UploaderClient` в server.ts). Подмена на другую реализацию (мок, другой бэкенд) не ломает контракт.
- **Вывод:** ✅ подстановка реализаций поддерживается.

### 1.4 Interface Segregation (ISP)

- Публичный контракт сервиса — маршруты GET /health и POST /v1/crystalize; Arweave-слой используется только для подписи и отправки bundle (bundleAndPublish). Интерфейсы узкие.
- **Вывод:** ✅ клиенты не зависят от лишних методов.

### 1.5 Dependency Inversion (DIP)

- `buildApp({ config, arweaveClient })` принимает абстракцию `UploaderClient`; конфиг и клиент инжектятся при старте. Создание `ArweaveClient` в `startServer()` — композиция корня приложения.
- **Вывод:** ✅ зависимость от абстракции, не от конкретного ArweaveClient.

## 2. Безопасность (аудит)

### 2.1 Секреты и конфигурация

| Элемент | Практика | Оценка |
|---------|----------|--------|
| JWK | Только env или файл; не логируется | ✅ |
| RELAY_AUTH_TOKEN | Env; не логируется; сравнение не timing-safe | ⚠️ При необходимости — заменить на timing-safe сравнение |
| PORT / ARWEAVE_* | Без секретов в логах | ✅ |

### 2.2 Сеть и вход

| Элемент | Практика | Оценка |
|---------|----------|--------|
| Слушатель | `0.0.0.0` — ожидаемо для контейнера | ✅ |
| HTTPS | На edge (Railway); до сервиса — внутренняя сеть | ✅ |
| Входные данные | Валидация Zod; нет eval/exec; тело — только строка и hex | ✅ |

### 2.3 Авторизация

- Опциональный Bearer; при отсутствии `RELAY_AUTH_TOKEN` endpoint открыт (в проде не рекомендуется).
- Рекомендация: в production всегда задавать `RELAY_AUTH_TOKEN`. См. `docs/analysis/audit-bearer-auth.md`.

### 2.4 Исходящие вызовы

- Один внешний вызов — Arweave gateway (протокол/хост/порт из конфига). Риск: подмена gateway через env; митигация — контроль env в деплое.

## 3. Реплицируемость инфраструктуры для других микросервисов

### 3.1 Что можно переиспользовать без изменений

- **Слой приложения:** Fastify, раздача конфига из env, единая точка входа `startServer()`.
- **Паттерн:** config → buildApp(deps) → listen; зависимости (клиент к внешнему сервису) передаются снаружи.
- **Обвязка:** health endpoint, опциональная Bearer-авторизация, структурированное логирование (JSON), валидация входящего тела (Zod).
- **Инфраструктура:** Dockerfile (multi-stage Node), railway.json (DOCKERFILE builder, healthcheck), скрипт smoke по URL без порта.

### 3.2 Что нужно заменить под новый микросервис

- **Доменный слой:** вместо `ArweaveClient` — свой адаптер (БД, другой API, очередь и т.д.), реализующий узкий интерфейс под задачу.
- **Валидация:** свои схемы под новый контракт запросов.
- **Конфиг:** свои env-переменные (без ARWEAVE_*, с своими секретами и URL).
- **Теги/контракт ответа:** под домен (не transaction_id/url, а свои поля).

### 3.3 Ограничения при репликации

- **Один основной сценарий на сервис:** текущий шаблон заточен под один тип операции (upload crystall). Несколько разнородных сценариев лучше разносить по разным сервисам или явно выделять в отдельные модули/маршруты.
- **Состояние:** сервис stateless; персистентное состояние не предусмотрено. Для сценариев с очередями/БД нужно добавлять свои адаптеры и конфиг.
- **Порты:** приложение слушает один порт (PORT из env); платформа задаёт порт — не зашивать в коде.

## 4. Ограничения по типам задач (производительность и безопасность)

### 4.1 Производительность

| Фактор | Ограничение | Рекомендация |
|--------|-------------|---------------|
| Пропускная способность | Один процесс Node; блокировки только на I/O (Arweave gateway) | Для высокого RPS — горизонтальное масштабирование (несколько реплик), лимиты на стороне платформы. |
| Таймауты | Нет явного таймаута на вызов Arweave в коде | При необходимости — задать timeout в клиенте Arweave или обернуть post() в Promise.race. |
| Размер тела | Нет жёсткого лимита в коде; Fastify по умолчанию ограничивает тело | Для больших payload — проверить/настроить limit в Fastify. |
| Ключ и подпись | Подпись в основном потоке | При очень высокой нагрузке рассмотреть вынос подписи в worker/очередь (усложнение архитектуры). |

### 4.2 Безопасность

| Фактор | Ограничение | Рекомендация |
|--------|-------------|--------------|
| Bearer | Сравнение не timing-safe | В средах с высокими требованиями — заменить на timing-safe сравнение. |
| Открытый режим | При отсутствии RELAY_AUTH_TOKEN endpoint открыт | В production не использовать без токена. |
| Секреты в env | Риск утечки через логи/метрики | Не логировать env; использовать секрет-менеджер платформы (Railway Variables и т.п.). |
| Arweave gateway | Доверие к host/port из конфига | Жёстко контролировать env в деплое; при необходимости — pin к конкретному хосту. |

### 4.3 Типы задач: где шаблон подходит

- **Подходит:** stateless HTTP API с одним-двумя сценариями, внешний вызов к одному бэкенду (Arweave, другой API, при добавлении адаптера — БД/очередь), опциональная Bearer-авторизация, деплой в контейнере с портом из env.
- **Частично подходит:** несколько сценариев — можно добавить маршруты и валидаторы, сохраняя обвязку (config, auth, logging, health).
- **Не подходит без доработок:** долгие фоновые задачи, сложная оркестрация, состояние в памяти, несколько разнородных бэкендов с разными SLA — потребуются отдельные воркеры, очереди, явные таймауты и политики повторных попыток.

## 5. Чеклист репликации

При создании нового микросервиса на этой основе:

- [ ] Скопировать обвязку: config (под свои env), auth, logging, server (health + шаблон маршрута).
- [ ] Заменить доменный адаптер (интерфейс + реализация) вместо ArweaveClient.
- [ ] Задать свои Zod-схемы и типы ответов.
- [ ] Обновить Dockerfile/railway.json при необходимости (тот же шаблон обычно подходит).
- [ ] Настроить секреты и RELAY_AUTH_TOKEN (или аналог) в деплое.
- [ ] Адаптировать smoke-скрипт под новый URL и контракт (при необходимости).
- [ ] Учесть ограничения раздела 4 для целевой нагрузки и требований безопасности.
