# Требования: WordPress / WooCommerce ↔ Bot API

Документ фиксирует **продуктовый замысел** и границы **текущего** REST-слоя. Фактические контракты — **[`api.md`](./api.md)** и OpenAPI.

## Что уже отражено в Bot API

| Область | REST (см. `api.md`) | Примечание |
|---------|---------------------|------------|
| API-ключи продавца | `/api-keys/*` | HMAC |
| Каталог / загрузка продуктов | `/products/*`, `/media/upload`, `/description/upload` | HMAC |
| Аутентификация клиента | HMAC-заголовки | §3.1 `api.md` |

Требования к полям продукта и потоку CID — **[`commerce-upload-flow.md`](./commerce-upload-flow.md)**.

## Вне текущего Bot API (план или другие компоненты)

Следующие блоки из исходной постановки **не** описаны как отдельные маршруты в `bot/api/routes` на момент сверки с `api.md`:

- Управление **заказами** (создание/статусы в блокчейне из WP).
- **Инвайты** и онбординг продавцов через этот REST-слой.
- **Аналитика**, пуш-уведомления WP, полная двусторонняя синхронизация каталога.

Их реализация — отдельные эпики (контракты, бот, плагин); не смешивать с ожиданиями от существующих путей `/products` и т.д.

## Нефункциональные требования (сжато)

- **Задержка:** целевой порядок — единицы секунд для типичных вызовов; тяжёлые операции — асинхронно/очереди (вне scope данного файла).
- **Безопасность:** HMAC, секреты не в логах; расширения — см. `api.md` §8.
- **Надёжность:** ретраи и идемпотентность на стороне плагина там, где API не гарантирует повторный приём без побочных эффектов.

## Сценарии (только покрытые API)

1. **Продавец публикует товар из WooCommerce:** загрузка медиа/описания → CID → `POST /products/upload` с HMAC (детали — `commerce-upload-flow.md`).
2. **Управление ключами API** для интеграции — через `/api-keys` при наличии прав в блокчейн-слое (см. сервис ключей).

Остальные сценарии (заказы, инвайты) — после появления соответствующих эндпоинтов или сервисов.
